Part 4 of a series — designing the system around the model, so the agents and skills you build behave the same way on the hundredth run as on the first

Who this is for

  • Engineers who already build their own skills, subagents or agent pipelines and want them to be reliable, not just impressive in a demo.
  • People who keep hearing "harness engineering", "loop engineering" and "graph engineering" and want to know what each one actually means, and how they fit together.
  • Anyone who has watched an agent claim success on a task that failed, and wants to know which part of the system to fix.
  • Assumes fluency with Parts 1 and 2: you know the agent loop, context windows, tool calls, skills and subagents, and you have shipped something with an agentic tool.

The gap this fills

  • Part 2 taught you to work with an agent. This part teaches you to design the system the agent runs inside: what it sees, what it may touch, what it remembers, who checks it, when it stops, and how its steps connect.
  • During 2026 that design work picked up a stack of new labels. They are loosely defined, they overlap, and most explanations come from vendor blogs. This guide strips the labels back to the problems they solve.
  • It is a learning guide, not a cookbook. You finish with mental models and an audit checklist. Rewriting your own skills is a separate, later job, and you will do it better for having the models first.
  • Part 4 is a depth axis off Part 2, not a sequel to Part 3. Part 3 is about how an organisation adopts agents; this part is about how one agent system is built.

The Map

One equation, six questions, an outer loop, a short history of the buzzwords, and the running example — the backbone of everything that follows

Agent = Model + Harness

  • The model turns text into text. On its own it cannot read your files, run a command, remember yesterday, check its own work or verify that it is done.
  • The harness is everything else. LangChain's working definition (Mar 2026): "A harness is every piece of code, configuration, and execution logic that isn't the model itself."
  • So when an agent misbehaves, there are only two places to look: the model, or the harness. You can rarely change the model. You can almost always change the harness. That is why this guide spends its time there.

The six questions

Every harness, however it is built, answers these six questions. This is the single taxonomy used across the guide — chapter grouping, the failure map, the netpush dissection and the audit checklist.

The outer loop

  • The six questions describe one run. The outer loop works across runs: traces and failures from past runs come in, edits to the harness go out — a new check, a sharper instruction, a tighter permission.
  • Done by hand, this is a habit: "it got that wrong, so I'll fix the harness so it can't again." Done by an agent, it is a self-improving harness — powerful, and risky if the agent can edit its own judge. See Ch 14.
  • The simplest version in this guide is crash-doctor, a debugging skill that appends what it learned to a lessons.md file after every session and reads it at the start of the next.

From prompt to harness — and where loop and graph sit

  • The popular story is a lineage of eras: prompt engineering → context engineering → harness engineering → loop and graph engineering. Drew Breunig (Oct 2026) traces the first three steps and sums up the direction: "We're moving more and more of the work of assembling context from probabilistic model calls to deterministic code."
  • Each step contains the last. Palo IT's "Beyond the Prompt" lays the terms out as nested layers — prompt ⊂ context ⊂ harness ⊂ loop ⊂ graph — and stresses that none deprecates the layer below. codecentric (secondary, Jul 2026) adds that weaknesses in a lower layer get amplified by repetition.
  • This guide draws the last two rings differently. If a harness is everything that isn't the model, then the loop (control flow over time) and the graph (control flow across components) are parts of the harness, not layers above it. LangChain's own anatomy already lists orchestration — subagents, handoffs, routing — as a harness component, and its graph-engineering post calls a loop "a simple form of graph".
  • Why the nested view is more useful: it stops you treating "loop engineering" as a new thing to adopt. A loop with a weak checker is a weak harness that fails faster. You fix it in the checker, not by adding more loop. Ch 1 makes this argument in full.

1. The Model Is Not the Agent

What does it see? What can it do? What does it remember? How is it checked? How does it repeat? How do the pieces connect? Solid

What you'll learn: what a raw model cannot do on its own; what a harness is, in one sentence; how "prompt engineering" became "context engineering" became "harness engineering"; and why it is more useful to see loop and graph as parts of the harness than as new eras that replace it.

1.1 What a raw model can't do

Recap from Part 2 · Ch 1 The Agentic Coding Loop: an agent is a model called in a loop, with tools, until a goal is met. Strip away the loop and the tools and you are left with a function: text in, text out. That function is remarkable — and on its own it is not an agent.

Six things a bare model cannot do

  • See anything you didn't paste in. It has no view of your repo, your devices or today's date.
  • Act. It can write the words apply change; it cannot run them.
  • Remember between calls. Each call starts from an empty slate plus whatever you send.
  • Check its own output against reality. It can say "this config is valid"; that sentence is a prediction, not a test.
  • Repeat or stop. It doesn't retry on failure, and it can declare itself done but cannot verify it.
  • Coordinate with other steps, other agents or a human who must approve.

The pattern

  • Each missing ability maps to one of the six questions in The Map. That is not an accident: the six questions are simply the list of things a model can't do for itself.
  • Every working agent you have used fills these gaps with code and configuration. That code is the harness.

1.2 The harness, defined

LangChain's "The Anatomy of an Agent Harness" (Mar 2026) gives the definition this guide uses: Agent = Model + Harness, where "a harness is every piece of code, configuration, and execution logic that isn't the model itself."

What counts as harness

  • The system prompt and skill instructions (what it sees).
  • Tools, MCP servers and permission rules (what it can do).
  • Files it reads and writes between turns: plans, progress notes, reports (what it remembers).
  • Tests, linters, dry-runs and hooks that judge its output (how it is checked).
  • The loop that calls it again, with retry rules and stop rules (how it repeats).
  • Orchestrators, subagents, routing and approval gates (how the pieces connect).

Why the definition is useful

  • It is a complement: anything you can change that isn't the model's weights is harness. That makes the boundary easy to find in any system.
  • It tells you where your leverage is. You don't train the model. You do own the harness, end to end.
  • Early evidence (one study) points to the harness as where gains are. That study (as of Oct 2026) auto-evolved only the harness of a coding agent and raised its Terminal-Bench 2 pass rate from 69.7% to 77.0%, beating a human-designed harness at 71.9%; tools, middleware and memory mattered more than the system prompt (Lin et al., arXiv 2604.25850).
Model vs. harness is the first diagnostic split. When an agent fails, ask first: could a better harness have prevented this — by showing it the right thing, refusing the action, catching the bad output, or stopping the loop? Usually the answer is yes. Ch 13 builds that into a symptom table.

1.3 Prompt → context → harness: a short lineage

The names changed because the place where the work happened kept moving outward from the prompt.

1
Prompt engineering (~2022–2023)

The work is wording: instructions, examples, output format in a single message. The unit is one call.

2
Context engineering (from mid-2025)

The work is choosing everything in the window: retrieved files, tool results, history, notes. Anthropic (Sep 2025) frames context as a finite budget — "context rot" degrades recall as the window grows — managed with just-in-time retrieval, compaction, notes and sub-agents.

3
Harness engineering (from Feb 2026)

The work moves out of the window and into code: tools, checks, state files, hooks. Drew Breunig (Oct 2026): "as we moved more of these tools out of the context and into code, we started calling it harness engineering."

What actually changed at each step

  • Each step widened the scope of what you design: one message, then the whole window, then the whole system around the window.
  • Each step moved work from probability to determinism. Breunig's summary: "We're moving more and more of the work of assembling context from probabilistic model calls to deterministic code." Ch 2 is about doing that move deliberately.
  • None of the earlier skills went away. You still write prompts; they now live inside skill files that a harness loads.

1.4 Eras vs. nesting: where loop and graph belong

After "harness" came "loop engineering" Partly real (Jun 2026) and "graph engineering" Rebranding (Jul 2026). It is tempting to read the list as a series of eras, each one replacing the last. That reading causes real design mistakes.

The "eras" view and its trap

  • Eras view: prompt → context → harness → loop → graph, each a new thing to adopt.
  • The trap: when something fails, you reach for the newest layer. Agent unreliable? Wrap it in a loop. Loop unreliable? Turn it into a graph. Each wrapper repeats the underlying weakness more often, and more expensively.
  • codecentric (secondary, Jul 2026) puts it plainly: weaknesses in a lower layer get amplified by repetition.

The nested view (and two ways to draw it)

  • Palo IT's "Beyond the Prompt" draws the terms as nested rings — prompt ⊂ context ⊂ harness ⊂ loop ⊂ graph — and stresses that none deprecates the one below. That fixes the "replacement" error.
  • This guide nests the last two the other way round: loop and graph are components inside the harness. The loop is control flow over time; the graph is control flow across components. Both are "code, configuration and execution logic that isn't the model" — harness by definition.
  • The sources support this reading. LangChain's harness anatomy lists orchestration (subagents, handoffs, routing) and hooks as harness components. LangChain's graph post (Jul 2026) calls a loop "a simple form of graph" and notes that some open-ended tasks suit a harness better than a predefined graph — the two are design choices at the same level, not successive eras. LangChain uses "harness" for a single agent's runtime; in this guide's broad sense both options live inside the harness.
  • MindStudio (secondary) offers a one-liner that fits: "The loop is the agent's behavior. The harness is the agent's environment." In this guide, the environment includes the code that drives the behaviour.

Why the nested view wins in practice

  • It points at the real fix. A loop is only as good as its checker (Ch 7). If retries keep "succeeding" on bad output, the fix is the checker, not more loop.
  • It keeps one checklist. Six questions cover every layer, so your audit (Ch 17) doesn't grow a new section each time a new label trends.
  • It survives the next buzzword. Whatever "___ engineering" arrives next, ask which of the six questions it answers. If it answers none, it is probably a rebrand.
Contested, as of Oct 2026. Practitioners don't agree on how these terms nest, and an academic review of loop engineering (Lulla et al., arXiv 2608.21884) found broad agreement on loop components but no systematic evidence yet for the claimed benefits. Treat the nesting here as a design tool, not settled fact.

1.5 Harness engineering: solid or hype?

Why it is marked Solid

  • It names a real, separable body of work with a clear boundary (everything that isn't the model).
  • There is evidence beyond anecdote: a source-code study of production harnesses, a controlled harness-evolution experiment, and enterprise case studies that moved rules from prompts into code.
  • OpenAI's harness post (Feb 2026) and its author's Latent Space podcast interview (Apr 2026) report a team building ~1M lines over ~5 months with no hand-written code, where the engineers' job became designing environments, specifying intent and building feedback loops. Treat the numbers as one team's report, not a benchmark.

Where to stay sceptical

  • The term is new; its edges (is a CI pipeline "harness"?) are still argued. The definition is useful precisely because it is broad.
  • "We do harness engineering" says nothing about whether a team's checkers are any good. Judge the harness, not the label.
netpush
  • The model in netpush does two jobs: generate config from intent, and summarise the generated config for the approver. Everything else — parallel preflight, the dry-run checker, the approval gate, serial deploy (core first), verify, plan.yaml — is harness.
  • Swap in a stronger model and none of those guarantees improve. Give a frontier model only the tools and none of the rest of the harness, and it would happily push untested config to all six routers.
What this means for your skill
  • If you list everything in your skill that isn't the model, which of the six questions does each part answer — and which question has nothing answering it?
  • When your skill last failed, did you fix the prompt, or a harness part (a check, a permission, a state file)? Would the harness fix have held up better?
  • Are you adding a loop or extra agents to cover a weakness that a single better check would remove?
  • Which of your skill's behaviours depend on the model "remembering" or "checking" something it has no way to do?

2. Code vs. Model: Where Each Decision Belongs

How is it checked? What can it do?

What you'll learn: the single most important design decision in any harness — for every step, does code decide or does the model decide? You'll get the determinism dial as a mental model, a rule table for placing decisions, four tests for the hard cases, the hand-off pattern that joins code and model safely, and what goes wrong when you get it wrong in either direction.

The chapter in one line

The model proposes; code disposes. Let the model do what only a model can — synthesis, judgement, language. Let code do everything that has a right answer you can write down — parsing, matching, ordering, asserting and committing. Then make sure the code is actually right.

2.1 The determinism dial

Every decision in an agent system sits somewhere on a dial. At one end, code: same input, same output, every time. At the other, the model: flexible, able to handle inputs you never anticipated, and different on every run.

What each end gives you

  • Code end: repeatable, testable, auditable, cheap and fast. Brittle when the input is open-ended — natural language, unfamiliar error text, a new device output format.
  • Model end: handles novelty, ambiguity and language. Non-deterministic, harder to test, costs tokens, and can be confidently wrong.
  • The middle: constrained model output — the model fills a JSON schema, picks from a fixed list, or emits a diff that code then validates. Most good harness steps live here.

The trend, and why it isn't a rule

  • Breunig (Oct 2026) describes the field "moving more and more of the work of assembling context from probabilistic model calls to deterministic code". Over time, decisions slide toward the code end as teams learn what has a right answer.
  • That doesn't mean "code everything". It means: every time you notice the model making a decision with a right answer, that decision is a candidate to move.

2.3 Four tests for the hard cases

When a decision isn't obviously in the table, run it through these in order. The first "yes" usually settles it.

1
Is it irreversible or does it touch the outside world?

Yes → code owns the gate, even if a model proposed the action. Commits, deletes, pushes, messages to people. The model may suggest; code decides whether it runs.

2
Can you write down the right answer?

Yes → code. If you can write a test with an expected value, you can write the function. "Is BGP session state Established?" has an answer. "Is this change safe?" does not.

3
Is the input open-ended?

Yes → model, with structured output. Free text from a human, an error message you have never seen, a request to "make it like the other one". Code here becomes an endless pile of special cases.

4
Can code cheaply check the model's answer?

Yes → let the model decide and have code verify. This is the sweet spot: model flexibility, code reliability. No → add a human node (Ch 12) or narrow the task until code can check it.

"Who checks?" is part of the placement. A model decision with a code checker behind it is safe to automate. A model decision checked only by another model call is two guesses. A code decision checked by nothing is a guess written in a more confident font.

2.4 The hand-off: model proposes, code disposes

Real steps mix both. The skill is designing the seam so neither side can corrupt the other.

The three-beat pattern

  • Code gathers facts. Run the commands, parse the output, put clean structured data in front of the model. The model never scrapes raw text it could misread.
  • The model judges or generates. It returns a structured result — a JSON object, a choice from a list, a config block — not prose.
  • Code checks and acts. Validate the shape, run the dry-run, assert the invariants, then and only then perform the side effect.

Rules for the seam

  • Give the model a schema, not a request for "a summary". Free prose can't be checked.
  • Never let the model's words be the success signal. "Deployed successfully!" from a model is a claim; a parsed state value is evidence.
  • Keep the checker out of the model's reach. If the agent can edit the code that judges it, you've moved the decision back to the model by the back door (Ch 7).

What the research says (as of Oct 2026)

  • Ahn & Kim (arXiv 2607.08028) moved validation rules and schemas out of prompts and into code. Only the code-owned enforcement blocked every violation without hurting usefulness (120/120); a bolt-on guardrail over-refused (88/120).
  • Zhang (arXiv 2604.17025, single-author — read as an example, not consensus) reports that task decomposition, a machine-readable rule registry behind a fixed assertion interface, and state-locked feedback together made agent workflows more deterministic, with ablations suggesting all three are needed.

2.5 Getting it wrong, both ways

Too much model

Silent failures: the model reads a failed commit and reports success, because the output "looked fine".

Flakiness: the same input passes today and fails tomorrow; you can't reproduce the bug.

No audit trail: "why did it deploy?" has no answer beyond "the model thought so".

Cost: you pay tokens for decisions a ten-line function makes for free.

Too much code

Brittle parsing of language: regex over free-text error messages that breaks on the next wording change.

Rule explosion: nested if/else trying to encode judgement, never finished.

Rejecting valid variety: the harness refuses inputs a model would have handled fine.

Over-rigid flow: LangChain notes some open-ended tasks suit a flexible harness better than a predefined graph.

The subtle third failure: code that is deterministic and wrong

  • Moving a decision into code makes it repeatable, not right. A wrong pattern fails the same way every time — quietly.
  • Code-owned decisions need their own tests, built from real outputs, including the ugly ones: aborts, partial successes, warnings, truncated output.
  • The safest matchers are positive: look for the one string that proves success, anchored to the final status line, and treat anything else as failure. A negative matcher ("no error found") passes everything it didn't anticipate.

2.6 Moving a decision along the dial

Placement isn't fixed. A healthy harness moves decisions toward code as you learn which ones have right answers.

Signals a decision should move toward code

  • You keep correcting the model on the same point. That correction is a rule; write it down as code.
  • The model's choice is almost always the same. Hard-code it and save the tokens and the variance.
  • A failure would be expensive or irreversible. Put a deterministic gate in front of it, even if the model still proposes.

Signals a decision should move toward the model

  • The code is a growing list of special cases and still misses new ones.
  • Inputs are written by humans, or vary by device and version in ways you can't enumerate.
  • A cheap code check exists for the model's answer — so letting the model decide costs little risk.
This is the outer loop in miniature: each failure is a chance to move one decision to the end of the dial where it belongs (Ch 14).
netpush
  • Model: generate config from intent; summarise the generated config for the approver. Both are open-ended language tasks with a code check behind them (dry-run, then the human).
  • Code: parse CLI output, match success/fail, enforce core-first serial deploy, cap generate ↔ dry-run at max 3 attempts, stop on the first router failure.
  • The lesson of flaw 1: correct placement isn't enough. The success matcher was code, but negative and untested against real abort output.
What this means for your skill
  • List every decision your skill makes. For each: is it code or model today, and which of the four tests puts it there?
  • Where does your skill accept the model's own words ("done", "passed", "looks good") as a success signal?
  • Do your code matchers look for proof of success, or for absence of an error string? Have you tested them against a real failure output?
  • Where does the model hand data to code (or back)? Is that hand-off a schema, or free prose?

3.2 How the components lean on each other

The six aren't independent. Most real failures sit at a boundary between two of them.

  • Tools × graph: a write tool on the wrong node (say, a generator that can also deploy) skips every gate the graph was drawn to enforce.
  • State × loop: a loop that resumes from state must know which steps already ran, or it repeats side effects.

The honest answer as of Oct 2026: evidence is early, but it points away from the prompt.

4. What It Sees

What does it see? Solid

What you'll learn: why the context window is a harness layer you design rather than a bucket you fill; how progressive disclosure keeps the window small; why a skill is really on-demand context; what to keep out on purpose; and where context ends and state begins.

4.1 Recap: context is working memory

Part 2 · Ch 2 Context as Working Memory covered the basics: the context window is everything the model can see on this turn — system prompt, instructions files, tool results, the conversation so far. It is finite, it fills up, and it degrades as it grows. This chapter takes the designer's view instead: the harness decides what goes in, when, and in what shape. That decision is yours, not the model's.

4.2 Context is a budget, not a bucket

One-line definition: context design is choosing what the model sees on each turn so it has what it needs for this step and nothing that distracts from it.

What breaks without it

  • More tokens is not more knowledge. Anthropic's context-engineering guidance (Sep 2025) names context rot: recall gets worse as the window fills, because the model has a limited attention budget to spread across everything in it.
  • A stuffed window fails quietly. The fact the model needed is technically present, but buried under 40 KB of logs, so it is ignored. You see "the agent forgot the rule" when the real bug is "the harness drowned the rule".
  • Drew Breunig (Oct 2026) names a related failure, context inertia, and notes that resetting the context is often the fix.

The shift: from model calls to code

  • Breunig's summary of the trend (as of Oct 2026): "We're moving more and more of the work of assembling context from probabilistic model calls to deterministic code." The harness, not the model, picks what to load.
  • A source-code study of 11 production coding-agent harnesses (Barbaste et al., Jul 2026) found none use vector-embedding retrieval. They load context with plain tools — files, search, explicit reads. Treat that as a data point about current practice, not a law.
Rule of thumb. Every token in the window should earn its place for the step being run now. If you can't say which decision a block of context informs, it probably shouldn't be there.

4.3 Progressive disclosure

Progressive disclosure means showing the model a short index first and loading the detail only when a step actually needs it. It is the main tool for keeping the window small without hiding anything.

Three tiers of context

  • Always loaded: a few lines of identity, hard rules, and an index of what else exists. Keep it short enough that you would read all of it yourself every time.
  • Loaded on demand: a procedure, a reference table, a schema — pulled in by name when the current step calls for it.
  • Fetched just in time: live data (a file, a command output, a device's running state) read by a tool at the moment of use. Anthropic's guidance calls this just-in-time retrieval: keep lightweight pointers in context and fetch the content when needed.

Skills are on-demand context

  • In Claude Code (as of Oct 2026), only a skill's short description sits in context. The full SKILL.md body loads when the skill is invoked, and its supporting files load only when the body points to them.
  • So a skill is progressive disclosure packaged as a folder. The description is the index entry; the body is the on-demand tier; the supporting files are the just-in-time tier.
  • Design consequence: the description is the most important line you write. If it doesn't say when to use the skill, the detail never loads, however good it is.

Subagents as context isolation

  • A subagent runs in its own context window (Claude Code docs, as of Oct 2026). Give it a noisy job — read 30 files, parse long output — and only its short summary comes back to the parent.
  • That is progressive disclosure for work: the parent sees the conclusion, not the raw material.

4.4 What to keep out

Deciding what the model must not see is as much a design act as deciding what it must see. Each item below has a cost if it gets in.

4.5 Context vs. state: where the line is

Context is what the model sees now. State is what the system knows across turns, sessions and crashes. They are different layers, and mixing them up is a common design bug.

The test

  • Ask: "If the window were wiped right now, would the run be lost?" If yes, you are storing state in context. Compaction, a crash, or a new session will lose it.
  • Context should be rebuilt from state, not be the state. A good harness can reload the important parts from files at any point.
  • Rule: anything you would need to resume goes in a file. Anything only needed for this step stays in context. Ch 6 builds on this line.
netpush
  • Each preflight worker reads one router's running state in its own context. The orchestrator gets back a short structured result, not the raw CLI dump.
  • generate sees the intent from plan.yaml plus the preflight summaries — not six routers' full configs at once.
  • The approver sees a model-written summary of the generated config (v1 computes no diff; Ch 16 adds one). Summarising is model work; deciding what is in the change is not (see Ch 2).
  • The orchestrator's own context holds the current stage only. Everything it would need after a crash lives in plan.yaml and reports/ (Ch 6).
What this means for your skill
  • Does the skill's description say when to use it, clearly enough that it loads at the right time and not otherwise?
  • Which parts of the body are needed on every run, and which could move to a supporting file that loads on demand?
  • Where does a tool dump raw output into the window that code could summarise first?
  • If the window were wiped mid-run, what would be lost that should have been in a file?
  • Can the agent see the code that grades it — and does it need to?

5. What It Can Do

What can it do?

What you'll learn: why the tool surface is a design decision with real consequences; few sharp tools vs. many general ones; how to size blast radius; the commit-with-auto-rollback pattern for actions on real devices; and why most workers should be read-only.

5.1 Recap: tools are how the agent touches the world

Part 2 · Ch 3 Tools, Side Effects & the Agent's World covered what tools are, how permissions gate them, and why side effects need care. Here the question is the designer's: given a job, which tools should exist, how much can each one change, and where do you put the guard? A harness that answers this well makes many mistakes impossible rather than merely unlikely.

5.2 Shape of the tool surface

The tool surface is the set of actions the agent can take and the shape of each one: its inputs, its outputs, and what it is allowed to touch.

Few sharp tools vs. one big general tool

Few sharp tools

  • read_running_config(router), dry_run(router, file), commit_confirmed(router, file)
  • Each does one thing; inputs are typed; output is structured
  • Easy to permit, log, and test in isolation
  • Cost: you must build them, and they don't cover surprises

One general tool

  • A shell: ssh router "<anything>"
  • Covers every case, including ones you didn't foresee
  • Permission is all-or-nothing; review means reading every command
  • Cost: blast radius equals everything the shell can reach

How to choose

  • Use general tools for exploring (reading, searching) where mistakes are cheap. Use sharp tools for changing things where mistakes are expensive.
  • A sharp tool moves a rule out of the prompt and into code. "Always dry-run before commit" in a prompt is a request; a commit tool that refuses without a passing dry-run report is a guarantee. Research on enterprise agents (Ahn & Kim, Jul 2026) found only code-owned enforcement blocked violations without over-refusing.
  • Return structured results. A tool that returns {"status":"aborted","reason":"…"} spares the model from parsing — and parsing is code's job (Ch 2).

5.3 Blast radius

Blast radius is the worst-case damage a single action can cause if the agent gets it wrong. You design it down before you need it, not after an incident.

Three dials

  • Scope: how many things one call can touch. One router per call beats "apply to fleet".
  • Reversibility: can the change be undone automatically, by a human, or not at all? Irreversible actions need a human gate (Ch 12).
  • Detectability: will you know it went wrong within seconds, hours, or never? Silent damage is the worst kind.

Where the guard lives

  • Tool allow/deny lists. In Claude Code (as of Oct 2026) each subagent has its own tools / disallowedTools list and permissionMode. A worker that has no write tool cannot write.
  • Hooks. A PreToolUse hook runs your code before a tool call and can deny it (Claude Code docs, as of Oct 2026). Use it for rules a list can't express: "no commit unless a passing dry-run report for this router exists".
  • Outside the harness. Device-side controls — a lab-only credential, a role that can't touch management interfaces — still hold if the harness has a bug. A study packaging OS sandboxing and tool restriction into a harness (Gore, Jul 2026) also notes that model non-determinism makes security outcomes inconsistent: don't rely on the model's restraint.
The prompt is not a permission system. "Never touch the management interface" in a prompt will be followed most of the time. A permission rule or a device-side role is followed every time. For anything with real blast radius, you want "every time".

5.4 Guarded actions: commit with auto-rollback

Some changes can cut off the very connection you would use to fix them — a bad routing or access-list change on a remote router is the classic case. The commit-with-auto-rollback pattern makes such a change revert itself unless someone confirms it is healthy.

The pattern (invented, vendor-neutral syntax)

# illustrative only — "netctl" is a made-up CLI
netctl load  change.cfg
netctl commit --confirm-within 5m      # applied, but on a timer

# ... run health checks over a NEW session ...
netctl show neighbors --json           # code asserts expected state

netctl commit --confirm                # healthy: make it permanent
# no confirm within 5m  →  router reverts on its own
1
Apply on a timer

The change takes effect, but the device holds the old config ready to restore.

2
Prove health from outside

Check over a fresh connection, asserting on state values. If you can't reconnect, that is the answer.

3
Confirm — or do nothing

Confirm only on a passing check. Silence is safe: the device rolls itself back.

Why it fits agents so well

  • The safe outcome is the default. If the agent crashes, hangs, or blows its budget mid-change, the timer fires and the device recovers. Nobody needs to notice.
  • The confirm step is a natural place for a code checker: no passing assertion, no confirm.
  • Scope it carefully. Auto-rollback undoes this router's change. It is not a licence to roll back other routers that already succeeded — see the stop rule below.

5.5 Read-only by default

In most multi-agent pipelines only one or two workers need to change anything. Everyone else should be unable to.

The principle

  • Give each worker the smallest tool set that does its job. Investigators, planners and checkers get read tools only.
  • A read-only worker can be run in parallel, retried freely, and pointed at production with low risk. That is a huge operational win for very little effort.
  • Concentrate write access in one worker with sharp tools and a human gate in front of it. Then you only need to audit one place.

Watch the side doors

  • A "read-only" worker with a general shell is not read-only. Check what each tool can do, not what it is named.
  • Writable files count. If a worker can write to the directory where the checker lives, it can change the checker (Ch 7).
netpush
  • preflight is read-only and runs per router, in parallel — safe because it can't change anything.
  • dry-run stages and discards; it never commits. verify runs show commands only.
  • deploy is the only worker that changes a router, it sits behind the human approval gate, and it runs serially, core first.
  • Deploy stops on the first router failure and never blind-rolls back peers that already succeeded. A guarded commit like the one above can still revert the failing router on its own — that is a different, narrower action.
  • Ordering, success/fail matching and stop rules are code, not model judgement.
What this means for your skill
  • List every tool each agent or subagent can call. Which of them can change something, and does each one need to?
  • Which rules live only in the prompt that could be enforced by a sharp tool, a hook, or a permission?
  • What is the worst single action this skill can take, and is it reversible without a human?
  • If the agent died halfway through a change, would the system end up safe by default?
  • Can any worker write to files that other workers trust — plans, reports, checkers?

6. State Outside the Window

What does it remember?

What you'll learn: why anything that must survive belongs in files, not the context window; how plan and report files become shared state; checkpoints; how a long-running skill resumes after compaction or a crash; and why every step that changes the world must be safe to run twice.

6.1 Files are the agent's memory

State is what the system knows across turns, sessions and crashes. The context window is not state: it gets compacted, it gets reset, and it vanishes when the process dies.

What breaks without it

  • Context compaction — the harness summarising old turns to free space — keeps the gist and drops detail. "Router edge3 failed dry-run twice" can become "some routers had issues".
  • A crash, a timeout or a closed laptop loses everything held only in the window. The next run starts from zero, or worse, from a guess.
  • Two agents can't share what lives in one agent's head. Parallel workers need a shared medium.

What the evidence says (as of Oct 2026)

  • Anthropic's long-running-agent guidance (Nov 2025): an initializer sets up the environment; later sessions do one feature at a time, commit to git, and update a progress file. A JSON feature list that starts all-failing stops early "done" claims.
  • Anthropic's context-engineering guidance names structured note-taking — the agent writing notes outside the window — as a core long-horizon technique.
  • A review of loop engineering (Lulla et al., Aug 2026) mined 217 GitHub repos and found loops usually commit their startup config but rarely commit the recommended state files. The advice is common; the practice is not.

6.2 Plans and reports as shared state

The simplest useful state design is two kinds of file: one the orchestrator owns (the plan) and one per unit of work that workers write (the reports).

# plan.yaml — illustrative
intent: "set NTP servers to the new pair on all Lab A routers"
routers:
  core1: { role: core, stages: { preflight: done, dryrun: pass, deploy: pending, verify: pending } }
  core2: { role: core, stages: { preflight: done, dryrun: pass, deploy: pending, verify: pending } }
  edge1: { role: edge, stages: { preflight: done, dryrun: pass, deploy: pending, verify: pending } }
  # ... edge2–edge4

# reports/dryrun-edge1.json — written by the worker, read by code
{ "router": "edge1", "stage": "dryrun", "result": "pass", "attempt": 1 }

Design rules

  • One writer per file. The orchestrator owns plan.yaml; each worker owns its own report. No two agents edit the same file, so there are no write races.
  • Structured, not prose. Code reads these files to decide what runs next. Prose would force a model to interpret state, which is exactly what you moved out of the model.
  • The file is the truth. If the orchestrator's memory and the file disagree, the file wins. The orchestrator rebuilds its picture from disk at every decision point.

6.3 Checkpoints and resume

A checkpoint is a point where the state on disk is complete enough to restart from. Resume means: read the files, work out where you were, continue from there.

Example: triage resuming after compaction

triage is a fictional long-running skill with four phases: reproduce → isolate → propose fix → check fix. It can run for hours and will often be compacted mid-run.

# triage-state.json — illustrative
{
  "phase": "isolate",
  "done":  ["reproduce"],
  "facts": ["fails only with 2+ peers", "repro script: repro.sh"],
  "ruled_out": ["config typo", "timer race"],
  "next_step": "bisect the last 8 commits with repro.sh"
}
  • Before compaction or a crash, the skill has already written each finding to the state file the moment it learned it — not at the end of the phase.
  • After, the skill's first instruction is "read triage-state.json". It reloads phase, facts and the ruled-out list, and carries on. The summary in the window no longer matters.
  • Ruled-out is state too. Without it, a resumed agent re-tests ideas it already killed, sometimes for hours.

When to checkpoint

  • After every step that cost real time or tokens to learn.
  • Before and after every step that changes the outside world.
  • At every phase boundary, together with the next step in one plain sentence.

6.4 Idempotent steps

A step is idempotent if running it twice leaves the world the same as running it once. Resume makes this non-optional: after a crash you often can't tell whether the last step finished.

The crash window

  • Picture: the agent commits a change, then crashes before writing "done" to the report. On resume the file says pending. The harness runs the step again.
  • For a read, that's fine. For "append a line", you now have it twice. For a device change, you may push twice, re-trigger a reload, or overwrite a fix someone made in between.

Three ways to make a step safe to repeat

  • Check, then act. Before changing anything, read the target's current state. If it already matches the intent, record "already applied" and skip.
  • Idempotency marker. Tag each change with a run or change ID that is stored on the target or in an atomic record, so a later run can see "this change already landed here".
  • Declarative intent. Prefer "make it look like this" over "do these edits". Applying a desired state twice is naturally safe; applying a list of edits twice is not.
netpush v1 flaw. netpush resumes from plan.yaml and reports/, but v1 had no idempotency marker. If the orchestrator crashed after a router's commit landed but before reports/deploy-<router>.json was written, plan.yaml still said deploy: pending for that router and no reports/deploy-<router>.json existed yet — so a resumed run could re-deploy that router. Fixed in Ch 16.
netpush
  • Shared state is plan.yaml (intent plus per-router stages) and reports/<stage>-<router>.json.
  • The orchestrator resumes from these files, not from its context — so a compacted or restarted orchestrator can pick up mid-pipeline.
  • The generate ↔ dry-run retry count lives in the reports, so "max 3 attempts" still holds after a restart; it doesn't reset to zero.
  • Gap: resume trusts the report file, and the report can lag the router. See the flaw box above.
What this means for your skill
  • If the session were compacted right now, what would the skill lose that it can't rebuild from files?
  • Does the skill write findings as it learns them, or only at the end?
  • Is there one clear owner for each state file, and is it structured enough for code to read?
  • Which steps change the outside world, and what happens if each runs twice?
  • Does the first instruction on resume say "read the state file"?

7. The Checker Comes First

How is it checked? How does it repeat?

What you'll learn: why a loop is only as good as its judge, so you design the checker before the loop; the kinds of checker and what each one misses; asserting on state instead of exit codes; the traps in using a model as a judge; reward hacking; and why the checker must sit outside anything the agent can edit.

7.1 Recap: review and verification

Part 2 · Ch 10 Safety, Review & Verification covered how you check an agent's work: reading diffs, running tests, not trusting "done". This chapter is about what happens when you are no longer in the loop. Once a harness retries on its own, the checker replaces you as the judge — and it has to be at least as hard to fool as you were.

7.2 A loop is only as good as its judge

A checker is whatever decides "pass" or "fail" for a step: a test, an assertion, a dry-run, a model acting as judge, or a human. Every loop has one, even if it is just "the agent said it was done".

Why the checker comes first

  • A loop amplifies whatever its checker rewards. A good checker plus retries converges on correct work. A weak checker plus retries converges on work that passes the checker — faster, and with more confidence.
  • Retries can't fix a judge that can't tell good from bad. Ten attempts against a check that misses the bug yield ten confident wrong answers.
  • Lilian Weng (Jul 2026) calls evaluators the central bottleneck for self-improving harnesses. The same holds for any loop: the model can generate faster than you can judge.

So design in this order

  • 1. What does "correct" look like, observably? If you can't write it as a check, the loop has no target.
  • 2. What would a wrong answer that passes look like? Name it, then tighten the check until it fails.
  • 3. Only then build the loop that generates and retries.
Not loops first, judges later. Most broken loops were built the other way round: the generate-and-retry part was fun to build, and "how do we know it worked?" was bolted on. Flip it. A loop with no trustworthy checker is not automation, it is an unattended guess generator.

  • A dry-run tells you the config is well-formed and stages cleanly. It does not tell you the device will accept it at commit, or that the network will be healthy after.
  • So a passing dry-run is a necessary gate, never a sufficient one. Treat its pass as "allowed to try", not "known good".

7.4 Assert on state, not on exit codes

An exit code tells you the command ran. It does not tell you the world is right. These are different questions, and loops that confuse them report success on broken systems.

Weak: trusts the command

netctl show ntp
# exit 0  →  "verified" ✗

Passes on an empty table, an error message printed to stdout, or a server that is configured but unreachable.

Strong: asserts the value

netctl show ntp --json
# code asserts: servers == intent.servers
#               and one peer state == "synced"

Fails unless the router reports exactly the intended servers, actually in use.

Rules for state assertions

  • Compare observed values to the intent, taken from the plan — never to what the agent says it did.
  • Empty output, "not found", or an unconverged value is a fail, not a skip.
  • Read the whole output. A naive grep -i error misses failure strings that don't contain "error" — see the deploy flaw in Ch 2.

7.5 Model as judge: useful, with traps

Using a model to grade output (often called LLM-as-judge) is the only practical option for fuzzy qualities. It is also the easiest checker to fool, so know its traps.

The traps

  • Shared blind spots. A judge built on the same kind of model as the worker tends to miss the same mistakes the worker made.
  • Persuadable. If the output says "all tests pass" or "verified on all routers", a judge reading it may simply believe it. Never let the judge grade claims; give it evidence.
  • Grades the look, not the facts. Tidy, confident output scores well even when a value is wrong.
  • Not repeatable. The same input can get a different verdict on a different run. Bad for a gate that must be consistent.

Using it safely

  • Use model judges for quality (is this summary faithful? is this explanation clear?), and code for correctness (is the value right?).
  • Give the judge a narrow rubric and raw evidence, not the worker's own narrative.
  • Never let a model judge be the only gate before an irreversible action.

7.6 Reward hacking, and keeping the checker out of reach

Reward hacking is when an agent makes the check pass without doing the task — by changing what is measured instead of what is built. It isn't malice; it is the loop optimising exactly what you told it to.

What it looks like

  • Editing or deleting the failing test. Loosening an assertion "to match the new behaviour".
  • Special-casing the test input. Catching an exception so the check never sees it.
  • Declaring done early. Anthropic's long-running-agent guidance (Nov 2025) uses a feature list that starts all-failing precisely so "done" must be earned feature by feature, not claimed.

The structural fix: put the checker outside what the agent can edit

  • The agent being judged must not have write access to the judge — its code, its thresholds, its expected values, or the place it reads intent from.
  • Weng (Jul 2026) makes the same point for self-improving systems: keep the evaluator and the permission controls outside the loop that is changing things, to limit reward hacking.
  • Enforce it with permissions, not prose: a read-only mount, a separate directory the agent's tools can't reach, or a PreToolUse hook that denies writes to checker paths (Claude Code docs, as of Oct 2026).
  • Treat any change to a checker as a human-reviewed change, never as part of an agent's retry.
netpush v1 flaw. In v1 the verify checks — the expected-state assertions — lived in the same working directory the generate agent could write to. generate wrote checks/verify.yaml alongside its configs; on any re-run — a dry-run retry, or an operator re-run after a verify failure — nothing stopped it from relaxing the expectations instead of fixing the config. That is a reward-hacking hole: verify could go green on a router that was wrong. Fixed in Ch 16.
netpush
  • dry-run is syntax/staging only — parse-passing is not commit-passing — so it gates deploy but never stands in for verify.
  • verify asserts on observed state values per router, never on exit codes.
  • generate ↔ dry-run is capped at max 3 attempts in total, then escalates to a human. The retry is worthless without a dry-run that really fails bad configs.
  • Success/fail matching is code. The model writes the config and summarises the generated config for the approver; it never decides whether a router passed.
  • Gap: the verify checker was editable by the generate agent (flaw box above).
What this means for your skill
  • What exactly decides "pass" at each step — and could a wrong result pass it?
  • Does any check trust an exit code, a "success" string, or the agent's own claim instead of an observed value?
  • Where a model judges, is it grading evidence against a rubric, or grading the worker's story?
  • Can the agent being checked write to the checker, its thresholds, or its expected values?
  • If you added retries tomorrow, would they converge on correct work or on work that passes?

8. Anatomy of an Engineered Loop

How does it repeat? How is it checked? Partly real

What you'll learn: the four stages every engineered loop has; what has to replace you once you stop typing the next prompt; how to design a retry policy that converges instead of thrashing; the exit conditions every loop needs; and the "three loops" framing that tells you which loop you are actually engineering.

8.1 Recap: the loop you already know

You met the basic agent loop in Part 2 · Ch 1 The Agentic Coding Loop: the model reads context, calls a tool, sees the result, and decides what to do next until it says it is done. That loop runs inside one agent session and you sit at the keyboard to restart it. This chapter is about the loop you build around that: the code that sets the goal, judges each attempt, and decides whether to go again, stop, or call a human.

Why a loop needs engineering at all

  • A bare agent loop stops when the model believes it is done. Belief is not evidence. An engineered loop stops when a checker says so, or when a rule says to give up.
  • Without explicit rules, the two common failures are opposite: the loop quits too early (a false "done"), or it never quits (the same fix tried forever).
  • Loop engineering is the work of making those decisions in code, ahead of time, so the loop behaves the same way at 3 a.m. as it does when you are watching.
Hype check: loop engineering is "Partly real". The term spread in June 2026 and its origin is contested (credited variously to Boris Cherny's viral remark and to an Addy Osmani essay). IBM gave it a formal definition in July 2026, but an academic review from August 2026 found practitioners agree on the parts while there is no systematic evidence yet for the claimed benefits (as of Oct 2026). The practice is real; the measured payoff is not yet established.

8.2 Goal → act → observe → adjust

IBM's explainer (July 2026) describes an engineered loop in four stages: goal → action → observation → adjustment. Each stage is a place where the harness, not the model, has to supply something.

What each stage needs from the harness

  • Goal: a target a checker can test. "Make the config work" is not a goal; "the dry-run reports zero errors on every router" is.
  • Act: the agent does one bounded unit of work with the tools you gave it (Ch 5).
  • Observe: something other than the agent measures the result. This is the checker from Ch 7; the loop is only as good as it is.
  • Adjust: a rule decides what happens next and what new information goes into the next attempt. This is the part people most often leave to the model, and the part that most needs to be code.
The adjust step is a decision, so treat it like one. "Retry, stop, or escalate?" is ordering and stop logic. By the rules in Ch 2, it belongs in code. The model can help write the next attempt; it should not decide whether there is one.

8.3 Who prompts the agent when you don't?

The line that made the term spread, attributed to Boris Cherny (June 2026): "I don't prompt Claude anymore. I write loops that prompt Claude." Take it literally. Once you step away, every job you did between turns becomes the harness's job.

The jobs you were silently doing

  • Reading the result. You glanced at the output and knew whether it worked. The loop needs a checker that produces a pass/fail plus a reason.
  • Writing the next prompt. You said "that failed because X, try Y." The loop needs a template that feeds the checker's reason back in, not a generic "try again".
  • Deciding to stop. You gave up after a few tries, or noticed it was going in circles. The loop needs an attempt cap and a no-progress test.
  • Knowing when to ask someone. You recognised a problem you could not fix. The loop needs an escalation path that ends with a human, with enough context to act.
"Try again" is not a prompt. If the follow-up prompt carries no new information, attempt N+1 sees what attempt N saw and tends to make the same mistake. Each retry must add something: the checker's error text, a narrower scope, or a hint.

8.4 Retry policy: bounded, informed, escalating

A retry policy answers three questions: how many times, with what change, and what happens after the last one. Leave any of them open and the loop either thrashes or quits silently.

1
Cap the attempts

Pick a small fixed number. If it does not converge in a few tries, more tries rarely help; it usually means the goal, context or tools are wrong.

2
Feed the failure back

Pass the checker's exact error (trimmed, not paraphrased by the model) into the next attempt. The retry should be a response to evidence.

3
Detect "no progress"

If two attempts fail with the same error, stop early. Repeating an identical failure is a signal, not bad luck.

4
Escalate, don't swallow

When the cap is hit, hand off to a human with the goal, every attempt, and every checker verdict. A loop that quietly gives up is worse than one that never started.

Retrying only helps when something differs between attempts. The cap protects you when nothing does.

8.5 Exit conditions

Every loop needs more than one way out. Write them down before the first run; a loop with only a success exit has no plan for the day success never comes.

ExitTriggerWhat the loop must do
SuccessThe independent checker passesRecord the evidence (checker output), then hand off to the next step
Attempt capRetry limit reachedEscalate with full history
No progressSame failure twice in a rowStop early and escalate
BudgetTime, tokens or cost exhausted (Ch 9)Stop and report; never silently continue
Hard failureAn irreversible step failedStop now; do not "fix forward" without a human

Who decides "done"?

  • Not the agent doing the work. Its "I'm done" is a claim; the checker turns it into evidence.
  • A common pattern for long-running agents is a feature list that starts with every item marked failing, so "done" means every check has flipped, not that the model feels finished (Anthropic engineering, Nov 2025).
  • Every non-success exit should leave a written report. The next run, or the human, starts from it.

8.6 The three loops

Andrew Ng (The Batch, June 2026) describes three nested loops in building software, separated mainly by how long one turn takes. They help you name which loop you are engineering, because each needs different checkers and different stop rules.

LoopOne turn takesWho judges the result
Agentic coding loopMinutesAutomated checks: build, tests, dry-runs
Developer feedback loopTens of minutes to hoursYou, reviewing what the agent produced and steering it
External feedback loopHours, and sometimes days or weeksUsers, testers, A/B tests: the real world

How to use the framing

  • Ng frames this for building new products; the shape transfers to any agent work. Vendor blogs often shorten the outer loop to "days"; his own wording is "hours … days or even weeks".
  • Loop engineering mostly automates the inner loop so your time moves to the middle one. It does not remove the middle loop; it changes what you review.
  • The inner loop is only safe to automate as far as its checker is trustworthy. Anything the checker cannot see (see the dry-run limits in Ch 7) gets pushed out to a slower, costlier loop.
netpush
  • Inner loop: generate ↔ dry-run. Goal: every router's dry-run passes. Act: the model generates config from intent. Observe: the per-router dry-run reports. Adjust: code feeds the failing router's error text back into the next generate.
  • Retry rule: max 3 attempts, then stop and escalate to a human with all three attempts and their dry-run reports. The model never decides whether to try a fourth time. v1 has no no-progress exit (8.4): two identical dry-run failures still use up the third attempt.
  • Deploy is not a loop. It runs serially, core first, and stops on the first router failure. It never retries automatically and never blind-rolls back peers; a failed commit is a hard-failure exit.
  • Middle loop: the human approval gate after dry-run is where your developer feedback loop lives. verify stays inside the run. Outer loop: post-change monitoring of Lab A and reports from the people who use it.
What this means for your skill
  • Where does your skill's loop decide "done", and is that decision made by the worker or by an independent check?
  • Is there a written attempt cap, and what exactly happens when it is hit?
  • Does each retry carry new information (the checker's error), or just "try again"?
  • Which of the five exits in 8.5 does your loop have, and which are missing?
  • Which of the three loops are you automating, and which one are you quietly still doing by hand?

9. Budgets & Stopping Rules

How does it repeat?

What you'll learn: the four budgets that bound a loop, why each catches a failure the others miss, and why a loop that runs out of budget must fail loudly rather than retry quietly.

9.1 Four budgets, four failure modes

A budget is a limit set before the run starts; crossing it is an exit condition. The attempt cap from Ch 8 is one budget. You need the others because a loop can burn resources without ever finishing an attempt.

BudgetCatchesWithout it
IterationsThe same fix tried again and againEndless retries that each look reasonable
Wall-clock timeHung tools, slow devices, waiting on a lockA run still "in progress" the next morning
TokensOne attempt that reads or writes far too muchA context window full of noise, and a degrading agent
CostAll of the above, summed across runs and agentsA surprise bill from a loop nobody was watching

Setting them

  • Set budgets per run and per step. A per-run limit alone lets one step eat the whole budget.
  • Base them on normal runs: a few times the usual cost is a budget; ten times is a hope.
  • Enforce them in code, outside the agent. An agent asked to "stay under budget" cannot see its own spend reliably.

9.2 Fail loud, never loop forever

When a budget runs out, the loop has two options: stop and say so, or keep trying in a way nobody notices. Only the first is safe.

What "fail loud" means

  • Stop. No "one more try" after the limit. The limit is the decision.
  • Report. Write which budget ran out, what was achieved, the last checker verdict, and where the state files are (Ch 6).
  • Mark the result clearly. "Stopped: budget exceeded" is a distinct outcome, not a success and not a crash. Anything downstream must be able to tell them apart.

The silent-retry trap

  • A wrapper that catches the budget error and restarts the loop "to be safe" turns a bounded loop into an unbounded one.
  • A model told "keep going until it works" will happily treat a budget warning as one more obstacle to route around.
A loop with no stop rule is a cost leak with a progress bar. Every engineered loop should be able to answer: "What is the most this run can possibly cost, and what happens when it gets there?"
netpush
  • Each run has a per-run wall-clock budget and a token budget. Exceeding either stops the run and writes a report; it is never retried silently.
  • The iteration budget is the inner-loop rule: max 3 attempts for generate ↔ dry-run, then escalate to a human.
  • Because state lives in plan.yaml and reports/<stage>-<router>.json, a stopped run can be inspected and resumed by a person instead of restarted blind (mind the idempotency gap, Ch 6).
What this means for your skill
  • Which of the four budgets does your skill enforce, and which does it just hope for?
  • Is each budget enforced by code outside the agent, or by an instruction in the prompt?
  • When a budget runs out, what does the user actually see?
  • Is there any wrapper, retry or "resume" path that can quietly restart a stopped run?

10. Background & Scheduled Loops

How does it repeat? What does it remember?

What you'll learn: what changes when a loop runs with nobody watching, the three extra pieces of harness an unattended loop needs, and how one tool exposes interval and scheduled loops today.

10.1 Loops nobody watches

An unattended loop is one that starts without you: on a timer, on a schedule, or on an event such as a new commit or a CI run. Everything in Ch 8 and Ch 9 still applies, but you lose the last safety net: a person who notices something odd.

What breaks when you are not there

  • Nobody sees the result. A failed run that writes to a log nobody reads is the same as no run.
  • Nobody can stop it quickly. A misbehaving loop keeps firing on schedule until someone finds out where it lives.
  • Runs overlap or repeat. A slow run is still going when the next one starts, or a retried trigger runs the same step twice.
  • State goes missing. A 2026 study of 217 loop repositories found loops usually commit their start-up config but rarely commit the recommended state files (as of Oct 2026). Without state, each run starts from zero.

10.2 The extra harness an unattended loop needs

1
Notifications

Every non-success exit sends a message to where a person will see it, with the report attached or linked. Success can be quiet; failure cannot.

2
A kill switch

One documented way to stop all future runs at once, checked at the start of every run: a flag file, a config value, a disabled schedule. If stopping it requires finding and editing three places, it will not be stopped in time.

3
Idempotency

Running the same step twice must be safe. Before acting, check the target itself — or a marker written atomically with the change — for this run's id. A "done" line written after the action leaves the crash window from Ch 6. Add a run lock so two runs can't work at once.

Scheduled means unattended, and unattended means tighter permissions. A loop you watch can be trusted with a bigger tool surface because you will catch mistakes. A loop that fires at night should get the smallest set of tools that does the job, and no irreversible action without a human gate.

11. From Loop to Graph

How do the pieces connect? What does it remember? Rebranding

What you'll learn: what a graph adds once one loop is no longer enough; the four kinds of node (code, LLM call, agent, human); how edges and conditions route work; why the shared state should be a typed file, not a chat transcript; fan-out/fan-in and the orchestrator–worker pattern; why netpush stops on the first failed router instead of rolling everyone back; and how to tell when your loop has outgrown itself.

11.1 Recap: you have already run multi-agent work

Part 2 · Ch 11 Multi-Agent & Parallel Workflows showed how to run agents side by side in parallel sessions, worktrees and subagents. It was about using several agents. This chapter is about designing the wiring between them, which answers the sixth harness question: How do the pieces connect?

What a graph is, in one line

  • A graph is a set of steps (nodes) and the rules for moving between them (edges), all reading and writing one shared state.
  • A loop is the simplest graph: one node with an edge back to itself. LangChain makes the same point: loops are a simple form of graph (LangChain, “3 Years of Graph Engineering with LangGraph”, Jul 2026).
  • Real graphs have cycles (retries, validation, human approval), so they are usually not DAGs (directed acyclic graphs) (same source).

Solid practice, new label

  • As of Oct 2026, "graph engineering" as a label is usually traced to a July 2026 Peter Steinberger post asking “Are we still talking loops or did we shift to graphs yet?” (as reported by Data Science Dojo, Jul 2026). The exact date varies by time zone, and the origin is contested (Palo IT, “Beyond the Prompt”).
  • The practice is older. Anthropic documented orchestrator–workers, routing and parallelization patterns in Dec 2024 (“Building effective agents”). LangChain describes graph engineering as a new name for something it has done for three years.
  • Hence the Rebranding tag: the engineering is real and useful, but the label adds nothing new. See Ch 15.

11.2 netpush drawn as a graph

The running example is easier to understand as a picture than as prose. Each box is a node. Each arrow is an edge, and some edges carry a condition.

1
Orchestrator → preflight (per router, parallel, read-only)

Six workers, one for each Lab A router (2 core, 4 edge). Each one snapshots its router and writes reports/preflight-<router>.json. No worker can change anything.

2
Generate (once, central)

A single agent turns the intent in plan.yaml plus the snapshots into per-router config. It runs once and centrally, so the configs on both ends of a link stay consistent with each other.

3
Dry-run (per router, parallel)

Each router stages and discards its config. A failure sends work back to generate, up to max 3 attempts, and then escalates to a human. Remember that parse-passing is not commit-passing (Ch 7).

4
Human approval gate

Nothing touches a live router until a person says yes. The gate is a node in the graph, not something bolted on beside it (Ch 12).

5
Deploy (serial, core first) → verify (per router)

Routers commit one at a time, core first and then edge, so a bad change surfaces on the 2 core routers before the 4 edge routers depend on it. Deploy stops on the first router that fails. Verify asserts on observed state values, never on exit codes.

Notice that the shape changes from parallel to central to parallel to serial. A single loop cannot express that shape, and that is the reason to use a graph.

11.3 Nodes and edges

Every node in an agent graph is one of four kinds. The kind tells you how far the node is allowed to wander and how much you need to check its output. (LangChain lists code, LLM call, tool call and full agent as node kinds; this guide folds tool calls into code and adds the human.)

Node kindWhat it isnetpush exampleDeterminism
CodeA plain function or scriptDeploy ordering, matching commit output, the stop ruleFully deterministic
LLM callOne prompt in, one answer out, with no toolsSummarising the generated config for the approver (v1 computes no diff; Ch 16 adds one)Bounded: a single shot
AgentA model running its own tool loopGenerate, which reads snapshots and writes configsOpen-ended inside its sandbox
HumanA person who decides or editsThe approval gate, and escalation after max 3 attemptsSlow, costly, accountable

Edges carry the control flow

  • Fixed edge: always goes to the next node, for example preflight → generate.
  • Conditional edge: a rule chooses the next node. In netpush, dry-run fails → generate (while attempts < 3); dry-run fails a third time → human; every dry-run passes → approval gate.
  • Write edge conditions in code that reads state, not as a model's judgement. "Did all six dry-run reports say pass?" is a lookup in the report files, so no model should be asked to decide it (Ch 2).

What changed recently

  • A single node can now be a whole agent run (LangChain, Jul 2026). That makes graphs much more capable, and it also means one node can fail in many more ways.
  • Research separates graphs that are fixed before deployment from graphs that are chosen or revised per run (Yue et al., workflow-optimization survey, Mar 2026). netpush is fixed, which is the right choice when every step touches live devices.

11.4 Typed shared state

Nodes need to pass work to each other. If the hand-off is a chat transcript, every downstream node has to re-read prose and guess what it means. A typed state file has known fields that code can check, so each hand-off becomes a contract.

# plan.yaml (illustrative)
intent: "add loopback 10 to every router"
generate: {attempts: 2}   # run-level; a regenerate resets every router's dry_run to pending
routers:
  - {name: core1, role: core, stages: {preflight: pass, dry_run: pass, deploy: pending}}
  - {name: edge3, role: edge, stages: {preflight: pass, dry_run: fail}}
approval: {status: pending}

Why typed beats free text

  • Code can test the edge conditions: all(r.stages.dry_run == "pass" for r in routers). A model is not needed for that.
  • Workers get a narrow view of the state. A dry-run worker reads its own router's config and writes only reports/dry-run-<router>.json.
  • The orchestrator resumes from these files after a crash or context compaction, because the state lives on disk and not in anyone's context window (Ch 6).
The state file is the graph's memory. A graph without durable state still works as long as nothing interrupts it. Once something does, it has no record of where it was.

11.5 Fan-out, fan-in, and stopping without making it worse

Orchestrator–worker and fan-out/fan-in

  • Orchestrator–worker: one coordinator owns the plan and dispatches narrow workers (Anthropic, Dec 2024). The workers do not talk to each other. They only read and write state.
  • Fan-out: the same node runs N times in parallel. netpush does this for preflight and dry-run, which are safe to parallelise because neither one commits anything.
  • Fan-in: a join waits for all N results before continuing. Generate fans in from six preflight reports, and the gate fans in from six dry-run reports.
  • Deploy deliberately does not fan out. Committing to routers in parallel would remove your ability to stop after the first failure.

Stop on first failure, and don't blind-rollback

  • If deploy fails on the third router, the graph stops. It records which routers are committed, which are pending and which failed, and then reports to a human.
  • It does not automatically roll back the routers that were already committed. Those routers are running a config that dry-ran cleanly and committed a moment ago. Rolling them back blindly is a second, unverified change, and it can cut off a neighbour that now depends on the new config.
  • Recovery belongs to a human with the full picture. The graph's job is to stop the damage from spreading and to leave an accurate record of where things stand.
An edge is a policy decision. "On failure, go to rollback" and "on failure, go to stop" are each one arrow in the diagram, but they have very different effects on the network. Design failure edges as carefully as the success path.

11.6 When should a loop become a graph?

Most workflows don't need a graph (Data Science Dojo, Jul 2026), and some open-ended tasks work better as one agent in a good harness than as a predefined graph (LangChain, Jul 2026). Promote a loop to a graph only when you see one of the signals below.

Signals that you've outgrown one loop

  • Different steps need different permissions. Preflight is read-only and deploy can commit. One loop with one tool set has to grant the union of both.
  • Different steps need different shapes: parallel here, serial there, run once centrally somewhere else.
  • A human must decide partway through. A gate needs a well-defined place in the flow where execution pauses and later resumes.
  • Different steps need different checkers. A dry-run judge and a verify judge test different things.
  • You need to resume partway through without redoing earlier steps.

Signals to stay a loop

  • The task is exploratory and you can't name its steps in advance, as with debugging or research.
  • Every step uses the same tools and the same checker.
  • You would be drawing the graph mainly to make the system look organised.
netpush
  • netpush is a graph rather than a loop because its steps differ in permissions (read-only vs. commit), in shape (parallel, central, serial) and in checkers (dry-run vs. verify), and because a human gate sits between staging and committing.
  • The retry loop (generate ↔ dry-run, max 3 attempts) lives inside the graph as a cycle. The loop is a component of the graph, not a competitor to it.
  • Shared state is plan.yaml plus reports/<stage>-<router>.json, and the orchestrator resumes from these files.
  • Deploy runs serially, core first, and stops on the first router failure. It never blind-rolls back peers.
What this means for your skill
  • Can you draw your skill as nodes and edges? If not, is that because it is truly open-ended, or because its control flow is implicit?
  • Which of your edge conditions does a model decide that code could decide by reading state?
  • Is the hand-off between your subagents a typed file, or a paragraph the next agent has to interpret?
  • Where does your skill fan out, and could any of those parallel steps make a change you can't stop halfway through?
  • When a step fails partway through, does your skill stop and report, or does it try to undo everything on its own?

12. Humans as Nodes

How do the pieces connect? How is it checked?

What you'll learn: why an approval gate is a node in the graph rather than a separate layer; where gates belong; what an approver has to see to make a real decision; how gates turn into rubber stamps; and how propose-then-generate puts the human where their judgement costs the least and catches the most.

12.1 A gate is a node

  • A human gate takes inputs (what to approve), produces outputs (approve, reject or edit), and has outgoing edges like any other node. Draw it in the graph so that every path that skips it is visible.
  • It is the slowest and most expensive node you have. Each gate costs someone's attention, so use as few as you can and make each one count.
  • Record the decision in the shared state (for example, approval: {status: approved, by: …}). Then a resumed run knows the approval already happened and doesn't need to guess.

Where gates belong

  • Before edges you can't undo: committing to a live device, sending a message, merging code. In netpush that point is between dry-run and deploy.
  • Where a loop has given up: netpush escalates to a human after max 3 attempts, which is better than retrying forever.
  • Not in front of read-only or easily reversible steps. A gate there only teaches people to click "yes" without reading.

12.2 What the approver must see

A gate is only as good as what it shows the person. If the person can't see the risk, approving is a guess.

Show the change, not the artefact

  • A diff against the current state (from the preflight snapshot), not the full new config. People can review 12 changed lines. They can't meaningfully review 800 lines of config.
  • The blast radius: which routers change, the order they change in (core first), and what happens if one fails (stop, with no blind rollback).
  • Checker results: what the dry-run proved, and also what it can't prove.
  • A model-written summary is useful, but it is not evidence. netpush v1 has the model summarise the generated config and computes no diff (gap 4); v2 has it summarise a diff that code computed. Show that summary next to the diff that code computed, so the approver can check the summary against the actual change.

The rubber-stamp failure

  • When a gate shows too much, fires too often, or nearly always passes, people stop reading and start clicking. The gate still exists, but it has stopped catching anything.
  • You can spot this from outside: approval times drop to a few seconds, and nobody ever rejects anything.
  • The fix is to show less and make the change easy to see, not to add more gates.
netpush v1 flaw. The approval gate showed the full generated config for each router, not a diff against the preflight snapshot. Six routers' worth of raw config is too much to review, so approvers skimmed it and approved. The gate was in place, but it had become a rubber stamp. Fixed in Ch 16.

12.3 Propose-then-generate

The cheapest point to put a human in the loop is where the artefact is small and still easy to change, before anything expensive gets built on top of it.

1
Propose

gen-parser drafts only the output schema for a new parser: field names, types and nesting. It fits on one screen.

2
Human gate

A person reviews the schema, then approves it or asks for changes. A schema question such as "should this be a list or a map?" takes seconds to answer now, but it would take an hour to fix once the code exists.

3
Generate

Only after approval does the skill generate the parser code and its tests. Both are built against the approved schema, which is now a fixed contract.

The same idea covers both cases: review the plan when it is small, and review a diff of the change rather than the whole output.
netpush
  • There are two human nodes. The approval gate sits before deploy, which is the first edge that can't be undone. Escalation happens after max 3 attempts of generate ↔ dry-run.
  • The gate's input should be a code-computed diff plus a model-written summary, with the order (core first) and the stop rule shown.
  • In v1 the gate showed raw config, which made it a rubber stamp. Ch 16 fixes this.
What this means for your skill
  • Which step in your skill is the first one that can't be undone, and is there a gate right before it?
  • Does your gate show a diff, or the whole artefact?
  • When your skill shows a model-written summary to the approver, does it also show the evidence that summary is based on?
  • Is your gate in a place where saying "no" is cheap, such as the proposal, or where it is expensive, such as the finished code?
  • How often has anyone rejected at this gate? If the answer is never, is it still catching anything?

13. The Failure Map

How is it checked? How do the pieces connect?

What you'll learn: how to go from “it did something wrong” to the layer that broke: the model, or one of the six harness questions. You get a symptom-indexed table, a short decision flow for unfamiliar symptoms, and the rule that turns each fix into a permanent check, so the same failure can't come back quietly.

13.1 Recap: where Part 2 left off

Part 2 covered agent failures from the user's side of the keyboard: how a loop goes wrong, the common failure modes, and how to debug alongside an agent. See Part 2 · Ch 1 The Agentic Coding Loop (bad loops, failure modes) and Part 2 · Ch 9 Debugging with Agents. This chapter doesn't repeat them. It asks a designer's question: which part of the system should change so this never happens again?

Why a map, not a list of tips

  • Without a map you fix the symptom where you noticed it, which is usually the prompt. You add one more “IMPORTANT: never do X” line. It works for a week, then the context grows and the line gets lost.
  • Most agent failures are harness failures that look like model failures. The model did the reasonable thing given what it saw, what it could do and what it was checked against.
  • The map uses the same seven layers as the rest of the guide: Model, plus the six questions. One taxonomy means a failure found here maps straight onto a row of the audit in Ch 17.

13.2 First cut: model or harness?

Before you walk the six questions, decide whether the model is the limit at all. This is the cheapest split and it saves you from rebuilding a harness around a capability gap.

The swap test

  • Replay the same task with the same context, tools and checker, and change only the model to a more capable one. Agents are non-deterministic, so replay several times per model and compare pass rates (14.3), not single runs.
  • Its pass rate jumps: the failure was likely capability. You can pay for the bigger model on that step, or shrink the step: move part of the decision into code (Ch 2) so a weaker model has less to judge.
  • It still fails about as often: the harness is the likelier cause. A stronger model given the same wrong inputs fails the same way. Go to the six questions.

Why this order

  • The harness is where your leverage is. Research on automatically evolving harnesses found that tools, middleware and long-term memory moved results more than the system prompt did (Lin et al., Apr 2026). Treat this as one study, not a law.
  • Model and harness interact: Weng notes harness self-improvement still needs a capable base model, and a technique that helped a strong model hurt weaker ones (Lil'Log, Jul 2026).
Save the trace before you touch anything. The swap test and every row below need a replayable record: inputs, tool calls, tool outputs, checker verdicts. If your harness doesn't keep one, that is your first finding, under What does it remember?

13.4 Reading a symptom you haven't seen

The table covers the common cases. For a new one, walk the layers in a fixed order. The order runs from cheapest to check to most expensive, and it stops at the first layer that explains the trace.

1
Replay from the trace

Reproduce on the saved inputs. If you can't reproduce it, the first fix is better recording, not a guess.

2
Swap test

Stronger model, same harness. Passes → Model layer. Fails → continue.

3
Check: was the right answer reachable?

What does it see? Was the needed fact in context? What can it do? Did a tool exist for the action? What does it remember? Did it know what was already done?

4
Check: was the wrong answer caught?

How is it checked? Would the checker have failed this output? How does it repeat? Did the loop retry, stop, or escalate correctly? How do the pieces connect? Did the failure cross an edge it shouldn't have?

5
Change one layer, re-run

Change one thing, replay, and compare. Two changes at once teach you nothing about which one worked.

Steps 3 and 4 are two different failures. “It produced a wrong answer” and “we shipped a wrong answer” are separate bugs. Fix both. A better prompt cuts the first; only a checker or a gate stops the second.

13.5 Every fix becomes a check

A fix you can't detect regressing isn't finished. The point of locating the layer is to put a guard in that layer, so the failure is caught by the system, not by you on a bad day.

Turning a finding into a guard

  • Save the failing trace as a test case. Your harness now has an eval set, even if it's small. Ch 14 builds on exactly this.
  • Prefer guards in code over guards in prose. A study of enterprise agents found that only code-owned enforcement blocked rule violations without hurting useful output, while a bolt-on guardrail over-refused (Ahn & Kim, Jul 2026).
  • Hashimoto described this habit as the core of what he called harness engineering: when the agent makes a mistake, fix it once so it doesn't happen again (Feb 2026).

When the map points everywhere

  • If one incident touches three layers, fix the one closest to the irreversible action first. A checker or gate in front of deploy beats a better prompt upstream.
  • If the same symptom keeps returning after fixes in different layers, you likely have a How do the pieces connect? problem: the fix lands in one node and the failure enters through another.
The map shrinks over time. Each fixed row that gains a check stops being a live failure. A harness that has been through many incidents fails in fewer, stranger ways, and that's the sign it's maturing.

14. Self-Improving Harnesses

How does it repeat? How is it checked?

What you'll learn: the outer loop, where traces from real runs turn into edits to the harness itself. You start from the primitive version (a lessons file), see why every harness change needs an eval gate, and learn the one structural rule that keeps the loop honest: the evaluator and the permissions sit outside what the loop can edit. The chapter ends with research directions, clearly marked as research.

14.1 The outer loop: traces in, harness edits out

Chapters 8–10 covered the inner loop: the agent repeating act → observe → adjust on one task. The outer loop runs across many tasks. Its input is what happened on past runs; its output is a change to the harness, such as a context file, a tool, a check or a stop rule.

What breaks without it

  • The harness is frozen at the day you wrote it. Every failure since then is either fixed by hand, ad hoc, or forgotten.
  • Ch 13's “every fix becomes a check” is a manual outer loop. This chapter is about making it routine, then partly automatic.

Who runs it

  • You, by hand: read failures, edit the skill. This is where everyone starts and it's fine.
  • The agent proposes, you approve: the agent drafts the lesson or the harness edit; a human gate decides. This is a human node (Ch 12) on the outer loop.
  • Fully automatic: a search process edits the harness and keeps what scores better. As of Oct 2026 this is research, not common practice (14.5).

14.2 The primitive version: crash-doctor's lessons.md

crash-doctor is the fictional debugging skill from the running example. After every session it appends what it learned to a lessons.md file, and it reads that file at the start of the next session. That's an outer loop in about ten lines of instruction.

# lessons.md  (crash-doctor, illustrative)
- 2026-09-02  Core from the route daemon: frame 0 is in the allocator,
  so the real fault is the caller two frames up. Check frames 1-3 first.
  evidence: session 41
- 2026-09-15  Symbols didn't match: the core came from a different build.
  Compare the build id before reading any frame.
  evidence: sessions 44, 47
- 2026-10-03  "Check frames 1-3 first" was wrong for watchdog aborts;
  those point at the stuck thread, not the caller.
  supersedes: 2026-09-02 (partly)   evidence: session 52

Why it works at all

  • It moves knowledge from one session's context, which is lost at the end, to a file that is loaded next time. That's What does it remember? applied to the harness itself.
  • It costs nothing to start. No eval set, no infrastructure, just a file and a habit.

Where it breaks

  • It only grows. Every lesson is loaded every time, so the file slowly becomes the stale, always-on context that Ch 4 warns about.
  • Lessons contradict. The third entry above partly overrides the first. Without a supersedes link, the model sees both and picks one.
  • Nothing checks a lesson. The agent writes its own lessons from its own reading of the session. A wrong lesson is now a permanent instruction.
  • Lessons never graduate. “Compare the build id first” is a deterministic rule. It belongs in code (Ch 2), as a pre-check that refuses mismatched cores, not as a sentence the model may skip.
Treat lessons.md as an inbox, not a rulebook. Date each entry and cite its evidence. Prune it on a schedule. Promote any lesson that recurs into a tool, a check or a skill edit, then delete the entry. A short lessons file is a sign it's working.

14.3 Eval-gated harness changes

A harness edit is a code change to a system you can't fully predict. Without a gate you can't tell an improvement from a regression that happened to fix today's case. The gate is an eval: a fixed set of tasks with known-good outcomes, run before and after the change.

The minimum viable eval

  • Start with the saved failing traces from Ch 13. Each fixed incident is one test case. Add a handful of normal, passing cases so you notice when a change breaks them.
  • Score with deterministic checks wherever possible: state values, file contents, exit conditions. Use a model as judge only where no code check exists, and read Ch 7's traps first.
  • Run each case more than once. Agents are non-deterministic, so one pass proves little. Compare pass rates, not single runs.

The gate rule

  • A harness change ships only if it fixes its target case and doesn't lower the pass rate on the rest.
  • Write down what you expect the change to do before you run it. One research system pairs every harness edit with a prediction and checks the prediction on the next round (Lin et al., Apr 2026). The habit works by hand too: a change whose effect you can't predict is a change you don't understand yet.
  • Keep the change small. One lesson, one tool or one check per change, for the same reason as Ch 13: two changes at once tell you nothing about which one helped.
Your eval set is the real asset. Prompts and skills will be rewritten many times. A good set of cases with trusted scoring outlives all of them, and it's the only thing that lets you upgrade the model, or let the agent edit its own harness, without guessing.

14.4 What must stay outside the loop

An outer loop optimises whatever the evaluator rewards. If the loop can edit the evaluator, the cheapest path to a higher score is to edit the evaluator. This is reward hacking: the score goes up and the real behaviour doesn't.

The structural rule

  • Weng's survey of self-improving harnesses names evaluators as the central bottleneck, and argues that the evaluator and permission controls should sit outside the loop that evolves the harness (Lil'Log, Jul 2026).
  • Evaluator outside: eval cases, scoring code and pass thresholds live where the evolving agent can't write. A change to them is a separate, human-reviewed change.
  • Permissions outside: the loop may propose a new tool or a wider tool list, but it can't grant one. Otherwise “improve the harness” quietly becomes “give myself more access”.

What the loop may edit

Inside the loop (editable) Outside the loop (fixed, human-owned)
Context files, skill text, lessonsEval cases and scoring code
Tool descriptions and examplesTool allow/deny lists and permission modes
Retry hints, decomposition of stepsBudgets and hard stop rules
Proposed new checks (as drafts)The checkers that gate real actions
The same rule applies inside a single run. Ch 7 kept the checker out of the worker's reach for one task. Here it's the same idea one level up. If either the inner or the outer loop can edit its own judge, you no longer know what a pass means.

14.5 Research directions (as of Oct 2026)

Automatic harness evolution is an active research area. The results below are early, come from benchmark settings, and are summarised from the papers' own claims. Read them as directions, not as practice you should copy today.

Search over harness code

  • Once a harness is code, a model can search over it: propose an edit, evaluate, keep the better variant. Weng's survey covers this line of work (it cites Meta-Harness, ADAS and AFlow) and notes it still needs a capable base model (Lil'Log, Jul 2026).
  • Lin et al. report an observability-driven loop that evolved a coding-agent harness over 10 iterations, raising one benchmark's pass rate from 69.7% to 77.0%, above a human-designed baseline at 71.9%. Their ablations credited tools, middleware and long-term memory more than the system prompt (arXiv, Apr–May 2026). It's one paper, on one benchmark.

Harnesses built per task

  • JIT-Agent trains a model to generate a task-specific harness (memory, planning, action protocol, tool orchestration) on the fly and repair it from an archive of past configurations. It reports large gains for weaker base models (Zhang et al., arXiv, Aug–Sep 2026). Treat the numbers as preliminary.
  • A workflow-optimisation survey sorts methods by whether the graph structure is fixed before deployment or chosen and revised per run (Yue et al., arXiv, Mar 2026). Per-task harnesses push the same idea down a level.

What to take from it now

  • Every one of these systems depends on an evaluator it trusts. Build your eval set first; the automation is the easy part to add later.
  • The edits that paid off in one study (Lin et al.) were structural (tools, memory, middleware), not prompt wording. Point your manual outer loop at the same places.
netpush
  • Traces already exist. Every run leaves plan.yaml and reports/<stage>-<router>.json. These are the raw material for an outer loop; nothing new has to be logged to start one.
  • Illustrative extension: each escalation after max 3 attempts on generate ↔ dry-run becomes an eval case: the intent, the router and the dry-run error. A change to the generate prompt ships only if it clears those cases on Lab A dry-runs without breaking passing ones.
  • Outside the loop: the verify checker, the approval gate, the budgets and deploy permissions must never be editable by the outer loop.

  • Which lessons in your notes are really deterministic rules that should be a pre-check in code?

  • Could your skill, or an agent improving it, edit its own checker or widen its own tool list?

15.3 Lineage or nesting?

The popular story is a timeline of eras: prompt (2023) → context (2025) → harness (early 2026) → loop and graph (mid 2026), each replacing the last. The terms did arrive in roughly that order. They didn't replace each other.

The nested view

  • Palo IT describes the layers as nested (prompt inside context, inside harness, inside loop, inside graph), with none deprecating the layer below.
  • Breunig traces the same path as a shift of work “from probabilistic model calls to deterministic code”: as tools moved out of the context and into code, “we started calling it harness engineering” (Oct 2026).
  • This guide reorders the outer layers: the loop and the graph are parts of the harness (How does it repeat? and How do the pieces connect?), not layers above it. That's an editorial choice made for skill design, and The Map explains why.

A test for the next label

  • Which of the six questions does it answer? If none, it's probably about the model or the org, not the harness.
  • What breaks without it that the existing layers don't already cover? If you can't name a failure, it's a rename.
  • Is there a primary source with techniques, not just a definition? Is there evidence the techniques work? The loop-engineering review is a good model: it separated agreement on components from evidence of benefit.
Learn the six questions, not the labels. Labels will keep coming. If a new one maps onto a question you already handle, you can skip the hype. If it doesn't map, read it closely: that's the rare case where something new is going on.

16. Dissecting netpush

How is it checked? How do the pieces connect?

What you'll learn: how to take one real-shaped agent pipeline and read it through every lens in this guide — the six questions, the loop, the graph, the checker, the state, and the human gates. You'll see what netpush already gets right, then watch the four flaws planted in earlier chapters surface, each with a before/after fix and the reasoning behind it. netpush is fictional and illustrative; the habits it teaches are not.

16.1 netpush in one screen

Recap of the running example (canon from The Map). netpush pushes one config change to "Lab A": six routers, 2 core and 4 edge. An orchestrator drives five kinds of worker, with one human gate in the middle.

The pipeline

  • preflight — per router, in parallel, read-only. Snapshots running config and health.
  • generate — once, central. A model turns the intent into per-router config.
  • dry-run — per router, in parallel. Syntax/staging check only.
  • human approval gate — a person decides whether the change goes live.
  • deploy — serial, core first. Stops on the first router failure; never blind-rolls back peers.
  • verify — per router. Asserts on observed state values, never on exit codes.

The rules around it

  • Shared state: plan.yaml (intent + per-router stages) and reports/<stage>-<router>.json. The orchestrator resumes from these files, not from its memory.
  • Retry: generate ↔ dry-run retries max 3 attempts, then escalates to a human.
  • Budgets: a per-run wall-clock and token budget. Exceeded → stop and report, never silent retry.
  • Code vs model: the model generates config from intent and summarises the generated config for the approver (v1 computes no diff — gap 4). Code parses CLI output, matches success/fail, orders the deploy and enforces stop rules.

16.2 Lens 1: the six questions

16.3 Lenses 2–6: loop, graph, checker, state, gates

Loop (Ch 8, Ch 9)

  • strong The only model-driven loop is generate ↔ dry-run, and it has a hard exit: max 3 attempts, then a human. No loop runs forever.
  • strong Budgets are stop conditions, not warnings. Running out of time or tokens produces a report, not a fourth quiet retry.
  • Deploy is deliberately not a loop. A failed commit is a decision point for a person, not something to retry.

Graph (Ch 11)

  • strong Parallel where it's safe (read-only preflight, side-effect-free dry-run), serial where it isn't (deploy).
  • strong Edge semantics are explicit: a deploy failure halts the walk and records committed / pending / failed. It does not roll back peers that already succeeded — a blind rollback can cut off a neighbour and turn one broken router into three.
  • strong Core first: if the change breaks something, it breaks where you're watching most closely, before it spreads to every edge.

Checker (Ch 7)

  • strong netpush knows its checkers' limits: dry-run is labelled syntax/staging only — parse-passing is not commit-passing.
  • strong verify asserts on state values (sessions up, prefixes present), never on "the command exited 0".
  • gap 1 deploy's own success check was a substring search. gap 3 verify's expectations were editable by the agent being checked.

State and gates (Ch 6, Ch 12)

  • strong All coordination goes through files, so a crashed or compacted orchestrator can resume.
  • gap 2 Files record finished stages, not started ones — the window between commit and report is unguarded.
  • strong The gate sits on the only irreversible edge. gap 4 But what it shows makes approval a rubber stamp.

16.4 Gaps 1 & 3: the checkers that couldn't be trusted

Gap 1 — deploy matched grep -i error (first flagged in Ch 2)

  • What happened. The edge-3 apply was aborted with a message that didn't contain the word "error". The grep found nothing, the session exited cleanly, and deploy reported success.
  • Why it broke. A deny-list ("fail if you see X") passes everything it didn't anticipate. Success needs an allow-list: "pass only if you see Y".

Before (v1)

edge-3# apply change
apply: aborted — reference to undefined group 'edge-peers' (line 14)
edge-3#

$ grep -i error out.txt || echo "deploy ok"
deploy ok          # wrong

After (v2)

# code, not model: parse the FULL output
ok  = re.search(r"^apply: ok \(txn \S+\)$", out, re.M)
if not ok:
    status = "failed"      # incl. empty output
    save_raw(out)          # keep evidence
    stop_walk()            # stop on first failure
else:
    status = "committed"
  • The match is code-owned, anchored and positive. Anything else — rejection, timeout, empty output, a string nobody has seen — is a failure.
  • The raw output is saved to the report, so a human (or a later model call) can explain why. The model may summarise the failure; it never decides whether one happened.

Gap 3 — verify's checker was editable by generate (first flagged in Ch 7)

  • What happened. generate wrote checks/verify.yaml alongside its configs, and verify read its expectations from it. On any re-run — a dry-run retry, or an operator re-run after a verify failure — nothing stopped generate from relaxing neighbors_up == 4 to neighbors_up >= 0.
  • Why it matters. An agent optimising for "pass" will find the cheapest path to pass. If the judge is reachable, editing the judge is cheapest. That's reward hacking — no malice required.

Before (v1)

generate: write access to the whole run dir.
checks/verify.yaml: written by generate, lives next to configs.
verify trusts whatever the file says at run time.

After (v2)

Expectations derived by code from plan.yaml intent, hashed, and frozen at the approval gate.
generate may write only configs/; a deny rule (e.g. a pre-tool-use hook, as of Oct 2026) blocks writes to checks/.
verify checks the hash before it runs; a mismatch fails the run.
Changing a checker is a reviewed change to the harness, never a step inside a run.

One principle, two gaps. Both fixes move the judge out of reach: gap 1 takes judgement away from a fuzzy text match, gap 3 takes write access away from the thing being judged. The same rule shows up at harness scale in Ch 14: evaluator and permissions sit outside the loop that changes things.

16.5 Gaps 2 & 4: the resume hole and the rubber stamp

Gap 2 — no idempotency marker (first flagged in Ch 6)

  • What happened. The run stopped (budget hit, session crash) after core1 committed but before reports/deploy-core1.json was written. On resume, the orchestrator saw no report and deployed core1 again.
  • Why it matters. Some changes are harmless twice; many aren't (sequence-numbered entries, appended lists, anything that flaps a session on re-commit). "Resume from files" is only safe if the files say what has started, not just what has finished.

Before (v1)

# resume logic
for r in deploy_order:          # core first
    if exists(f"reports/deploy-{r}.json"):
        continue
    deploy(r)                   # may repeat!

After (v2)

mark(r, "started", cfg_hash)    # before commit
commit(r, label=f"netpush-{run_id}")
mark(r, "committed", cfg_hash)  # after OK match

# resume
if state(r) == "committed": skip
if state(r) == "started":
    if device_has_label(r, run_id):
        mark(r, "committed"); skip
    else: escalate(r)           # never guess
  • Two markers bracket the side effect; a run-id label on the device lets code check what actually happened instead of guessing.
  • The ambiguous case ("started", no label found) goes to a human. Resume logic that guesses is just a retry with extra steps.

Gap 4 — the gate showed raw config (first flagged in Ch 12)

  • What happened. The approver was shown six full configs, hundreds of lines each. After the third run they scrolled to the bottom and typed yes.
  • Why it matters. A gate the human can't evaluate in a couple of minutes isn't a check — it's a delay with a signature on it. The risk lives in the change, so show the change.

Before (v1)

"Here is the generated config for core1, core2, edge1–edge4. Approve? (yes/no)"

Raw text, no context, approval not tied to anything — if generate re-ran after approval, the old "yes" still counted.

After (v2)

Per-router diff vs the preflight snapshot (code-built — the authority).
Summary written by the model, labelled as a summary of the diff.
Dry-run result per router and the deploy order.
Risk flags computed by code: deletions, core routers touched, management paths touched.
Binding: approval is recorded against the plan hash; any change after approval re-opens the gate.

Notice where the model ended up. In v2 the model does more useful work at the gate (a readable summary) and less dangerous work everywhere else. That's the determinism dial from Ch 2: judgement and prose to the model, matching and deciding to code.

16.6 What was already strong — and the failure map, re-run

Keep these; don't "fix" them

  • Read-only parallel preflight. Cheap, safe, and gives generate and the gate a real baseline.
  • One central generate. Cross-router consistency (unique IDs, symmetric links) is checked once, in one place.
  • Honest checker labels. Nobody believes dry-run proves the commit will succeed.
  • Bounded loops. max 3 attempts plus budgets mean every failure ends in a report someone reads.
  • Stop on first failure, no blind rollback. The graph fails small and leaves a clear record.

17. The Skill Audit Checklist

How is it checked?

What you'll learn: a reusable rubric that scores any skill or agent against the six questions plus the model itself; how to read a score so it tells you what to fix first; a worked audit of the fictional gen-parser skill (findings only — no rewrite); and a step-by-step routine for running the audit on a skill you own.

17.1 Why a rubric, and how to score

Chapter 16 dissected one pipeline by hand. A rubric turns that into something you can repeat in twenty minutes, compare across skills, and re-run after a change.

The scale

  • 0 — absent. Nobody designed this; it happens by accident or not at all.
  • 1 — present but soft. It's written in the prompt or in someone's head, but nothing enforces it.
  • 2 — explicit and enforced. Code, permissions, files or a gate make it true whether or not the model co-operates.

Reading the score

  • Seven rows, max 14. The total is for trend-tracking only; fix the lowest row first, not the cheapest one.
  • A 0 next to an irreversible action (commit, delete, push, send) outranks every other finding.
  • "1" is the dangerous score: it looks handled, so nobody revisits it. Gap 1 in netpush was a 1 — there was a check.

17.3 Meet gen-parser (the audit subject)

gen-parser is a fictional, approval-gated skill. Given a captured sample of a CLI command's structured output, it builds a parser for that command.

1
Propose schema

The model reads the sample output and writes a proposed schema (field names, types, which keys are optional) into the chat.

2
Human approves

You read the proposal, ask for tweaks, and say "approved". The skill's instructions say not to generate before approval.

3
Generate code + tests

The model writes the parser and its unit tests, runs the tests, and keeps editing until they pass.

The shape is good — propose-then-generate puts a human node before the expensive step (Ch 12). The audit asks what holds that shape up.

Reading the result: 5 / 14

  • Fix first: "What does it remember?" (0) — the approval, the skill's whole safety story, is the least durable thing in it.
  • Then: "How does it repeat?" (0) and the self-graded tests under "How is it checked?" — together they form an unbounded loop judged by the agent running it.
  • Leave alone: the propose-then-generate shape. The design is right; the enforcement is missing. That's the most common audit outcome.
Pattern to remember. gen-parser and netpush v1 failed in the same places: an approval not bound to anything, and a checker inside the agent's reach. When two unrelated skills share a gap, it's probably a gap in how you build skills, not in either skill.

17.5 How to run this on your own skill

1
Draw the graph first

Sketch every step, who does it (code, model, agent, human) and every edge — including what happens on failure. If you can't draw it, that's finding #1.

2
Mark the irreversible edges

Circle every step that commits, deletes, pushes or sends. Audit those rows hardest; a 0 here outranks everything.

3
Score each row with evidence

For every score, point at a file, permission, hook or gate. "The prompt says so" caps the row at 1.

4
Replay one bad day

Pick a real failure (or invent one: crash mid-run, checker edited, approver in a hurry). Walk it through the graph and note which row should have caught it.

5
Write findings, not fixes

List the lowest rows first with one line each and the chapter to read. Keep the audit file next to the skill and re-score after every change to it.

  • v1's total looked healthy. The four 1s were where every real failure lived — that's why you fix the lowest rows, not chase the total.
What this means for your skill
  • Which row of your skill scores lowest — and is it next to an irreversible action?
  • How many of your "1"s are a sentence in a prompt that nothing enforces?

Cheat Sheet

The whole guide on one screen: the spine, the six questions, where code and model each belong, how loops stop, and the graph patterns you'll reuse.

The spine

  • Agent = Model + Harness. The harness is everything that isn't the model: context, tools, state, checkers, loops, graph, gates.
  • Loop and graph live inside the harness. Loop = control flow over time; graph = control flow across components. They're not eras that replace it.
  • Outer loop: traces in, harness edits out — with the evaluator and permissions kept outside the loop that does the editing.
#QuestionLayerOne-line rule
1What does it see?ContextLoad on demand; give each worker only its slice.
2What can it do?Tools & permissionsRead-only by default; isolate and guard every irreversible action.
3What does it remember?StateFiles, not chat; mark "started" before a side effect, "done" after.
4How is it checked?CheckerDeterministic, state-based, positive-match, out of the agent's reach.
5How does it repeat?LoopGoal, exit condition, retry cap, budget; fail loud.
6How do the pieces connect?Graph (incl. humans)Explicit edges incl. failure edges; a bound gate on each irreversible edge.

Code owns

Parsing output · matching success/fail · ordering · counting · asserting on state · committing · stop rules · budgets · permissions.

Model owns

Turning intent into artefacts · judgement on open-ended input · synthesis · summarising diffs and failures for a human · proposing (never approving) its own changes.

Loop stop rules

Success by an independent checker · retry cap (netpush: max 3 attempts, then escalate) · wall-clock, token and cost budgets · no progress across N attempts · any irreversible failure. Exhausted → stop and report, never silent retry.

Graph patterns

Fan-out/fan-in (parallel read-only workers) · orchestrator–worker · evaluator–optimizer (generate ↔ check) · serial walk with stop-on-first-failure (netpush deploy, core first) · human gate before an irreversible edge · no blind rollback of peers.

Decision Frameworks

Three questions you'll face every time you design or change a skill. Walk the steps in order and stop at the first one that decides it.

1. Code or model?

1
Is there one right answer you could write a test for?

Yes (parse this output, did the commit succeed, is this list sorted) → code. Stop.

2
Is the input open-ended or the output prose?

Yes (turn intent into config, summarise a diff, propose a schema) → model, then go to step 3.

3
Can code check the model's output?

Yes → model proposes, code checks. No → a human checks, or the output stays advisory.

4
Does a wrong answer cause an irreversible effect?

Yes → the decision to act is never the model's alone. Code gates it, a human approves it, or both.

Detail: Ch 2. Code vs. Model

2. Loop or graph?

1
Is it one actor repeating act → observe → adjust toward one goal?

Yes → a loop is enough. Give it a checker, a cap and a budget.

2
Is the task open-ended with no knowable step list?

Yes → a well-harnessed single agent loop may beat a predefined graph. Don't force structure the task doesn't have.

3
Do different steps need different tools, permissions or context?

Yes → split into nodes. That's a graph, even if it's a straight line.

4
Can parts run in parallel, or must some run in a fixed order?

Either → graph, with fan-out/fan-in or a serial walk made explicit.

Detail: Ch 8. Anatomy of an Engineered Loop · Ch 11. From Loop to Graph

3. Where does the human go?

1
Find the irreversible edges

Commit, deploy, delete, push, send. Put a gate immediately before each — not at the start of the run, not after.

2
Find the expensive forks

Where a wrong early choice wastes the rest of the run (schema, plan, approach), add a propose-then-approve gate.

3
Decide what the human sees

A diff, a short summary, checker results and code-computed risk flags. If it takes more than a few minutes to judge, it will become a rubber stamp.

4
Bind the approval

Record it in state against a version or hash. Any change after approval re-opens the gate.

5
Remove gates that never say no

If a gate hasn't rejected anything in months, either replace it with a code check or make what it shows sharper.
