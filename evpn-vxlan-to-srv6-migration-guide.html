Welcome

Moving your data-center overlay from VXLAN to SRv6 — the comparison and the playbook.

EVPN-VXLAN is mature, widely deployed, and well understood. EVPN-SRv6 is where the silicon and toolchain investment is heading. This guide covers both the technical delta between the two encapsulations and the step-by-step mechanics of migrating a live fabric without a maintenance window.

The Migration Question

Why move a perfectly working VXLAN fabric to SRv6?

VXLAN works — "because SRv6 is newer" is not an engineering justification. This section lays out the real reasons operators migrate, and the equally important reasons not to.

Header tax and scale

  • VXLAN carries an 8-byte VXLAN header plus a full UDP/IP outer — 50 bytes of overhead per packet before the inner Ethernet frame.
  • SRv6 with a uSID-only path (no SRH in the data plane) adds only a 40-byte IPv6 header; the entire forwarding instruction is encoded inside the DA.
  • VXLAN VNI is 24 bits — 16 million identifiers. SRv6 SID space is 128 bits; identifier exhaustion is not a practical concern at any fabric scale.
  • uSID compression means multiple segment instructions fit in a single 128-bit address, keeping MTU impact flat even for multi-hop TE paths.

Unifying SP + DC underlay

  • If your DC connects to a service-provider or WAN backbone that already runs SRv6, a SRv6 DC overlay lets the same IPv6/SRv6 underlay span both domains — no encap boundary at the DC edge.
  • One technology means one skill set, one set of tooling (path computation, telemetry collectors, verification scripts), and one operational model across campus, DC, and WAN.
  • End-to-end SRv6 eliminates the VXLAN-to-MPLS (or VXLAN-to-SRv6) hand-off stitching that today lives on a dedicated border or DCI node.

Service insertion and traffic engineering

  • SR Policy and Flex-Algo are first-class constructs in SRv6 — low-latency paths, disjoint paths, and color-based steering are native.
  • Bolting TE onto a VXLAN fabric requires overlay tricks (VXLAN policy maps, DSCP remarking) that are brittle and hard to verify end-to-end.
  • SRv6 service function chaining (SFC) inserts middleboxes by placing their SID in the segment list — no bump-in-the-wire VLAN gymnastics.

Vendor and silicon roadmap pressure

  • New ASIC generations (e.g., Cisco Silicon One, Broadcom Jericho3-AI, Marvell Teralynx) are increasingly SRv6-first; VXLAN feature parity on the latest pipelines is becoming an afterthought. (Verify current silicon SRv6 support against vendor data sheets.)
  • Some vendor product lines have already sunset VXLAN feature development; bug fixes continue but new capabilities (Enhanced EVPN, per-flow TE) land on SRv6 first.
  • If your refresh cycle aligns with the next ASIC generation, designing for SRv6 now avoids a second migration later.

What's NOT a reason to migrate

  • Your fabric is pure DC with no SP/WAN integration story — the "unified underlay" argument doesn't apply, and VXLAN operational simplicity may outweigh any benefit.
  • You are at moderate scale (sub-10k VNIs, no cross-DC TE requirements) and VXLAN is meeting all SLAs — the overhead delta is immaterial.
  • Your operations team has deep VXLAN expertise and no SRv6 familiarity — a forced migration under time pressure is a risk, not an improvement.
  • If any of these apply, read §21 Decision Matrix before proceeding.
Note: This guide assumes you've decided to migrate (or are seriously considering it). If you haven't, jump to §21 Decision Matrix first — it walks through the evaluation criteria so you can make the call with data.
1. What Stays the Same — BGP-EVPN Control Plane

The control plane is invariant. The data plane is what changes.

BGP-EVPN was designed as an encapsulation-agnostic control plane. Swapping VXLAN for SRv6 means replacing what rides inside the outer header — the BGP session topology, route types, and service semantics are untouched.

BGP-EVPN AFI/SAFI is unchanged

  • AFI 25 / SAFI 70 (l2vpn evpn) is the same on both encapsulations.
  • Route Distinguisher and Route Target semantics, format, and import/export policy logic carry over without modification.
  • Route-reflector placement (spines as RRs) and BGP session topology are identical.
  • The only BGP attribute that changes is the Tunnel Encapsulation attribute (RFC 9012) — value changes from VXLAN (8) to SRv6 L3 Service (14) or SRv6 L2 Service (15).

Route types still mean the same thing

  • Type 2 (MAC/IP Advertisement) — carries host MAC and optionally IP; used for L2 MAC learning and L3 host-route injection into VRFs. Role unchanged.
  • Type 3 (Inclusive Multicast Ethernet Tag / IMET) — signals BUM flooding membership per EVI. Role unchanged; the encap-specific attribute is what differs.
  • Type 4 (Ethernet Segment) — per-ES DF election; mechanism and timer behavior unchanged.
  • Type 5 (IP Prefix Route) — L3 VRF prefix advertisement for symmetric IRB; role unchanged.
  • Type 1 (ES per-EAD) encap-specific attribute differences are covered in §5.

MAC/IP learning is unchanged

  • Bridge-domain MAC learning still runs in the dataplane; BGP-EVPN still distributes those MAC/IP bindings to remote PEs.
  • ARP/ND suppression — local proxy reply from the PE's ARP/ND cache — works identically; suppression is decoupled from encapsulation.
  • MAC Mobility sequence numbers and sticky MAC semantics are carried in the same BGP extended community, unchanged.

EVPN config shape

  • VRF definitions, VNI-to-EVI bindings, RD/RT policy, and MAC-VRF templates remain structurally the same.
  • Anycast gateway MAC address assignments on SVIs are unchanged.
  • Only the underlay forwarding context changes: VTEP IP → SRv6 locator; VNI → service SID.

2. What Changes — Encap, Endpoint, Service ID

Three layers of change: the encapsulation header, the endpoint identity, the service identifier.

Everything that changes lives at or below the outer IP header. The BGP control plane passes the same routes; what changes is how the forwarding plane interprets and applies the reachability information those routes carry.

Encapsulation header

  • VXLAN: outer Ethernet + outer IPv4/v6 + UDP (dst 4789) + 8-byte VXLAN header containing the 24-bit VNI. Total overhead: ~50 bytes (IPv4 outer).
  • SRv6 uSID: outer Ethernet + outer IPv6 header (40 bytes). The destination address is the forwarding instruction. No UDP, no fixed tunnel header.
  • SRH (Segment Routing Header) is present only when the active segment list has more than one entry — for most single-hop EVPN data-plane flows, the SRH is absent.

Endpoint identity

  • VXLAN: endpoint is a VTEP identified by an IPv4 (or IPv6) loopback address. The BGP Next-Hop in the EVPN route is the VTEP IP.
  • SRv6: endpoint is the SRv6 node identified by its locator prefix. The BGP Next-Hop is the node's IPv6 loopback; the service SID encodes both the node and the service action.
  • uN locator (fc00:0:N::/48 in this guide) acts as the VTEP-equivalent for reachability; each leaf's per-leaf locator (fc00:0:1:N::/64) hosts service SIDs.

Service identifier

  • VXLAN: 24-bit VNI identifies the Layer-2 or VRF service instance. The VNI is carried in the VXLAN header.
  • SRv6: service SID carries both the endpoint and the action. L2 MAC-VRF unicast uses uDT2U/End.DT2U (decap + unicast MAC lookup in the bridge domain); L2 BUM uses uDT2M/End.DT2M; L3 VRF uses uDT4/End.DT4 (IPv4) and uDT6/End.DT6 (IPv6).
  • The SID is programmed per leaf per service — unlike VNI, it is not fabric-wide flat; it encodes the destination node.

Where uSID fits

  • uSID compresses the segment list into the 128-bit IPv6 destination address — typically 32-bit micro-segments packed into the lower 96 bits.
  • For most EVPN flows (single destination, no TE policy), the DA contains exactly one uSID and no SRH is pushed, keeping overhead at 40 bytes.
  • When a TE path is required (multi-hop segment list), additional uSIDs are packed into the same DA; an SRH is added only when the list overflows 128 bits.

VXLAN vs SRv6 at a Glance

VXLAN

  • Outer IPv4 or IPv6 + UDP (4789)
  • 8-byte VXLAN header; 24-bit VNI
  • VTEP = IPv4/v6 loopback
  • ~50 bytes overhead (IPv4 outer)
  • Service ID: flat 24-bit VNI (fabric-wide)
  • No native TE; UDP src hash for ECMP
  • IPv4 and IPv6 underlay supported

SRv6 (uSID)

  • Outer IPv6 only (no UDP)
  • 40-byte IPv6 header; SRH optional
  • Endpoint = SRv6 node locator + SID
  • 54 bytes total outer overhead on the no-SRH path (14 B outer Eth + 40 B IPv6); the 40 B IPv6 header carries the destination service SID
  • Service ID: 128-bit SID (node-scoped)
  • Native TE via segment list in DA or SRH
  • IPv6 underlay required

3. Reference Topology

Used in every packet walk and migration scenario. Read once, refer back.

A 2-spine / 4-leaf iBGP-EVPN fabric is the canonical target, with Spine-1 and Spine-2 acting as iBGP route-reflectors for all EVPN sessions (leaves peer upward to both spines as RR clients). This RR-on-spines pattern is the dominant DC deployment model.

Fabric nodes

  • Spine-1, Spine-2 — pure transit (no host-facing ports); iBGP RRs for the EVPN address family. No SIDs assigned to spines.
  • Leaf-1, Leaf-2, Leaf-3, Leaf-4 — EVPN PEs; all carry VTEP function (State A) or SRv6 endpoint function (State B/M).
  • All nodes share a common iBGP AS (65000). Underlay runs IS-IS or eBGP/IGP; only loopback reachability is required.

Hosts and services

  • Host-A — single-homed to Leaf-1, VLAN-100.
  • Host-B — single-homed to Leaf-3, VLAN-100. (Same L2 segment as Host-A across the fabric.)
  • Host-C — single-homed to Leaf-1, VLAN-200.
  • Host-D — dual-homed to Leaf-3 and Leaf-4 via an Ethernet Segment (ESI = 0x0001:0001:0001:0001:0001), VLAN-200. DF election applies.
  • VRF "green" — L3 VRF spanning VLAN-100 and VLAN-200 on all leaves, symmetric IRB. Both SVIs are VRF members; inter-subnet routing is local at each leaf's anycast gateway.

VLAN / VNI map

  • VLAN-100 → VNI-10100 → EVI 100
  • VLAN-200 → VNI-10200 → EVI 200
  • VRF "green" → L3 VNI-10300 (VXLAN) / uDT4 SID (SRv6)

Three topology states

  • State A — pure VXLAN: all four leaves are VTEP nodes. All EVPN routes carry the VXLAN Tunnel Encap attribute. This is the "before" baseline.
  • State B — pure SRv6 uSID: all four leaves are SRv6 endpoints. All EVPN routes carry SRv6 Service TLVs with uSID-based SIDs. This is the "after" target.
  • State M — mid-migration, dual-encap: Leaf-1 and Leaf-3 remain VXLAN; Leaf-2 and Leaf-4 have migrated to SRv6. Leaf-2 and Leaf-4 act as redundant border-leaves (gateway nodes) that stitch between the two encapsulations. Leaf-4 is dual-homed with Host-D, making it a gateway that also participates in ESI DF election.

Address conventions

  • IPv4 loopbacks: Leaf-1 = 203.0.113.1/32, Leaf-2 = 203.0.113.2/32, Leaf-3 = 203.0.113.3/32, Leaf-4 = 203.0.113.4/32.
  • IPv6 loopbacks: Leaf-1 = 2001:db8:1::1/128, Leaf-2 = 2001:db8:1::2/128, Leaf-3 = 2001:db8:1::3/128, Leaf-4 = 2001:db8:1::4/128.
  • uN locator block: fc00:0:1::/48 — allocated to this fabric.
  • Per-leaf locator: fc00:0:1:N::/64 where N = leaf number (1–4). Service SIDs are allocated within this /64.
  • Service SIDs:
    • Leaf-3 uDT2U for VNI-10100 (EVI 100): fc00:0:1:3:e000::
    • Per-leaf uDT2U for VNI-10200 (EVI 200): fc00:0:1:N:e001::
    • Per-leaf uDT4 for VRF green (IPv4): fc00:0:1:N:e100::

4. Header Math — VXLAN Stack vs SRv6 Stack

Every migration starts by understanding the bytes you're swapping.

VXLAN encap stack

  • Outer Ethernet (14 B) + outer IP (20 B IPv4 / 40 B IPv6) + UDP (8 B) + VXLAN header (8 B) + inner Ethernet frame.
  • Total overhead: 50 B with IPv4 outer; 70 B with IPv6 outer.
  • The 8-byte VXLAN header carries the 24-bit VNI in the low 3 bytes; the remaining 5 bytes are flags/reserved.
  • UDP destination port 4789 (IANA); source port is typically entropy-hashed for ECMP.

SRv6 encap stack

  • Outer Ethernet (14 B) + outer IPv6 header (40 B) + optional SRH + payload (inner Ethernet or IP packet).
  • No UDP, no fixed tunnel header — the IPv6 destination address is the forwarding instruction.
  • uSID no-SRH path (single segment, most EVPN flows): 54 B total outer overhead (14 + 40).
  • SRH is pushed only when the active segment list exceeds what fits in the 128-bit DA. SRH base = 8 B; each additional SID = 16 B.
  • SRH + 1 segment: 54 B outer + 8 B SRH base + 16 B = ~78 B. SRH + 2 segments: ~94 B.

Header-tax comparison

  • SRv6 uSID (54 B) sits between VXLAN-v4 (50 B) and VXLAN-v6 (70 B) — the difference is 4 bytes on the common IPv4-outer VXLAN path.
  • Jumbo-MTU fabric (9000 B or 9216 B) absorbs all encap cases without fragmentation or MTU reduction on host-facing SVIs.
  • The hard constraint is 1500-byte host MTU: all encap variants reduce the effective inner MTU by their overhead; ensure host MSS clamping or PMTUD is active.
  • SRH path (78 B+) costs meaningfully more; avoid SRH in the EVPN data plane unless explicit TE policy requires it.

What's the same

  • The original Ethernet frame (L2 service) or IP packet (L3 service) is carried unchanged as the inner payload — neither encap touches the inner header or payload bytes.
  • Inner VLAN tags, IP TTL, DSCP markings, and TCP flags are preserved end-to-end.

5. Route-Type Behavior Across Encaps

Same route types, different per-encap attributes.

Scope: §1 named the route types and confirmed they survive the migration. This section compares the per-encap BGP attributes for each route type — specifically where the VTEP/Next-Hop, Tunnel Encap community, and SID encoding differ between VXLAN and SRv6. See §1 for the "unchanged" summary.

Type 1 — Ethernet Auto-Discovery (per-ES and per-EVI)

  • Drives two mechanisms: per-ES A-D (mass-withdrawal on ES failure) and per-EVI A-D (aliasing — remote PEs load-balance to multi-homed leaf).
  • VXLAN encoding: ES Label field carries a label value signalling the ES (VXLAN repurposes the MPLS label field as a VNI/label placeholder); Tunnel Encap attr = VXLAN (type 8, RFC 9012).
  • SRv6 encoding: ES Label field is replaced by an ES SID — a per-ES SRv6 SID allocated on the PE; BGP Prefix-SID attr (RFC 8669) carries the SRv6 Service TLV (RFC 9252).
  • DF-election algorithm and timers are identical — the DF-Election Extended Community is unchanged; only the SID/label encoding differs.

Type 2 — MAC/IP Advertisement

  • Primary route for host MAC learning and host-route injection into VRFs.
  • VXLAN encoding: MPLS Label1 field repurposed as the L2 VNI (24 bits, e.g., VNI-10100); MPLS Label2 (when IP+MAC) carries the L3 VNI (e.g., VNI-10300 for VRF green).
  • SRv6 encoding: Label1 → uDT2U/End.DT2U service SID for L2 unicast MAC lookup in the bridge domain; Label2 → L3 service SID (uDT4/End.DT4 for IPv4 VRF; uDT6/End.DT6 for IPv6 VRF).
  • MAC Mobility sequence number is carried in the MAC Mobility Extended Community — identical in both encaps; sticky-MAC behavior unchanged.

Type 3 — Inclusive Multicast Ethernet Tag (IMET)

  • Signals BUM flooding membership per EVI; every PE for an EVI originates one Type 3 per EVI.
  • PMSI Tunnel attribute (RFC 6514) carries the replication mode: Ingress Replication (IR) is the most common mode for both VXLAN and SRv6 fabrics.
  • VXLAN IMET: PMSI tunnel-type = Ingress Replication; tunnel identifier = VTEP IP + VNI.
  • SRv6 IMET: PMSI tunnel-type = Ingress Replication; tunnel identifier = SRv6 endpoint IP; additionally, SRv6 supports uDT2M/End.DT2M as a native-multicast BUM action in the data plane (no need for a separate replication tunnel IP).

Type 4 — Ethernet Segment Route

  • Originated by every PE attached to a given ESI; used by remote PEs to discover all members of a multi-homed ES for DF election.
  • VXLAN encoding: ES Label field carries a label value identifying the ES; Tunnel Encap attr = type 8 (VXLAN).
  • SRv6 encoding: ES Label → ES SID (same SID structure as Type 1); BGP Prefix-SID attr with SRv6 Service TLV (RFC 9252).
  • DF-election algorithm (highest-IP wins by default, or W-ECMP/modulo) and all associated timers run identically regardless of encap.

Type 5 — IP Prefix Route

  • L3 VRF prefix advertisement for symmetric IRB; the cleanest route type to migrate first — no MAC state, pure IP prefix + next-hop.
  • VXLAN encoding: GW IP field carries the IP next-hop for the prefix inside the VRF; MPLS label = L3 VNI (e.g., VNI-10300); GW MAC = anycast gateway MAC on the originating leaf.
  • SRv6 encoding: GW IP / GW MAC handling unchanged; MPLS label → uDT4 SID (IPv4 VRF) or uDT6 SID (IPv6 VRF); BGP Prefix-SID attr with SRv6 L3 Service TLV (RFC 9252, type 5 sub-TLV).
  • Recommended first migration target: stand up SRv6 leaf, advertise Type 5 routes with SRv6 encoding, verify L3 reachability before touching L2 (Type 2/3) routes.

How the Encap Is Signalled in BGP

VXLAN side

  • BGP Encapsulation Extended Community (RFC 9012): type value 8 = VXLAN. Carried on all EVPN NLRI originated by a VXLAN PE.
  • MPLS Label fields in the EVPN NLRI (Types 1, 2, 4, 5) are repurposed as VNI containers — the 20-bit MPLS label field carries the 24-bit VNI with a right-shift or direct mapping depending on implementation.
  • No BGP Prefix-SID attribute is present on VXLAN routes.

SRv6 side

  • BGP Prefix-SID attribute (RFC 8669) is added to the EVPN NLRI, carrying the SRv6 Service TLV (RFC 9252).
  • For L3 services (Type 5, Type 2 with IP, VRF lookup): Type 5 sub-TLV — SRv6 L3 Service TLV — encodes the uDT4 or uDT6 SID and the transposition offset/length for packing the SID into the label field.
  • For L2 services (Type 2 MAC, Type 3 IMET, Type 1 A-D): Type 6 sub-TLV — SRv6 L2 Service TLV — encodes the uDT2U or uDT2M SID.
  • BGP Encapsulation Extended Community type 14 = SRv6 L3 Service; type 15 = SRv6 L2 Service (RFC 9012).

Next-hop encoding gotcha: If a receiving leaf has not negotiated SRv6 encap capability, it installs the route with a valid next-hop but programs the forwarding entry with no valid SID resolution — the route is installed in the RIB but silently unusable in the FIB. Traffic blackholes without a BGP-level error. Audit encap capability on every PE before enabling dual-stack: verify show bgp l2vpn evpn neighbor <ip> detail shows SRv6 capability negotiated, and spot-check show evpn evi detail to confirm SIDs are resolved.
6. Packet Walk 1 — Type 2 MAC/IP, Side-by-Side

Host-A → Host-B unicast (same VNI, different leaves), traced in both encaps.

A single unicast frame crossing two leaves in the same bridge domain is the most common forwarding event in a leaf-spine EVPN fabric. Walking it in parallel exposes exactly where the two encapsulations diverge — and how little the control plane cares.

Scenario

  • Host-A is attached to Leaf-1 on VLAN-100, mapped to VNI-10100.
  • Host-B is attached to Leaf-3 on the same VLAN-100 / VNI-10100 bridge domain.
  • Host-B's MAC has already been learned by Leaf-1 via a BGP-EVPN Type 2 advertisement from Leaf-3 — no ARP/ND flood required for this frame.
  • Both leaves run dual-stack underlays; Spine-1 and Spine-2 provide ECMP.

Control plane — what each leaf installs

  • Leaf-3 originates a BGP-EVPN Type 2 route for Host-B MAC, advertising its reachability in VNI-10100.
  • VXLAN path: Leaf-1 installs a MAC-VRF entry — Host-B MAC → VTEP next-hop 203.0.113.3, encap VNI 10100.
  • SRv6 path: Leaf-1 installs a MAC-VRF entry — Host-B MAC → service SID fc00:0:1:3:e000:: (Leaf-3 uDT2U for VNI-10100), outer IPv6 src 2001:db8:1::1.
  • No per-prefix SID is needed for the MAC itself; the SID encodes the entire EVI lookup on the egress PE.

The two walks produce identical L2 delivery to Host-B. The differences are entirely in the outer header and the egress lookup model.

What the side-by-side highlights

  • Header tax near-parity: VXLAN overhead is 50 B (IPv4 outer); SRv6 uSID is 54 B (IPv6 outer, no SRH). SRv6 is 4 B heavier than VXLAN-over-v4, but 16 B leaner than VXLAN-over-v6 (70 B) — the typical migration target already runs dual-stack underlays.
  • Egress lookup model diverges: VXLAN decap uses a two-step lookup — match UDP dport 4789, extract VNI, then look up VNI in a separate VNI→MAC-VRF binding table. SRv6 uses a single SID table hit — the 128-bit DA is matched directly against a local SID entry whose bound behavior (uDT2U) encodes both the EVI selection and the forwarding action.
  • Control plane is identical: Both paths are populated by the same BGP-EVPN Type 2 advertisement from Leaf-3. The route distinguisher, RT, and MAC/IP payload are unchanged — only the NLRI encap attribute (VXLAN vs SRv6 L2 Service) differs.
Same forwarding outcome, different lookup model. Both encapsulations deliver the L2 frame to Host-B with equivalent MAC learning and no per-flow state on the spines. The forwarding performance trade-off — SID table depth vs. VNI table depth — is a silicon implementation detail, not a protocol constraint. See §9 for hardware offload considerations and ASIC lookup pipeline analysis.
7. Packet Walk 2 — Type 5 IP Prefix, Side-by-Side

L3 VPN tenant, two subnets on two leaves — the cleanest service to migrate first.

Where Walk 1 traced an L2 frame across a shared bridge domain, Walk 2 crosses a VRF boundary. The source and destination are in different subnets; each leaf performs an IRB route lookup, not a MAC lookup. This is the dominant traffic pattern for data-center east-west L3 traffic and the safest place to start a live migration.

Scenario

  • Host-A (10.10.100.x) is on Leaf-1, VLAN-100, VRF green.
  • Remote subnet 10.10.200.0/24 is on Leaf-3, VLAN-200, same VRF green.
  • No shared bridge domain — this is pure L3, symmetric IRB. Each leaf owns its local subnet and advertises it as a BGP-EVPN Type 5 IP Prefix route.
  • Both leaves run dual-stack underlays; Spine-1 and Spine-2 provide ECMP.

Control plane — what each leaf installs

  • Leaf-3 originates a BGP-EVPN Type 5 route for 10.10.200.0/24, advertising its L3 reachability in VRF green.
  • The Type 5 NLRI carries a GW IP (Leaf-3's IRB address or loopback) and a GW MAC (Leaf-3 router-MAC). These are used by the ingress PE to rewrite the inner dst MAC before encapsulation.
  • VXLAN path: Leaf-1 installs an IP route in VRF green — 10.10.200.0/24 → VTEP next-hop 203.0.113.3, encap L3-VNI 50100, inner dst MAC = Leaf-3 router-MAC.
  • SRv6 path: Leaf-1 installs an IP route in VRF green — 10.10.200.0/24 → L3 service SID fc00:0:1:3:e100:: (Leaf-3 uDT4 for VRF green). No router-MAC rewrite needed; the SID encodes the entire VRF lookup on the egress PE.
  • L3-VNI 50100 is the per-VRF L3-VNI for VRF green; it is distinct from the per-VLAN L2-VNIs (10100, 10200).

Both walks deliver the inner IPv4 packet to the destination host identically. The VRF binding method — L3-VNI vs. uDT4 SID — is the only structural difference; the BGP-EVPN Type 5 control plane is shared.

Why this is the safe first cut

  • No bridge-domain state to migrate: Type 5 routes carry no MAC, no ARP-suppression cache, no BUM state. There is nothing to synchronize or drain before flipping the encap.
  • IRB cutover is VRF-scoped: Changing the encap on a Type 5 route affects only the L3 VRF forwarding entry on the ingress PE. The broadcast domain on either leaf is untouched. Hosts see no link-state change.
  • Rollback is trivial: Re-advertise the prefix with the old encap (VXLAN), withdraw the new one (SRv6). Traffic reverts within BGP convergence time (~sub-second with BFD). No host-facing impact; no MAC flush; no ARP re-trigger.
  • Verification is clean: A single show bgp evpn route type 5 and a ping across the VRF confirm correct forwarding on both sides before and after the cut.
Start here. Type 5 (L3 prefix) is the recommended first cut in any VXLAN→SRv6 migration: no bridge-domain state, no MAC mobility events, no BUM suppression cache to keep coherent across the transition window. Rollback is a one-line BGP config change with zero host-facing impact. Migrate all L3-only VRFs first, validate, then proceed to L2/L3 combined services (Type 2).
8. Packet Walk 3 — Type 3 IMET / BUM

ARP/flood handling. Ingress replication is the common ground; SRv6 unlocks options VXLAN can't reach.

Broadcast, Unknown-unicast, and Multicast (BUM) traffic is the one class that cannot be delivered with a single unicast tunnel — it must be replicated to every remote leaf that has members in the same bridge domain. This walk covers how both encapsulations handle that problem, using a concrete ARP-request flood as the example.

Scenario

  • Host-A sends an ARP request in VLAN-100 / VNI-10100 (EVI 100). Because the ARP target is unknown, Leaf-1 must flood to all other leaves with members in VNI-10100: Leaf-2, Leaf-3, and Leaf-4.
  • Leaf-1 ingress loopback: 203.0.113.1 (v4) / 2001:db8:1::1 (v6).
  • Remote member VTEPs (VXLAN): 203.0.113.2, 203.0.113.3, 203.0.113.4.
  • Remote member uDT2M SIDs (SRv6): fc00:0:1:2:e800::, fc00:0:1:3:e800::, fc00:0:1:4:e800:: — the e800 block denotes the L2 BUM/multicast service function (distinct from e000 uDT2U unicast and e100 uDT4 L3).

Control plane — Type 3 IMET

  • Each leaf with members in an EVI advertises a BGP-EVPN Type 3 (Inclusive Multicast Ethernet Tag, IMET) route per (EVI, Ethernet Tag). The NLRI carries the originating router's loopback as the replication endpoint.
  • Every Type 3 route carries a PMSI Tunnel attribute (RFC 6514) that declares the leaf's BUM replication mode. For ingress replication, Tunnel Type = 6 (Ingress Replication); the Tunnel Identifier field carries the leaf's VTEP address (VXLAN) or its SRv6 uDT2M service SID.
  • On receiving Type 3 routes from Leaf-2, Leaf-3, and Leaf-4, Leaf-1 builds a flood list for VNI-10100: one entry per remote leaf, keyed on the PMSI Tunnel Identifier. When a BUM frame arrives from Host-A, Leaf-1 iterates this list and creates one encapsulated copy per entry.
  • ARP-suppression caches (populated from Type 2 MAC/IP routes) may suppress ARP flooding for known targets, but unknown targets — including first-time ARPs and anycast gateways not yet learned — still hit the BUM path.

Ingress Replication — Both Encaps

Ingress replication is architecturally identical in VXLAN and SRv6: the ingress PE clones the frame once per remote member and sends each clone as a unicast packet. Only the outer header format differs. The source PE bears the full replication cost — one copy per remote leaf, N−1 copies for N leaves in the EVI.

The model (identical in spirit)

  • The ingress PE (Leaf-1) receives the BUM frame on the local access port.
  • It consults the per-EVI flood list, built from received Type 3 IMET PMSI Tunnel attributes.
  • For each remote member, it generates one unicast encapsulated copy. No multicast state is required in the underlay — spines forward each copy as ordinary unicast.
  • Egress leaves (Leaf-2, Leaf-3, Leaf-4) each receive their copy, decapsulate, and deliver the frame to local ports in VNI-10100.

VXLAN copy

  • Leaf-1 produces 3 copies. Each copy: outer Eth + outer IPv4 src 203.0.113.1, dst = the target leaf's VTEP (.2, .3, .4 respectively) + UDP dport 4789 + VXLAN VNI 10100 + inner ARP frame.
  • The VNI is the same in every copy; only the outer IPv4 dst differs.
  • Outer overhead per copy: 50 B (Eth 14 + IPv4 20 + UDP 8 + VXLAN 8).

SRv6 copy

  • Leaf-1 produces 3 copies. Each copy: outer Eth + outer IPv6 src 2001:db8:1::1, DA = the target leaf's uDT2M SID (fc00:0:1:2:e800::, fc00:0:1:3:e800::, fc00:0:1:4:e800:: respectively) + inner ARP frame. No SRH — single uSID encodes both locator and BUM service function.
  • The SID encodes leaf identity and service type (uDT2M) simultaneously; the egress leaf matches the SID against its local SID table, decapsulates, and floods to the bridge domain.
  • Outer overhead per copy: 54 B (Eth 14 + IPv6 40). No SRH overhead.

Beyond ingress replication, each encapsulation family offers an alternative BUM mechanism. VXLAN's alternative (PIM-based multicast underlay) is a legacy option that adds operational complexity. SRv6's alternative (in-fabric replication via uDT2M / End.DT2M at a designated replicator) is a net improvement and requires no underlay multicast state.

VXLAN-specific: PIM-based multicast underlay (legacy)

  • Instead of ingress replication, the underlay runs PIM (typically PIM-SSM or PIM-SM). Each VNI is mapped to a multicast group address; BUM traffic is delivered via the underlay tree rather than N unicast copies.
  • Advantage: ingress PE sends one copy; the multicast tree handles replication at the spines. For large EVIs (many leaves) this reduces egress bandwidth at the source PE.
  • Disadvantage: requires PIM on all spines and leaves; adds protocol complexity and per-group state in the underlay. In practice most modern DC deployments use ingress replication exclusively and avoid underlay multicast altogether.
  • Prevalence: uncommon in greenfield deployments; more likely in legacy brownfield fabrics that were built before ingress replication was widely deployed.

SRv6-specific: in-fabric replication via uDT2M / End.DT2M

  • A designated fabric replicator node (e.g., a spine or a dedicated replicator leaf) is configured with an End.DT2M (or uDT2M in compressed uSID form) behavior. The ingress PE sends a single copy to the replicator's SID; the replicator expands and forwards to all member leaves.
  • This shifts the replication fan-out cost from the source PE to a purpose-built or over-provisioned replicator, reducing ingress PE compute and bandwidth for large EVIs.
  • No PIM, no underlay multicast state — replication is controlled entirely by the SRv6 policy and the replicator's SID table. Operationally cleaner than PIM-based underlay.
  • Not required for basic migration; ingress replication with uDT2M SIDs (as walked above) is the default and covers most deployments.

Migration implication

  • Default: use ingress replication on both sides. The PMSI Tunnel Type 6 (Ingress Replication) attribute is the same in both VXLAN and SRv6 BGP advertisements; only the Tunnel Identifier value changes (VTEP address → uDT2M SID). This minimizes migration risk and keeps the BUM plane structurally identical across the transition.
  • If your VXLAN deployment uses PIM underlay: the PIM-to-ingress-replication shift is a separate workstream. Do not conflate it with the VXLAN→SRv6 encap migration. Retire the PIM underlay after validating ingress replication for all VNIs, ideally in a maintenance window before the SRv6 cutover.
  • ARP suppression state: The suppression cache (populated from Type 2 routes) carries over to the SRv6 plane unchanged, since it lives in the BGP control plane. Unknown-target ARPs still exercise the BUM path; verify the uDT2M flood list on the new plane before completing the cutover.
PIM underlay retirement: If your VXLAN deployment uses a PIM multicast underlay for BUM delivery, migrating to SRv6 is also an opportunity to drop PIM entirely — uDT2M ingress replication (or in-fabric replication) requires zero underlay multicast state. However, plan the underlay-multicast retirement as a separate workstream from the encap migration. Conflating the two changes makes fault isolation harder and extends the maintenance window. Retire PIM per-VNI after validating ingress replication on the VXLAN plane first, then proceed with the SRv6 cutover.
