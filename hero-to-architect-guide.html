1. The Agentic Coding Loop

What you'll learn: how an agent actually works under the hood — the plan/act/observe cycle, what differs from chat, where it breaks, and how to read the loop in real time.

1.1 From chat to agent — the fundamental shift

Chat is a ping-pong game: you send one message, the model sends one message back, you respond. The conversation accumulates but nothing happens unless you copy text out and do something with it yourself. The model has no hands. It observes the world only through your keystrokes, and it acts on the world only through your clipboard.

An agent breaks that contract. You give it a goal — not a question — and it loops: it inspects its environment (reads files, runs commands, browses docs), it decides what to do next, it executes, it reads the results, and it decides again. This continues until it believes the goal is complete, hits a resource limit, or asks for your help. The model does have hands, in the form of tool calls.

The shift matters because your mental model has to change. In chat you are the executor; you parse the response and act. In an agent loop the model is the executor; you are the goal-setter, reviewer, and interrupt handler. The skills transfer poorly. "Just ask it better" is a chat reflex. "Give it a tighter spec and review the plan before it runs" is an agent reflex. This guide is about building the second kind of muscle memory.

v1 contrast: v1's "What is an AI Agent" section is the map — it tells you what an agent is and where it fits. This chapter is the depth — it tells you what's actually happening inside the loop so you can steer it, stop it, and diagnose it when it goes wrong.

1.2 The loop: plan → act → observe → repeat

Every agentic turn, regardless of tool, follows the same four-phase structure. The phase durations vary (planning can be milliseconds or several thinking tokens; acting can be one file read or a dozen parallel tool calls) but the sequence is invariant.

Plan
What should I do next?
→
Act
Execute tool calls
→
Observe
Read tool results
→
Repeat
Until goal met or blocked

Plan: The model reads its full context — system prompt, conversation history, tool definitions, and any previous tool results — and generates text that either answers directly or announces a tool call. When extended thinking is enabled, this phase is longer and more deliberate; the model can reason about multi-step consequences before committing to an action.

Act: The model emits one or more tool calls (file reads, shell commands, web fetches, editor edits). Most agents can fire multiple tools in parallel if they're independent. The model is not running the tools itself; the host process (Claude Code, Kilo Code, Gemini CLI) intercepts the output, executes the tools, and appends the results.

Observe: Tool results come back into the context as a structured message. The model now sees what happened: file contents, command output, error messages, anything the tool returned. This is where ground truth enters — the model's plan might have been wrong, and the observation corrects it.

Repeat: The model decides whether the goal is met. If not, it plans the next action. This loop continues until the model calls a "done" tool, the user interrupts, or the maximum turn limit is hit. Understanding that this is a loop — not a one-shot completion — is the single most important mental model shift in this guide.

1.3 Anatomy of one agent turn

Within a single turn, here is the typical sequence of events. The model receives its context, may produce reasoning tokens (if extended thinking is on), then emits text and/or tool calls. Each tool call gets executed and its result injected back before the next generation step.

The following is an annotated JSONL-style trace of a real three-tool turn: the agent reads a file, edits it, and runs a test to verify. This is a compressed representation of the actual protocol messages — real tool calls are wrapped in slightly different structures depending on the SDK, but the semantic content is identical.

// Turn N — context arrives
{ "role": "user", "content": "Add a --verbose flag to the CLI parser in cli.py, then run the tests." }

// Model plans (may include thinking tokens, not shown here)
// Model acts — tool call 1: read
{ "type": "tool_use", "name": "Read", "input": { "file_path": "/repo/cli.py" } }

// Tool result 1 injected back
{ "type": "tool_result", "content": "...file contents of cli.py..." }

// Model acts — tool call 2: edit (based on what it just read)
{ "type": "tool_use", "name": "Edit",
  "input": {
    "file_path": "/repo/cli.py",
    "old_string": "parser = argparse.ArgumentParser()",
    "new_string": "parser = argparse.ArgumentParser()\nparser.add_argument('--verbose', action='store_true')"
  }
}

// Tool result 2 injected back
{ "type": "tool_result", "content": "Edit applied successfully." }

// Model acts — tool call 3: verify
{ "type": "tool_use", "name": "Bash",
  "input": { "command": "cd /repo && python -m pytest tests/test_cli.py -q" }
}

// Tool result 3 injected back
{ "type": "tool_result", "content": "3 passed in 0.42s" }

// Model completes the turn
{ "role": "assistant", "content": "Done. Added --verbose flag. All 3 tests pass." }

Notice the pattern: every act is immediately followed by an observe before the next act. The model cannot "fire and forget" — it waits for each result before deciding the next step (unless it fires parallel tool calls, in which case it waits for all of them together). This sequential dependency is why agentic tasks are slower than chat: real I/O is happening at every step.

1.4 What the agent "sees" vs what you see

This is where most early-agent confusion lives. The model's actual input is a large, structured document: system prompt + conversation history + tool definitions + all tool results from this and previous turns. You see a terminal or an IDE panel. The two views are very different, and the mismatch is a reliable source of debugging headaches.

Consider: the model might have a <system-reminder> block injected by the harness telling it about available skills, recent memory, or permission grants. You don't see that unless you specifically ask to dump the context. The model's "beliefs" about what tools it has, what files it has read, and what was previously said are all locked inside that context document — which grows silently with every turn.

Concrete example: Claude Code injects a <system-reminder> with the current list of approved permissions, deferred tools, and active skills at the top of each turn. If a skill was loaded three turns ago, the model still "sees" it and can invoke it — even though your terminal shows no sign of it. If you're confused why the model is doing something, the first debugging step is: what is actually in its context right now?

The practical implication: agents can appear to behave inconsistently because their context has changed, not because the model is random. A long conversation where tool results accumulate, old decisions drift in and out of the context window, and injected reminders come and go will produce behavior that looks non-deterministic to a user watching only the terminal. Learning to reason about what is in the context — not just what you've typed — is a core skill.

1.5 Determinism, non-determinism, and the temperature knob

Temperature is the sampling parameter that controls how "creative" the model's output is. At temperature 0 (greedy), the model always picks the highest-probability next token. At higher values it samples more broadly, producing more varied output. This matters for agentic coding: you usually want low temperature for tool-call generation (you want the model to reliably call the right tool with the right arguments), but sometimes higher temperature for initial brainstorming or architecture ideation.

Important caveat: Claude Code and Gemini CLI do not expose temperature as a CLI surface-level parameter. It's fixed or invisible in those tools. The temperature dial matters when you're calling the underlying APIs directly — e.g., through the Anthropic SDK or the Google Gen AI SDK — where you control the sampling parameters yourself. For everyday CLI use, don't look for this knob; it isn't there.

But temperature is only one source of non-determinism. Parallel tool calls introduce ordering ambiguity: if two tools fire simultaneously and both modify state, the outcome depends on which result arrives first. Race conditions in shell commands are real. File system ordering, network latency in web-fetch tools, and even OS scheduling can affect which observation the model receives first. When you see "flaky" agent behavior that can't be explained by temperature, look at the tool execution layer, not the model.

The practical rule: for agentic coding, treat the output as probabilistic but reviewable. The model will usually do the right thing on the first attempt. When it doesn't, the loop gives it a chance to self-correct via the observe phase — provided you've given it enough context to recognize the error.

1.6 The control problem

The loop runs until it stops. The three main stop conditions are: (1) the model calls a terminal/done tool signalling completion, (2) the max-turn or token-budget limit is hit, or (3) the user interrupts. Understanding these is essential for working safely with agentic tools — especially when the agent has permission to write files, run commands, or make network calls.

Human-in-the-loop patterns are your primary control mechanism. The simplest form: the agent surfaces a plan as text before executing it, and you approve or modify before it runs. This is the "plan-then-confirm" gate, and it's built into most tools in some form. Claude Code's Plan Mode produces a text proposal and waits; Kilo Code's Architect mode thinks before switching to Code mode for execution. The gate does not prevent errors — it just moves them earlier, when they're cheaper to fix.

A subtler control pattern: granularity of permission. You can grant "approve all file reads" while requiring approval for each shell command, or vice versa. The right granularity depends on your trust in the task: for well-understood, reversible operations (reading files, writing new files), broad permission is fine. For operations with external effects (network calls, git push, database writes), tight granularity keeps you in the loop.

The most common control failure: granting broad "auto-accept" and then leaving the room while the agent runs a long task. The agent can't tell you it's confused halfway through — it will keep going, making decisions you would have caught if you'd been watching. Stay close for the first few turns of any novel task.

1.7 Plan mode vs auto mode vs interactive

Different tools use different vocabulary for their execution modes. We use a three-mode taxonomy here as a pedagogical frame — this is our framing, not an industry standard that all tools share. Knowing the underlying concept lets you map any tool's vocabulary back to the same mental model.

  • Plan mode: The agent reasons and produces a plan but takes no actions. All tool calls are suppressed. Output is text only. Use this when you want to see the agent's thinking before anything touches your filesystem or shell.
  • Auto mode: The agent executes the full loop without asking for approval at each step. Maximum throughput, minimum friction. Use this for well-understood tasks on isolated branches.
  • Interactive mode: The agent pauses before each tool call (or before "risky" ones) and asks for your approval. Maximum control, higher friction. Use this for novel or high-stakes tasks.

None of these modes is objectively correct — the right choice depends on the task scope, the reversibility of the actions, and your confidence in the spec. A common pattern: start interactive to understand what the agent is doing, build confidence, then switch to auto for subsequent runs of the same pattern.

1.8 Anatomy of a bad loop

Most agent failures aren't dramatic crashes — they're subtle drifts that compound over several turns until the output is wrong in ways that are hard to trace back. Knowing the failure archetypes lets you catch them early.

The rathole: The agent picks up on a tangent inside the task and goes deep on it, forgetting the original goal. A classic example: asked to add a feature, it notices a linting error, fixes it, notices the linter flagged three more files, fixes those, and is now three directories deep in style cleanup while the feature is untouched. Early-warning sign: tool calls whose file paths have diverged from the original scope.

Drift: The goal shifts gradually across many turns as the context window fills and early instructions lose effective weight. The model isn't ignoring you — it's weighting more recent context more heavily and has "forgotten" the preamble. Early-warning sign: output that technically satisfies the last thing you said but not the original intent stated five turns ago.

Premature claim-of-done: The model announces completion when the task is only partly finished. This often happens when the model observes a partial success signal (tests pass, no errors printed) and treats it as full success. Early-warning sign: the model says "Done" but the diff is smaller than expected, or the output doesn't include all the deliverables you asked for.

The 3-turn heuristic: If after three tool-call turns you can't see clear forward progress toward the original goal, stop the agent and re-prompt with a sharper scope. Don't let it continue hoping it will self-correct — it usually won't without fresh direction.

1.9 Mental model: agents are interns with very fast hands

The most useful mental model for working with agentic coding tools: imagine a junior engineer who is extremely fast, broadly knowledgeable, eager to help, and occasionally confidently wrong. They can read a thousand-line file in the time it takes you to type a command. They know most standard library APIs. They will attempt any task you give them without hesitation.

But they need clear specs. Vague instructions produce vague results. They will make reasonable-sounding decisions about ambiguous edge cases without flagging the ambiguity to you — because they are fast and eager and don't know they should pause. They can get lost in a large codebase without a map. And they can be confidently wrong about something domain-specific that isn't in their training data (your internal API, your company's deployment process, the specific invariants of your codebase).

The intern framing predicts the right management style: write specs as if you're briefing a smart engineer who doesn't know your system. Review every diff before merging. Give them small, bounded tasks rather than open-ended explorations. Check in after three turns. And don't be surprised when they do something sensible but not quite what you meant — that's not a model failure, that's a spec failure.

2. Context as Working Memory

What you'll learn: how the context window actually works as the agent's RAM — token economy, prompt caching, compaction, memory systems, and the anti-patterns that waste both.

2.1 The context window, in plain terms

Every model has a finite context window — a block of token slots that holds everything the model can "see" at inference time: your system prompt, the conversation history, tool schemas, tool outputs, and the assistant's own prior responses. Think of it as RAM. The CPU (the model) can only operate on what fits in RAM right now; anything outside it is simply invisible.

Current window sizes (verify current at time of reading): Claude Sonnet 4.6 and Opus 4.7 both offer a 200K-token default context with a 1M-token extended tier available on request; Gemini 2.5 Pro supports 1M tokens natively; GPT-4o and o3 top out around 128K tokens. Bigger windows don't mean free — everything in the window costs input tokens on every turn, even content that hasn't changed.

"In context" is binary: content is either inside the window or it isn't. There is no partial awareness, no fuzzy retrieval unless you build a RAG layer on top. When the window fills, either content is dropped (truncation), summarized (compaction), or the session ends.

2.3 The token economy — input vs output vs cached

Providers charge differently for three token categories: uncached input, cached input, and output. Cache reads are typically ~10× cheaper than uncached input; cache writes cost ~1.25× the base input rate on Anthropic (the write premium amortizes over subsequent cache hits). Output tokens are the most expensive category — often 3–5× the per-token input rate.

Steady-state cost formula (per turn, after cache is warm): 
cost = (uncached_in × P_input)
     + (cached_in  × P_input × 0.1)   // cache read: ~10× cheaper
     + (output     × P_output)         // output: most expensive
First-write cost formula (cache cold or invalidated): 
cost = (cacheable_prefix × P_input × 1.25)  // write premium on Anthropic
     + (uncached_remainder × P_input)
     + (output × P_output)

Multipliers vary by provider. As of mid-2026: Anthropic charges 1.25× for cache writes and 0.1× for cache reads; Google (Gemini API) uses a different cache pricing model — context caching charges a per-token-per-hour storage fee for cached prefixes rather than a write-multiplier (verify exact pricing against ai.google.dev before writing — the model evolves); OpenAI prompt caching for GPT-4o is automatic at 0.5× for cached reads. Always verify against current provider pricing pages before building cost models.

The strategic takeaway: maximize the fraction of each turn that lands in cached input. The steady-state formula shows cache reads are cheap; the first-write formula shows that invalidating the cache (by editing an early message or the system prompt) resets the clock and pays the write premium again.

2.4 Prompt caching — how it works, when it kicks in, what breaks it

Anthropic's prompt caching is prefix-based: the model caches the longest matching prefix of the input that was seen in a recent prior request (TTL: 5 minutes for standard, up to 1 hour with explicit cache-control headers — verify current TTL options against Anthropic docs, these evolve). The cache key is the exact byte sequence of the prefix — any edit to the system prompt, any added tool schema, or any changed message before the cached region invalidates it entirely.

Patterns that maximize cache hits:

  • Freeze the system prompt. Put stable content (persona, project conventions) at the top; put session-variable content (file paths, current branch) at the bottom or pass it as user messages.
  • Keep tool schemas stable. Don't register tools dynamically mid-session. A changed schema invalidates the entire prefix up to that point.
  • Use explicit cache-control breakpoints (Anthropic API: "cache_control": {"type": "ephemeral"}) to mark where the cacheable prefix ends. This tells the API exactly how much to cache rather than relying on automatic prefix matching.
  • Avoid prepending new content. Inserting new tool results early in the message list — rather than appending — breaks the prefix for everything that follows.

Claude Code handles cache breakpoints automatically — it marks the system prompt and loaded files as cacheable. You benefit without configuring anything; what you can do is avoid actions that bust the cache: editing CLAUDE.md mid-session, changing MCP server config, or using /clear when continuation would have preserved the warm cache.

When the context fills, each tool has its own compaction mechanism:

Compaction is lossy. The summarization step condenses many tokens into fewer, but nuance is lost — specific function signatures, exact error messages, intermediate reasoning. If you need to preserve something precisely across a compaction boundary, write it to a file or add it to your memory file (CLAUDE.md, GEMINI.md, etc.) before the compact runs.

After /compact in Claude Code, the session continues with a synthesized summary in place of the raw history. The model receives this as a user message prefixed with the compaction notice; your next turn can reference everything in the summary, but can't see the verbatim prior tool calls.

2.6 The cost of long sessions (and how to keep one going)

Long sessions degrade in two ways: context fills with stale tool output, and cache invalidations compound. The result is both slower (more tokens to process) and more expensive (cache misses, output re-explaining stale state). A 4-hour Claude Code session on a complex codebase can hit 500K+ input tokens per turn late in the session.

Techniques to extend session quality:

  • Pin key files early. Use /add or ask the agent to re-read critical files at the start of a new sub-task — they'll be near the front of the window and more likely to survive compaction.
  • Clear irrelevant tool output. If a large grep result or test log was useful but is now stale, ask the agent to note the key finding and discard the raw output. This keeps the window lean.
  • Spawn sub-agents for investigation. Use Claude Code's sub-agent mode (or Kilo Code's task delegation) for exploratory tasks (reading 20 files to answer a question). The sub-agent's context is separate; only the result lands in your main session.
  • Break naturally at task boundaries. Commit, note what's next, then /clear. Restart with a concise re-briefing. This costs a cache-write premium but avoids context bloat compounding across unrelated tasks.

2.7 When to start fresh vs continue — the /clear question

The decision of whether to clear context is not just economic — it affects the model's reasoning quality. Stale context that contradicts the current state of the codebase can cause the model to make decisions based on outdated information.

Decision tree: clear vs continue 
New topic / unrelated task?          → /clear (or New Task)
Same task, but context is stale?     → /clear, re-brief concisely
Mid-task, active files in context?   → Continue (preserve cache)

  • Gemini CLI: /clear — same behavior, wipes conversation.
  • Kilo Code: No /clear slash command. Use the New Task button in the side panel to start a fresh session. Alternatively, close and reopen the Kilo Code chat panel.

2.10 Context anti-patterns

These are the patterns most responsible for context bloat, cache busting, and degraded session quality:

  • Paste-the-whole-file. You paste a 500-line module when you have a question about one function. Use grep or the Read tool with line ranges instead. Five targeted lines cost 30 tokens; the full file costs 3 500.
  • Paste-and-pray. You dump a full stack trace, log file, or JSON blob and ask the model to "figure out what's wrong." The model reads it, but now it's permanently in the context. Use grep, head, or a summarizing sub-agent to extract the signal first.
  • Log dump accumulation. Running tests 10 times without clearing test output. Each run appends several KB of logs. After 10 runs you have 50 K tokens of mostly-identical output. Clear between runs or capture only the diff.
  • Mid-session schema changes. Registering a new MCP server or changing tool config mid-session invalidates the prefix cache for the entire session. Make tool config changes before starting a session.
  • Abandoning sub-agents for context efficiency. Running deep investigation (reading 20 files to answer an architectural question) in the main session when a sub-agent could do the same work with isolated context, returning only the answer.
  • Editing early messages. Retroactively editing a user message or system prompt mid-session. This breaks the cache prefix and forces a full re-encode of all subsequent content.

3. Tools, Side Effects & the Agent's World

What you'll learn: how tool calls extend an agent's capabilities, the blast-radius spectrum from grep to rm -rf, permission models, sandboxes, and how to design an allowlist that lets the agent move fast without breaking things.

3.1 What is a "tool" to an agent

From the model's perspective, a tool is a JSON-schema-described function it may choose to invoke. The runtime — Claude Code, Kilo Code, Gemini CLI — intercepts the model's tool-call output, executes the function, and injects the result back into context as a tool-result message. The model never runs code itself; it emits structured intent, and the harness acts on it.

Every tool definition in the Anthropic Messages API shape carries three standard fields (name and input_schema are required; description is strongly recommended but technically optional — the model relies on it for selection):

{
  "name": "read_file",
  "description": "Read the full text of a file at the given path. Returns file contents as a string.",
  "input_schema": {
    "type": "object",
    "properties": {
      "file_path": {
        "type": "string",
        "description": "Absolute path to the file to read"
      }
    },
    "required": ["file_path"]
  }
}

The description is not metadata — it is a natural-language instruction to the model about when and how to invoke the tool. A weak description means the model misuses the tool or skips it entirely. The input_schema is a JSON Schema object; the model's input will be validated against it before execution. This matters: a schema that accepts a string where an array is needed creates ambiguous behavior at the boundary.

3.2 Built-ins you'll use daily — Read, Edit, Write, Bash, Grep, Glob

Read loads a file into context. Prefer it over a Bash cat because the harness tracks which files have been read — both for permission enforcement and to provide line-number prefixes that make Edit diffs unambiguous. Always read before editing.

Edit makes a targeted string replacement in a file. It validates that the old string exists exactly once before applying the change. This is the right tool for surgical modifications: changing a function signature, fixing a bug, updating a constant. Because it sends only the diff, it is far cheaper in tokens than Write for large files.

Write creates or completely overwrites a file. Use it when you are producing a new file from scratch or when a complete rewrite is genuinely cheaper than a sequence of Edits. It requires a Read first on existing files — the harness will refuse otherwise, protecting you from clobbering unread state.

Bash runs an arbitrary shell command. It is the most powerful and the most dangerous built-in. Prefer narrow, read-only Bash invocations (grep, find, git log) during exploration, and reserve write/destructive commands for explicit intent. The harness can be configured to require per-call approval for Bash while auto-approving Read/Edit.

Grep searches file contents by pattern. It is faster than Bash grep for simple cases because the harness can short-circuit it without spawning a shell. Use it when you want the first occurrence in a large codebase — the tool returns matches with file paths and line numbers ready for a follow-up Read.

Glob lists files matching a pattern. Use it to discover structure — **/*.ts, src/**/index.{ts,tsx} — before deciding which files to read. It is strictly non-mutating and can always be auto-approved.

3.3 How agents pick which tool to call

The model selects a tool by weighing three signals: the tool's description (the primary signal), the shape of the input schema (does the data I have fit?), and the prior turn context (what has already been read, what partial state exists). A model that has just done a Read on a file will prefer Edit over Write for the same file because the context signal says "partial knowledge" matches Edit's stated contract.

This selection is not rule-based lookup — it is inference. The practical implication: if your tool description says "use this for X" and the model keeps using it for Y, the description is wrong or the schema is too permissive. Descriptions that include explicit anti-patterns ("do not use this if the file is larger than 100 lines") are not pedantry — they are steering prompts baked into the tool manifest. This becomes critical when you build your own MCP tools (Chapter 16): bad descriptions cause agent thrash that wastes tokens and time.

Prior turn context also influences tool ordering. If the agent is mid-plan and has already called Bash to clone a repo, it will sequence subsequent calls assuming the working directory is now inside the repo. This is why agent sessions with long tool-call chains become increasingly context-sensitive — the model's implicit state model grows with each tool result.

Not all tool calls are equal. A Glob that finds nothing has zero side effects; a Bash that pipes to psql in production has potentially irreversible ones. Before granting auto-approval to any tool, place it on the blast-radius spectrum.

3.5 Idempotency, retries, and the side-effect problem

Idempotency means running the same operation twice produces the same result as running it once. Most file edits are idempotent only if they are pure replacements. A Bash script that appends to a config file, runs npm install, or applies a database migration is not idempotent by default. If the agent retries — because a network timeout made the first attempt ambiguous — you can end up with duplicate entries, doubled dependencies, or failed migrations that refuse to re-run.

Patterns that help: wrap install steps with existence checks (if ! command -v foo; then install foo; fi), use CREATE TABLE IF NOT EXISTS in migrations, and use declarative config formats (Terraform, Helm values) rather than imperative scripts where possible. For Bash tools you expose to an agent, document idempotency guarantees in the tool description — the model will then reason about whether a retry is safe.

The retry problem is compounded in multi-step plans. An agent that executes steps 1–5 successfully, then fails at step 6, may restart from step 1 if context is lost. Without idempotency, steps 1–5 produce errors or duplicate state. This is why checkpointing (commit after each logical unit of work) is not just a workflow nicety — it is a correctness requirement when side effects are involved.

3.6 The permission model — ask, allow, allow-edits, plan-only

Permission tiers across the three major harnesses follow a common taxonomy despite different UI surfaces. At the coarsest level: plan-only (the agent proposes but never executes — pure planning mode); ask per call (every tool invocation requires interactive approval); allow by category (read-only always allowed, destructive always requires approval, everything else configured); and full auto (all tool calls execute without interruption).

Claude Code implements this through its settings.json allowlist and a per-session --dangerously-skip-permissions flag. Its default is ask-per-call for new tool patterns, which is the safest starting point. Kilo Code surfaces the same tiers as per-category checkboxes in the extension settings UI — read operations, write operations, and execute operations each have their own toggle, which you enable project-by-project without touching a config file.

Gemini CLI takes a different approach: it ships a one-shot launch flag, --yolo (verify any shorthand against current docs), which disables all permission prompts for the duration of that single CLI invocation. This is a flag at launch time, not a persisted mode toggle or a per-category setting. The asymmetry matters: there is no Gemini equivalent of Claude Code's per-pattern allowlist that carries across sessions — you either commit to --yolo at startup or you get prompts. Choose carefully based on the risk profile of the session.

3.7 Per-project allowlists — .claude/settings.json, Kilo permission rules

Claude Code resolves permissions in a layered hierarchy: global user settings, then per-project .claude/settings.json, then per-session overrides. The project file is the right place for team-shared rules — commit it to the repo so everyone on the project gets the same tool permissions automatically.

A minimal allowlist for a TypeScript project that wants read/edit auto-approved and all Bash requiring a pattern match:

{
  "permissions": {
    "allow": [
      "Read",
      "Edit",
      "Write",
      "Glob",
      "Grep",
      "Bash(npm run test)",
      "Bash(npm run build)",
      "Bash(git diff*)",
      "Bash(git log*)",
      "Bash(git status)"
    ],
    "deny": [
      "Bash(rm -rf*)",
      "Bash(git push*)"
    ]
  }
}

Kilo Code does not use a file-based allowlist. Its permission rules live in VS Code extension settings (the Kilo Code settings panel), and they are stored in VS Code's settings.json at the workspace or user level. Rules are configured via checkboxes per operation category — not by writing permission strings. This means Kilo rules are not automatically shareable via git commit; they must be distributed through workspace settings or documented separately. The checkbox UI is more approachable for individuals, but it lacks Claude Code's granular pattern-matching for specific Bash commands.

3.8 Auto-mode — when to use, when to fear

Auto-mode (full tool auto-approval) is the right choice for: isolated environments where blast radius is bounded by the sandbox (see 3.9), read-heavy exploration tasks where the worst outcome is a few extra file reads, and CI pipelines where there is no human in the loop anyway. The speed gain is real — interactive approval breaks the model's flow and introduces latency that fragments multi-step plans.

Auto-mode is dangerous for: any tool family that writes outside the working tree, operations on shared or production infrastructure, and sessions that include network-write tools (API calls, deployments, database writes). The failure mode is not that the model makes a wrong choice once — it is that a single bad tool call in a 20-step plan can leave a mess that is expensive to unwind. The model cannot feel regret; it keeps going.

Rules of thumb by tool family: Read/Grep/Glob are always safe for auto. Edit/Write are safe for auto when git is the safety net and the session is short enough that you will review the diff before committing. Bash is safe for auto only when the allowed patterns are tightly scoped — test runners, linters, read-only git commands. Network-write tools (MCP servers that POST to external APIs) should never be auto in anything resembling production.

3.9 The sandbox — container, devcontainer, VM, bare metal

The sandbox spectrum runs from bare metal (highest capability, highest blast radius) through devcontainer/Docker (filesystem and process isolation, shared network by default) through a full VM (network isolation, snapshotable) to ephemeral container per session (maximum safety, highest cost in setup time). Each step up the isolation ladder reduces blast radius but also reduces the agent's ability to reach things it might need — local databases, test infrastructure, hardware interfaces.

For most development work, a devcontainer is the sweet spot: the agent gets a real filesystem, a real shell, and the project's full toolchain, but it cannot write to your host filesystem or persist side effects across container teardown. VS Code and Cursor ship devcontainer support out of the box; Claude Code can be run inside a devcontainer manually or via a pre-configured Docker image. The cost is a 10–30 second startup penalty per session and the occasional "the tool I need isn't installed in the container" friction.

Ephemeral containers (spin up, run, destroy) are the right choice for high-blast-radius automation — think CI agents that run against feature branches. A fresh container per session guarantees no state leaks between runs. The downside is that the agent cannot benefit from warm caches, installed dependencies, or prior build artifacts unless those are baked into the base image. Design your base image around the agent's typical tool requirements, not around developer convenience.

3.10 Tool-call observability — what just happened on disk?

Claude Code exposes tool-call events via --output-format=stream-json, which emits a newline-delimited JSON stream of every event — tool invocations, tool results, model turns, and cost metadata. This is Claude Code-specific: Gemini CLI does not have an equivalent streaming JSON output flag (it logs to stderr in a human-readable format, and machine-parseable output requires wrapping the CLI or using the API directly); Kilo Code surfaces tool calls in the VS Code output panel as formatted log entries, not as a parseable stream.

For day-to-day observability without stream-JSON, git is the most reliable audit trail. Configure the agent to commit after each logical step, and git log --oneline --stat becomes a tool-call summary. For finer granularity, use hooks — Claude Code's hooks config block lets you fire shell commands on tool events (before/after Bash, after Edit, on session stop). A one-line hook that appends to a session log gives you a persistent record without needing to capture the stream.

For persistent MCP server tools, observability is a first-class design concern. Each MCP server should log its own inputs and outputs. When debugging an agent that called an MCP tool and produced a wrong result, the question is: did the model call the tool with the right input, or did the tool return the wrong output? Without per-tool logs, you can only infer from context — with them, you can pinpoint in seconds. Build logging into every MCP server you write (Chapter 16 returns to this).

The agent should be able to read and edit source files freely, run tests and lints, and read git history — but should never push to remote, run migrations without approval, or call any cloud CLI. Here is the .claude/settings.json allowlist for that project:

      "Read", "Edit", "Write", "Glob", "Grep",

      "Bash(npm run lint*)",

To apply the same logic in Kilo Code: open Kilo Code settings → Permissions → enable "Read files" and "Edit/Write files" auto-approve; leave "Execute commands" as ask-per-call. Because Kilo's category granularity is coarser than Claude Code's pattern matching, the system prompt becomes the second enforcement layer for specific Bash commands.

Test your allowlist before trusting it: run the agent on a throwaway branch, watch the approval prompts it triggers, and refine. A good allowlist produces zero prompts for the 80% of operations that are routine and exactly one prompt for the 20% that carry real risk. If you are getting prompts on every file read, the allowlist is too tight; if the agent is pushing to remote without asking, it is too loose.

4.2 The three dials — capability vs cost vs latency

Every model selection decision reduces to three dials you cannot maximize simultaneously. Capability is the model's ability to reason correctly on hard tasks — long context coherence, multi-step planning, subtle bug detection. Cost is the dollar price of input and output tokens. Latency is time-to-first-token and total generation time. Turning one dial up typically turns at least one other down.

The pick rule, stated simply: use the cheapest model that can do the job correctly at the latency your workflow tolerates. "Can do the job correctly" is the constraint that prevents you from always picking Haiku/Flash — if the model hallucinates on your task, the downstream debugging cost exceeds the model savings. "At the latency your workflow tolerates" is the constraint that prevents you from always picking Opus/GPT-5 — if your task is synchronous and user-facing, a 20-second response is not acceptable regardless of how good it is.

A useful calibration exercise: run the same 10-prompt benchmark across three model tiers on your actual workload. Measure accuracy (does the output work without correction?), latency (wall clock from call to response), and cost (tokens in/out). Plot them. You will almost always find a tier that dominates on cost/latency with acceptable accuracy loss — that is your workhorse model. The top tier becomes the specialist you reach for when the workhorse fails.

4.6 Local models — Ollama, LM Studio, when they make sense

Ollama and LM Studio are the two dominant local inference runtimes for developers in 2026. Ollama is CLI-first: ollama run llama4 downloads and runs a model with no GUI, exposes an OpenAI-compatible REST endpoint at localhost:11434, and integrates with any tool that accepts an OpenAI API base URL override. LM Studio is GUI-first: a macOS/Windows/Linux desktop app with model browsing, quantization selection, and a built-in chat UI, also exposing a compatible local API endpoint.

Local inference makes sense in three scenarios: privacy requirements (code, prompts, or data cannot leave the device — legal, compliance, or employer policy constraints); cost requirements (high-volume pipelines where per-token cloud costs exceed hardware amortization); offline requirements (air-gapped environments, travel, or unreliable connectivity). It does not make sense when capability is the binding constraint — a 70B local model on consumer hardware will not match Opus or GPT-5 on genuinely hard reasoning tasks, and the capability gap matters for architecture-level decisions.

Hardware baseline for useful local inference: Apple Silicon M2 Pro or later (32 GB unified memory minimum for 70B Q4), or an RTX 4070 or better (12 GB+ VRAM for 7–13B, 24 GB for 70B Q4). The latency picture is nuanced: on Apple M3 Ultra, Llama 4 70B at Q4 produces ~30–50 tokens/second — fast for batch tasks, borderline acceptable for interactive use. A cloud Haiku or Flash call is typically faster wall-clock if network latency is low. Local wins on privacy and sustained high-volume throughput.

4.7 BYO-model in Kilo Code — routing, fallbacks, mode-specific picks

Kilo Code's model routing is configured per mode: each mode (Architect, Code, Ask, Debug, etc.) can be assigned a different model independently. This is the right design for cost engineering — your Architect mode should use a high-capability model because it runs infrequently and its output drives downstream work, while your Ask mode (used dozens of times per session for quick questions) should use a fast, cheap model. The configuration surface for per-mode model assignment is in the Kilo Code settings UI under the Modes section. Verify the exact config file path and schema — Kilo Code has historically used workspace-level config (look for .kilocode/ directory or .roomodes file — verify against current Kilo Code docs, as the config format has evolved across versions).

An illustrative per-mode routing example (this is a suggested pattern, not Kilo Code's shipped default — your Kilo installation's actual defaults will differ): Architect mode → Claude 4.7 Opus (deep reasoning, infrequent); Code mode → Claude 4.7 Sonnet (fast, capable for routine coding); Ask mode → Claude 4.7 Haiku or Gemini Flash (speed-optimized, high-frequency). Debug mode might use Sonnet by default and escalate to Opus if the session produces more than 5 failed fix attempts.

Fallback routing — using a cheaper model first and escalating on failure or low confidence — is not natively built into Kilo Code's mode system as of mid-2026. You implement it at the orchestration layer: a custom mode whose system prompt instructs the model to explicitly mark tasks as requiring deep reasoning before the harness routes them. Alternatively, use the Kilo orchestrator pattern (Boomerang Tasks) where a lightweight orchestrator model delegates subtasks to specialist sub-agents running stronger models for hard subtasks only.

4.8 Thinking / extended thinking — what it buys, what it costs

Extended thinking (Claude's term) or "reasoning" mode (OpenAI's o-series framing) refers to models that perform explicit chain-of-thought deliberation before producing their final answer. The thinking tokens are generated internally, typically billed at a reduced rate compared to output tokens, but the total token count can be substantial — a hard problem might consume 10,000–30,000 thinking tokens before the visible response appears. The latency cost is the more practical constraint: extended thinking adds 10–60 seconds to response time for hard problems.

When extended thinking pays: multi-step logical problems with no obvious greedy path (algorithmic design, security threat modeling, root-cause analysis of complex bugs), tasks where the model has historically hallucinated on the first attempt, and tasks where the cost of a wrong answer (debugging time, rollback, production incident) exceeds the cost of the extra thinking budget. When it wastes: well-defined mechanical tasks (generate a CRUD endpoint, rename a variable, write a migration), tasks with a clear single-step answer, and any interactive session where 30-second latency breaks the developer's flow.

Practical guidance: set a thinking budget cap (Anthropic's API allows a budget_tokens parameter for extended thinking — verify current parameter name). A budget of 5,000–8,000 tokens handles most medium-hard coding problems without runaway cost. Set it to 0 for routine tasks (the model will not invoke thinking). Reserve unlimited budget for the rare genuinely hard problem. Track your thinking token spend separately — it will surprise you in mixed-use sessions.

4.9 Prompt caching as a cost lever — beyond the basics

Prompt caching allows the provider to store a prefix of your prompt on their inference infrastructure and skip re-processing it on subsequent calls. The cache hit discount is substantial — historically 90% reduction in input token cost for cached prefixes on Claude (verify current discount at docs.anthropic.com). The catch: the cache only hits if the prefix is byte-for-byte identical from call to call. Any character change in the cached prefix invalidates the cache for all content after the change point.

Three structural rules for maximizing cache hit rate: keep system prompts static — do not interpolate dynamic values (timestamps, session IDs, user names) into the system prompt; move dynamic content to the human turn. Append, don't insert — if you must modify a long prompt between calls, add new content at the end rather than inserting it in the middle; insertion invalidates everything downstream. Monitor hit rate explicitly — the Anthropic API returns cache_read_input_tokens and cache_creation_input_tokens in the usage object; track the ratio per session to validate that your caching strategy is working.

A worked example: a coding session with a 10,000-token system prompt (project context, codebase summary, CLAUDE.md rules) that runs 40 turns. Without caching: 40 × 10,000 = 400,000 input tokens billed at full price. With caching and stable prefix: 1 × 10,000 cache-creation tokens + 39 × 10,000 cache-read tokens. If cache reads cost 10% of full price, the session's system-prompt input cost drops by ~88%. At scale, this is the single highest-leverage cost reduction available without changing models.

4.10 Batching, message batches, async wins

Batch APIs allow you to submit multiple API requests as a single job, processed asynchronously with a completion window (typically up to 24 hours) rather than synchronously. In exchange for accepting async delivery, providers offer significant price reductions. The historical pattern across providers has been roughly 50% discount on batch vs. synchronous pricing — but verify current discount and SLA for each provider: Anthropic's Message Batches API, OpenAI's Batch API, and Google's equivalent each have their own current discount tiers and time-to-completion guarantees that change with infrastructure capacity (verify current at time of reading at each provider's batch documentation).

Batch APIs are the right tool for: generating documentation across a large codebase (hundreds of files, no user waiting), running evals over a test set, processing logs or data, classification pipelines, and any task where latency is not user-facing. They are wrong for: any interactive session, any task in the critical path of a deployment, and any task where the next step depends on the result of the current one (sequential dependencies prevent batching).

Implementation note for Claude Message Batches: the API accepts an array of request objects, each with its own custom_id for result matching. Results are polled or retrieved via a results endpoint after the batch completes. There is no streaming within a batch — each request produces a complete response. Error handling must account for partial failure: some requests in a batch may succeed while others fail; the custom_id map lets you retry only the failed items. This is meaningfully different from a synchronous retry loop.

4.11 Context size vs effective usable context

Nominal context windows have expanded dramatically: Claude 4.7 supports 200K tokens (with extended tiers), Gemini 3 Pro supports 1M+ tokens, GPT-5 supports 128K–1M depending on tier. These numbers do not mean you can fill them and get uniform quality. The "lost in the middle" problem — where information placed in the middle of a very long context is retrieved less reliably than information at the beginning or end — is documented across all frontier models, though the severity varies.

Rule of thumb (model-dependent, verify against current evals): performance begins to degrade past approximately 50–70% context fill for most coding tasks. This is not a cliff — it is a gradient, and the exact threshold depends on task type (factual retrieval degrades before reasoning), content structure (well-structured code is retrieved more reliably than prose), and model. Gemini 3 Pro has demonstrated stronger long-range recall than 2024-era frontier models at high fill levels — this is a genuine architectural advantage worth considering for specifically large-context use cases.

Practical consequence: for a 200K Claude session, treat ~120K–140K as your reliable working space. If your actual content needs more, restructure your context strategy: use retrieval (semantic search over the codebase, returning only relevant chunks) rather than whole-file loading, break the task into smaller subtasks with fresh context windows, or consider Gemini 3 Pro if the use case truly requires dense 500K+ context. Never pad context with content that is marginally relevant — every token of irrelevant context increases the chance that relevant content is displaced or diluted.

4.12 The cost-per-feature mental model

The cost of building a feature with an AI coding agent decomposes as: cost = input_tokens_per_turn × turns × turns_per_feature × input_price + output_tokens_per_turn × turns × turns_per_feature × output_price. The turns-per-feature variable is the one most developers underestimate — a feature that looks like "write the CRUD endpoint" typically involves 8–15 turns: initial plan, scaffold, write route, write model, write tests, fix lint error, fix test failure, refactor for consistency, add validation, handle edge case, final review. Not one.

A worked example with concrete numbers (using approximate mid-2026 pricing — verify current): a CRUD endpoint feature on Claude 4.7 Sonnet, 12 turns, average 4,000 input tokens/turn (including context + history) and 800 output tokens/turn. At approximately $3/million input tokens and $15/million output tokens (verify at docs.anthropic.com): input cost ≈ 12 × 4,000 × $0.000003 = $0.144; output cost ≈ 12 × 800 × $0.000015 = $0.144; total ≈ $0.29 per endpoint. With prompt caching hitting 80% of input tokens at a 90% discount, input cost drops to ~$0.032 — total with caching ≈ $0.18 per endpoint.

Scale this to a feature sprint: 20 endpoints + 10 service methods + 5 complex refactors. Without caching: roughly $0.29 × 35 = ~$10. With caching and Sonnet routing (reserving Opus for the 5 complex refactors): closer to $4–6. Routing the Opus tasks to Sonnet when possible and batching the non-interactive documentation generation could halve the total again. Cost-per-feature thinking turns model selection from an abstract API preference into a concrete budget line item.

5. IDE vs Terminal: Choosing Your Surface

What you'll learn: install and run the three primary agentic coding tools (Kilo Code, Claude Code, Gemini CLI), understand where each fits, place the wider field (Cursor, Aider, etc.) in context, and choose deliberately for the task in front of you.

5.1 The dominant idioms — IDE-resident vs terminal-resident

Agentic coding tools cluster into two idioms based on where they live in your workflow. IDE-resident tools embed directly inside your editor — VS Code, Cursor, Windsurf, JetBrains. They see the file tree, the open editor tabs, inline diagnostics, and the selection you've highlighted. The interaction model is visual: proposed changes appear as inline diffs you accept or reject, context is injected automatically from the current file or workspace, and the feedback loop runs at the speed of a keypress. For developers who already live inside an IDE all day, the cognitive overhead is nearly zero.

Terminal-resident tools live in your shell. They are invoked like any other CLI program, they read context from the working directory and flags you pass, and their output streams to stdout. This makes them composable: you can pipe them, script them, run them in CI, invoke them headlessly from a Makefile, or orchestrate multiple agents across repos without ever opening a GUI. The interaction model is conversational and scriptable rather than visual and point-and-click.

Neither idiom is strictly superior. IDE-resident tools reduce friction for single-file or single-project edits where visual diff review matters. Terminal-resident tools win on automation, reproducibility, and anything that needs to run without a human in the loop. Most professional engineers end up using at least one from each column, picking the right surface for each class of task.

5.2 The three primary tools — Kilo Code, Claude Code, Gemini CLI

This guide focuses on three tools that together represent the dominant paradigms at the time of writing. Kilo Code is an open-source VS Code extension that brings agentic, model-agnostic AI assistance directly into the IDE — the IDE-resident primary. Gemini CLI is Google's open-source terminal agent backed by the Gemini model family, with a notable free tier via personal Google account — the terminal-resident primary from the Gemini ecosystem.

These three were chosen not because competing tools are inferior, but because together they give you direct experience of both idioms, two distinct terminal-agent philosophies, two billing models, and two underlying model families. 5.6 IDE strengths vs terminal strengths

IDE-resident tools shine when the feedback loop is visual and iterative. Inline diff review — where each proposed change appears highlighted in the exact line it modifies — is genuinely faster than reading a patch in the terminal when you are editing a single file or a small cluster of related files. IDE tools also benefit from zero context-setup cost: the tool already knows which file you have open, what your cursor is on, and what the compiler is currently complaining about. For developers new to agentic coding, the IDE surface reduces the learning curve because the interaction feels like pair programming rather than CLI operations.

Terminal-resident tools have a different set of strengths that compound over time. They are scriptable: you can drive them from shell scripts, Makefiles, GitHub Actions, or any orchestration layer without a GUI. They compose with existing Unix tooling — pipe output to grep, chain them with &&, background them with &. They run headlessly in CI pipelines, enabling automated code review, security scanning, or documentation generation on every pull request. They also tend to give the user more explicit control over context, which matters for large codebases where automated context injection can bloat token costs.

A practical heuristic: reach for the IDE tool when you are actively editing and want to stay in flow; reach for the terminal tool when you want to automate, batch, run in CI, or operate across multiple repositories at once.

5.7 Claude Code vs Gemini CLI — the terminal-vs-terminal choice

Both Claude Code and Gemini CLI are terminal-resident agentic coding tools, and they overlap significantly in capability. Both can read your codebase, write code, run shell commands, and execute multi-step tasks. The practical differences come down to model family, context window, billing model, and ecosystem integration.

Claude Code is backed by Anthropic's Claude model family (Opus, Sonnet, Haiku). It has a strong reputation for following nuanced instructions precisely and for producing clean, idiomatic code. It integrates tightly with Anthropic's MCP ecosystem and exposes a powerful hooks system. Billing is not free: Claude Code requires either an Anthropic Pro or Max subscription, or an API key billed per token. There is no genuine free tier for production use.

Gemini CLI is backed by Google's Gemini model family and offers a 1 million token context window — significantly larger than Claude's current limits — which is a material advantage for tasks that require ingesting entire large codebases at once. The billing asymmetry is real and significant: Gemini CLI provides a genuine free tier via personal Google account, with approximately 1,000 requests per day at no charge (verify current limits at the official repo and AI Studio). For learners, side projects, and low-volume automation, this makes Gemini CLI the lower-friction entry point. For teams with existing Anthropic contracts or strong Claude-model preferences, Claude Code will often be the natural choice.

5.8 Working in multiple tools at once

Nothing prevents you from running more than one agentic tool on the same codebase simultaneously, and in practice many professional engineers do. The most common pairing is Kilo Code for active editing + Claude Code (or Gemini CLI) for review and security scanning. The workflow looks like this: Kilo Code makes a batch of changes in the IDE, you commit or stash them, and then you invoke Claude Code from the terminal with a prompt like "Review the changes I just made for security issues, off-by-one errors, and missing error handling." The terminal agent reads the diff independently and surfaces concerns that the in-IDE tool missed — because it is operating from a fresh, unanchored perspective rather than the same context frame that generated the code.

Another useful pairing is Claude Code for implementation + Gemini CLI for a second opinion on architecture. Because both are terminal-resident, you can run them sequentially in the same shell session, feeding the output of one as context to the other. This is not a workflow most tutorials teach, but it is one of the highest-leverage habits an agentic engineer can develop: using model diversity as a quality gate rather than relying on a single model's blind spots.

The main caveat when running multiple tools simultaneously is write conflicts. Establish a clear ownership rule: one tool writes, others read-only review. Never let two agents write to the same files concurrently without a coordination layer.

6. Spec-Driven Development: OpenSpec & SpecKit

What you'll learn: why specs matter when agents code at speed, two production approaches (OpenSpec and SpecKit) to driving features through specs, how they differ, and how to apply either to a real CLI tool.

6.1 Why specs matter when agents code fast

Agentic coding tools can generate hundreds of lines of working code in seconds. That speed is their greatest asset — and it is also the source of a subtle, compounding risk: drift is cheap, drift recovery is expensive.

When a human writes code slowly, each line of implementation is a moment of conscious alignment with intent. When an agent writes code fast, that alignment check collapses. The agent will produce code that compiles, passes tests, and looks plausible — but may be solving a slightly different problem than the one you actually have. The first sign of drift is often not a failing test but a code review comment like "this isn't quite what I asked for," or worse, a production bug that traces back to a misunderstood requirement.

The traditional countermeasure is code review. But code review catches drift after implementation. At agentic speed, a single session can produce changes across dozens of files before anyone looks at a diff. By the time drift is detected, the agent has built more on top of it — integration points, tests, documentation. The cost of unwinding grows non-linearly.

The right countermeasure is a spec written before the agent writes the first line of code. A spec externalises intent into a form the agent can read, reason over, and be held to. It becomes the ground truth that resolves ambiguity — not memory, not conversation history, not hope. When the spec is versioned alongside the code, drift becomes visible as a diff between the spec and the implementation, not as a mysterious behavior in production.

Specs also solve a second problem: context degradation. Long agent sessions lose fidelity. The spec file, re-injected at the start of each session, restores full context instantly. It is the cheapest possible form of persistent memory.

The time investment in writing a spec is almost always recovered in the first session it prevents from going sideways. At scale — multiple engineers, multiple agents, multiple concurrent features — specs are not overhead; they are the coordination layer that makes agentic development coherent.

6.2 The contract — spec → behavior → tests

A spec is not documentation written after the fact. It is a contract: a formal statement of what a feature must do, written before implementation begins. The contract has three parties: the spec that describes behavior, the implementation that realises it, and the tests that enforce it. When all three are in sync, you have working software. When any two diverge, you have a bug, a doc mistake, or a test gap — all recoverable. When all three diverge independently, you have an undocumented feature that no-one can safely change.

6.3 OpenSpec model — workspace and proposals

OpenSpec is an open-source specification management system designed for codebases where specs live alongside code in git. The core idea is that specs are first-class files, not wiki pages or tickets. They live in a versioned workspace, they are updated through a formal change process, and they are archived (not deleted) when superseded.

Note: The directory layout below reflects the OpenSpec model at the time of writing. Always verify the current canonical structure against the official repository at github.com/Fission-AI/OpenSpec before adopting it — directory names and file conventions have evolved across versions.

openspec/
├── specs/                        # canonical (accepted) specs live here
│   └── gitlog-report.md          # example: a feature spec
│
└── changes/                      # in-flight proposals
    ├── add-gitlog-report/        # one subdirectory per change id
    │   ├── proposal.md           # change rationale + summary
    │   └── specs/                # delta specs for this change
    │       └── gitlog-report.md  # the proposed new or modified spec
    │
    └── archive/                  # accepted/rejected changes moved here
        └── add-gitlog-report/    # original structure preserved

The lifecycle of an OpenSpec change moves through three states: proposed (in openspec/changes/<id>/), accepted (spec promoted to openspec/specs/, change directory moved to openspec/changes/archive/), and rejected (moved to archive without promotion). The archive discipline is intentional: rejected or superseded proposals are preserved for audit and context, not deleted.

The canonical specs in openspec/specs/ are the authoritative source of truth. Agents are expected to read from this directory before implementing any feature. The changes directory is ephemeral working space — it holds proposals under review and disappears from the active tree on acceptance.

CLI operations cover lifecycle management only: openspec list (show active changes), openspec show <id> (display a change's proposal and delta specs), openspec validate (lint spec structure), openspec archive <id> (move an accepted change to the archive). Content — writing the spec, reasoning about it — is handled by the AI slash commands, not the CLI.

6.5 SpecKit model — slash commands and artifacts

SpecKit takes a different philosophy: rather than a file-system workspace with a CLI lifecycle, it provides a set of AI slash commands that each write a specific artifact into a feature-scoped directory. The workflow is slash-command-driven rather than file-system-driven, and it is designed to work natively inside Claude Code or compatible AI environments.

Note: SpecKit's directory structure and exact slash command names may differ from what is shown below. Always verify the current artifact layout and command names against the official SpecKit documentation before adopting the pattern in a new project.

The four primary slash commands and their outputs:

CommandWritesPurpose
/specify <feature>spec.mdGenerate the feature specification — acceptance criteria, interface contract, edge cases

The key invariant is that each feature gets its own isolated directory containing all four artifacts in sequence.

The slash-command model has two important properties. First, each command is idempotent — you can re-run /specify to refine the spec without losing the plan, because each artifact is a separate file. Second, each command reads its predecessors — /plan reads spec.md, /tasks reads both, /implement reads all three. The chain is self-documenting.

6.9 Living with specs — drift, refactoring, archiving

Specs are not write-once artifacts. Code evolves, requirements change, and the spec that was accurate in month one will drift from the implementation by month three — unless you actively maintain it. The question is not whether drift will happen, but how you detect and correct it.

Detecting drift: The simplest technique is to include a "spec review" step in your regular code review process. When a PR modifies a feature, check whether the corresponding spec file was also updated. If the implementation changed but the spec did not, flag it. Some teams run a periodic "spec audit" session — every quarter, read through the canonical specs and run a quick prompt: "Does the current implementation of <feature> match this spec? Flag discrepancies." The agent will surface them in minutes.

Refactoring specs: When a feature genuinely changes scope or behavior, update the spec first, then update the implementation. This is the spec-driven equivalent of test-first development: the spec change is the declaration of intent, and the implementation change is the execution. In OpenSpec, this means creating a new change proposal for the spec update before touching the code. In SpecKit, it means re-running /specify with updated requirements before re-running /plan and /implement.

Archiving specs: When a feature is deprecated or removed, do not delete its spec. Archive it (in OpenSpec this is handled by the archive lifecycle; in SpecKit, move the spec directory to an archived/ subdirectory). Deleted specs disappear from the record; archived specs preserve the history of decisions. Future engineers — or future agents — will find context in archived specs that they cannot find anywhere else.

Spec granularity creep: Over time, specs tend to accumulate detail. A 2-page spec becomes a 10-page spec as edge cases are documented, exceptions are catalogued, and historical context is appended. This is mostly healthy, but watch for the point where the spec becomes harder to parse than the code. If an agent takes 60 seconds of context-loading to read the spec before it can start work, the spec has grown too large. Consider splitting into a core spec (the contract) and a separate decisions log (the history).

6.10 Anti-patterns — speccing what doesn't need a spec

Spec-driven development has real overhead. A spec file needs to be written, reviewed, maintained, and eventually archived. For the right features, this overhead is paid back many times over. For the wrong features, it is pure waste. Recognising the anti-patterns saves you from drowning in spec files for things that did not need one.

Anti-pattern 1: Speccing trivial CRUD. If the feature is "add a /users/:id GET endpoint that returns the user by ID," the spec is already fully described by the sentence you just wrote plus the existing data model. Writing a formal spec file adds no information. The agent can implement this from a one-line prompt. Reserve specs for features with non-trivial business logic, multiple output formats, or behavior that cannot be inferred from naming conventions.

Anti-pattern 2: Spec effort exceeds implementation effort. If writing and reviewing the spec takes longer than the implementation would have taken without one, the spec is not providing value at this scale. This most often happens with one-off scripts, migration scripts, or throwaway tooling. If the tool will be used once and discarded, a spec is overhead with no return. A rough prompt is sufficient.

Anti-pattern 3: Specs that drift untouched. A spec that no-one updates is worse than no spec — it actively misleads. Agents that read a stale spec will implement against outdated requirements with full confidence, because they have no way to know the spec is stale. If your team cannot commit to maintaining specs, do not introduce them. An honest "no spec, use judgment" is safer than a lying spec file.

Anti-pattern 4: Over-speccing exploratory work. In the early stages of a feature — when you are not yet sure what the right interface is — writing a detailed spec freezes premature decisions. In this phase, use a lightweight "spike spec" (a few bullet points of hypotheses) rather than a full behavioral contract. Graduate to a full spec once the shape of the feature is clear.

Anti-pattern 5: Spec by committee. A spec that needs sign-off from six people before any code is written reproduces the worst of traditional requirements processes without the benefits of agility. Keep spec review tight: one author, one reviewer, merge. Larger specs can go through wider review — but the default should be lightweight, not heavyweight.

7.1 What "plan" means here — different from spec

In everyday speech, "spec" and "plan" are near-synonyms. In agentic development they are completely distinct artifacts with different audiences, different lifecycles, and different purposes — and confusing them is one of the most reliable ways to produce a chaotic codebase.

A spec answers the question what. It is a durable contract: acceptance criteria, interface definitions, edge cases. It lives in version control alongside the code, changes rarely (only when requirements change), and is written for humans and agents alike to reference indefinitely. The spec is the source of truth about intent.

A plan answers the question how. It is a transient execution guide: ordered tasks, files to touch, code steps, commit points. It lives for the duration of one implementation session (or one sprint). Once the feature is merged, the plan is either archived or deleted — it has done its job. The plan is the source of truth about sequence.

The practical consequence: never modify the spec to satisfy a plan. If your plan conflicts with the spec, the plan is wrong. Replan. Never edit the spec mid-session unless the requirements themselves have changed (a rare, deliberate decision requiring stakeholder sign-off).

7.3 Anatomy of a good plan file

A plan file is a Markdown document (typically PLAN.md or specs/<feature>/plan.md) with a predictable structure. The superpowers:writing-plans skill produces this format automatically; the checklist below tells you what to look for when reviewing a plan the agent drafted.

Good plans share five structural properties:

  1. Numbered tasks — each task is a discrete unit of work with a single, verifiable outcome. If a task can't be described in one sentence, split it.
  2. Files-touched per task — every task names the files it will create, modify, or delete. This prevents surprise scope creep and makes review tractable.
  3. Code or command blocks within each task — the agent should not need to invent the approach mid-execution. Key commands, function signatures, or scaffolding snippets live inside the task so the agent stays on the planned path.
  4. Commit cadence — each task (or logical group of tasks) ends with a git commit. Atomic commits mean atomic rollback. Never let the agent execute more than one logical change before committing.
  5. Verification step — every task ends with a check: run the tests, grep for the expected output, or confirm the file exists. The agent should not mark a task complete without running its own verification.

7.5 Plan files as artifacts — committable, reviewable

A plan that exists only in conversation history has two problems: it disappears when the session ends, and it can't be reviewed by a teammate. Treating your plan as a committed artifact — a Markdown file in the repo — solves both.

Three benefits of committing your plan file:

  1. Reviewability — a PR containing PLAN.md alongside the spec lets a reviewer verify that the planned approach actually satisfies the spec criteria before a single line of implementation is written. This is the cheapest code review possible.
  2. Resumability — if you close the session mid-execution, the next session starts with: "Read PLAN.md and continue from Task N." No context reconstruction. No guessing what was done.
  3. Auditability — the git log records when the plan changed and why. If a post-mortem asks "did we have a plan for this?", the answer is in the history.

Typical file paths: PLAN.md at repo root for small features; specs/<feature>/plan.md alongside the spec for larger work; .claude/PLAN.md for plans that are agent-internal and shouldn't appear in the main repo tree.

Commit message convention: plan(<feature>): draft execution plan. This makes the plan easy to find in git log --oneline without grep.

7.6 Reviewing your agent's plan before it acts

Whether the plan comes from Claude plan mode, Kilo Architect, or the superpowers:writing-plans skill, you should review it before execution begins. A five-point check catches the most common failure modes:

  1. Right files? Every task names the files it will touch. Verify each file actually exists (for modifications) or makes sense to create at that path (for new files). Watch for files that are never mentioned — a plan that modifies cli.py but never touches the corresponding test file is almost certainly incomplete.
  2. Right order? Task N should not depend on something that Task N+2 creates. Read the dependency chain forward: if step 3 imports a module that step 5 creates, the plan will fail at step 3. The agent can get this wrong.
  3. Complete code in steps? Key function signatures, command invocations, and config snippets should appear in the task body — not be delegated to the agent's judgment at execution time. Vague instructions like "implement the parser" are plans waiting to go wrong. Specific instructions like "implement parse_git_log(path: str) -> list[Commit] in parser.py" are plans that execute predictably.
  4. No placeholders? Scan for TODO, ..., <fill in>, as appropriate. Placeholders in a plan become agent hallucinations during execution. Fill them in now or mark the task as requiring human input before the agent reaches it.
  5. Verification steps? Every task should have a concrete check: a test command to run, an output to grep for, a file to confirm exists. "Verify the feature works" is not a verification step. "Run pytest tests/test_parser.py -v and confirm all 4 tests pass" is.

The five-point check takes two to five minutes. It reliably prevents sessions that go sideways at step 3 and require a full replan. Pay the two minutes.

7.7 Mid-plan replanning when reality changes

Even a well-reviewed plan will sometimes collide with reality. The codebase was in a different state than expected. A dependency has a breaking API change. The chosen approach reveals a design flaw that wasn't visible from the spec. When this happens, you have two options — amend or abandon — and the choice depends on how far the collision propagates.

Amend when the reality change is local: the current task and at most one successor need to change, but the overall structure and commit plan remain valid. Update the affected tasks in the plan file, commit the updated plan with a message like plan(gitlog-report): amend task 3 — use argparse subcommands, then continue. The agent re-reads the updated plan.

Abandon and replan when the collision is structural: the approach chosen in the plan cannot satisfy the spec without touching more than two or three tasks, or the planned file structure is wrong. Stop execution, reset to the last clean commit, write a new plan, review it, then re-execute. Sunk cost reasoning ("we're already 60% done") is the enemy here. A bad 60% is more expensive to fix than a clean restart.

Signs you need a full replan:

  • The agent has started improvising — adding files not in the plan, skipping tasks, or reordering steps without telling you.
  • The current task has grown past its planned scope and is pulling in two or three others.
  • The git diff is much larger than expected for the current task.
  • A test introduced in an earlier task is now failing because of the current task's changes (integration conflict).

When in doubt, git diff HEAD~1 and count the files changed. If it's more than the plan said, you're already off-plan.

7.8 Plan templates and patterns

Most plans fall into one of four structural patterns. Recognising the pattern lets you get to a draft plan faster — either by prompting the agent with the pattern name, or by instantiating the template yourself.

Pattern Typical task sequence Watch for
Bug fix Reproduce → write failing test → fix → verify → commit Fix scope creep — fix only the bug, not the surrounding code
Feature add Scaffold → types/interfaces → core logic → CLI/API surface → tests → docs → commit Tests written after logic (TDD inverts this — see Ch 8)
Refactor Characterise tests → extract → move → update callers → verify → commit No behaviour change — any test failure is a bug in the refactor
Migration Shim old API → introduce new → migrate callers one-by-one → remove shim → verify → commit Never remove the shim until all callers are migrated

7.9 When to skip the plan (yes, sometimes)

Planning has a real cost: it takes time, it requires a spec to exist first, and it can feel like bureaucratic overhead on changes that are obviously small. The rule is: plan when the agent could go wrong; skip when it can't.

Safe to skip: a single-file typo or doc fix; renaming a variable with a find-and-replace; adding one line to a config file; trivially mechanical changes where the diff will obviously be correct. For these, just give the agent a direct instruction and review the diff before committing.

Safe to skip (sometimes): exploratory or throwaway work where you're not committing the output — prototyping an approach, generating a draft to read and discard, investigating a bug by trial and error. Plans impose commit structure; explorations don't benefit from that structure.

Not safe to skip: any change that touches more than two files; any change that involves a new abstraction or interface; any change where a wrong approach would require undoing more than 20 lines; any change that a teammate will review. For these, the two-minute plan review (7.6) is not overhead — it is the review.

The test: if the agent goes wrong, how long does recovery take? If the answer is more than five minutes, write a plan.

7.10 Plans across sessions — handoff and resume

Agentic sessions are bounded by context windows, working hours, and attention. A feature that takes four hours of elapsed time will probably span multiple sessions. The plan file is the mechanism that makes multi-session work coherent.

Handoff protocol: before closing a session mid-plan, the agent should update the plan file to mark completed tasks (e.g., prefix with [x]) and annotate the current task with a "stopped here" note including the last commit SHA. Commit this updated plan file. The commit message: plan(gitlog-report): checkpoint after task 3 — resume at task 4.

Resume protocol: open a new session, inject the spec and the updated plan file at the start of the context. Prompt: "Read PLAN.md. Tasks 1–3 are complete (see commit abc1234). Continue from Task 4." The agent reconstructs its working state from the plan + git log, not from conversation history. This is reliable across model updates, team members, and days-long gaps.

Team handoff: if a different engineer (or agent) picks up mid-plan, the same protocol applies. The plan file encodes intent; the git log encodes what was done; together they are a complete handoff document. No "what was I doing?" conversation needed.

The superpowers:executing-plans skill handles checkpoint and resume automatically when invoked with --resume. For manual workflows, the pattern above is reliable and requires no tooling beyond git.

8. Test-Driven Development with Agents

What you'll learn: why TDD becomes more important (not less) with agents, how the red-green-refactor cycle works as a control rod, the test types that survive agent edits, and how to write the gitlog-report tests before the implementation.

8.1 TDD with agents — does it still make sense? (yes, more than ever)

A common reaction to AI-assisted coding is: "The agent writes code so fast, do I really need to slow down with tests?" The answer is the opposite of what that reaction implies. TDD matters more with agents, not less. Here is why.

When you write code by hand you have a mental model of what the code does — you can feel when something is off. Agents don't have that sensory feedback loop. They generate code that looks convincing, compiles, and passes a cursory read. Without a failing test to refute them, they can claim "done" while the behaviour is still wrong — and they will sound confident doing it.

Tests are the only objective signal an agent can't fake. They either pass or they don't. When you give an agent a failing test and the instruction "make this pass without modifying the test," you have created an unambiguous success criterion. The agent iterates against that criterion. Without it, the agent optimises for your approval, which is a much noisier signal.

Three concrete problems TDD prevents in agentic work:

  • Silent regressions: Agent edits file A to fix a bug; test suite immediately tells you file B broke. Without tests you discover this at demo time.
  • Scope creep by accident: Agents occasionally rewrite more than you asked for. Tests catch when "fixing" one function altered the contract of another.
  • Confident wrong answers: Agents produce fluent, plausible outputs. Tests are the blunt instrument that says "no, the output was wrong" regardless of how fluent it sounded.

The discipline is: before you ask the agent to implement anything, you — or the agent under your direction — must write a failing test that encodes the acceptance criterion. The test is a compressed, executable version of the spec (see Ch 6). Implementation is the activity of making it pass.

8.2 Red → green → refactor as a control rod

The classic TDD cycle is red → green → refactor. With agents this cycle becomes a control rod — the mechanism that prevents the system from going critical.

🔴
RED
Write a failing test.
Run it. Confirm red.
You own this step.
→
🟢
GREEN
Tell agent: make this
test pass; don't touch
the test file.
→
🔵
REFACTOR
Agent cleans up.
Suite stays green.

How each step works with an agent:

Red: You write (or review) the failing test. This is a human responsibility. The test encodes your interpretation of the spec. If the agent writes the test for you without you verifying it against the spec, you risk the agent testing the wrong thing — and making it pass — which produces false confidence. At minimum, you must read and approve every test that enters the suite.

Green: Hand the failing test to the agent with a constrained prompt: "Make test_date_filter pass. Do not modify tests/test_gitlog.py. Show me the diff before writing it." The agent iterates. You watch the test output. Green means done — nothing more.

Refactor: Once green, the agent may refactor for clarity, performance, or structure. Your job here is to confirm the suite stays green after each refactor step. Never let the agent refactor on a red suite — that way lies a codebase where nothing works and no one knows why.

The control-rod metaphor is apt: the test suite absorbs energy from the agent's generative capacity and releases it in controlled, verifiable increments. Remove the tests (or let the agent update them freely) and the reaction goes uncontrolled.

8.3 Writing the failing test first — yourself, or with the agent

The gold standard is you write the test. You have read the spec (Ch 6), you understand the acceptance criteria, and you translate one criterion into one test function. The test is small, has a single assertion, and has a name that reads like a sentence: test_date_filter_excludes_commits_before_start_date.

The silver standard is you ask the agent to draft the test, then you verify it against the spec. Ask: "Read specs/gitlog-report/spec.md. Write failing pytest tests for the acceptance criteria in §3. Do not write any implementation. Return only the test file." Then read every test against the spec line by line. Delete any test that is not traceable to a specific acceptance criterion.

The "test what the spec says" rule (see Ch 6): a test that does not correspond to a named acceptance criterion is speculative. Speculative tests often encode the agent's assumptions, not yours. They pass when the agent writes implementation code that satisfies its own assumptions — creating a closed loop that excludes your intent entirely.

Checklist before adding any test:

  • Can I point to the exact line in the spec this test covers?
  • Does the test name match the acceptance criterion in plain language?
  • Does the test fail right now (against no implementation or a stub)?
  • Does the test have exactly one reason to fail?

If any answer is "no" or "I'm not sure," revise the test before adding it to the suite.

8.4 The "stop until green" discipline

This is a simple rule with profound consequences: do not move to the next task while any test in the suite is red.

Agents will routinely try to move on. The pattern looks like: "Test X is failing but that's because we haven't implemented feature Y yet — let me implement Y first and come back to X." This is almost always wrong. A failing test means the current task is incomplete. Moving on builds a stack of incomplete tasks that interact in ways that become progressively harder to untangle.

The correct response to a red test is:

  1. Stop. Do not write new features.
  2. Understand why the test is red. Read the error output literally.
  3. If the test is wrong (tests the wrong thing), fix the test and document why.
  4. If the implementation is wrong, fix the implementation.
  5. Run the full suite. Confirm all-green before proceeding.

Applied to agents: when you see an agent producing output and your test runner shows red, interrupt. Paste the test failure into the agent's context. Ask: "This test is still failing. Do not add new code. Fix only what is needed to make this test pass." The constraint "do not add new code" prevents the agent from burying the failure under additional complexity.

The "stop until green" discipline also applies to refactoring: never ask an agent to refactor code while tests are red. A red-plus-refactor session produces a diff where bug and cleanup are entangled, making review and bisection nearly impossible.

8.5 Golden tests — fixed, hand-curated truth

A golden test is a test with a hand-curated, fixed input and a hand-verified, fixed expected output. No generated fixtures. No dynamic comparisons. The expected value is typed in by a human who checked it against the spec and confirmed it is correct.

Golden tests are the most durable test type in an agentic codebase. Because both input and expected output are fixed strings (or structures), no agent refactor can accidentally make them pass on wrong output. If the output changes — for any reason — the test fails.

Example for gitlog-report (two authors, three commits):

GOLDEN_GIT_LOG = """
abc1234 Alice 2024-01-15 Add parser module
def5678 Bob   2024-01-16 Fix edge case in parser
ghi9012 Alice 2024-01-17 Add CLI entry point
"""

GOLDEN_EXPECTED = {
    "Alice": {"commit_count": 2, "files_changed": 0, "insertions": 0, "deletions": 0},
    "Bob":   {"commit_count": 1, "files_changed": 0, "insertions": 0, "deletions": 0},
}

def test_golden_multi_author():
    result = parse_gitlog(GOLDEN_GIT_LOG)
    assert result == GOLDEN_EXPECTED

Rules for golden tests:

  • The expected value is always a literal — never computed at test time.
  • When the expected output legitimately changes (because a requirement changed), update the golden value manually and commit with a message explaining why.
  • Never let an agent update a golden value without your explicit review. Treat any agent-proposed change to a golden value as a requirement change, not a test fix.

Golden tests are especially powerful for parsing, formatting, and report-generation tasks — exactly the kind of work gitlog-report does.

8.6 Snapshot tests and their dangers with agents

Snapshot tests (as offered by Jest, pytest-snapshot, and similar tools) automatically capture the output of a function and save it as a file. On subsequent runs, the test compares current output to the saved snapshot and fails only if they differ. When they differ, you run a "snapshot update" command and the new output becomes the new truth.

This convenience is a trap in agentic development. Agents will happily update snapshots to match wrong output. The pattern is: agent introduces a regression → test fails → agent runs snapshot update → test passes → agent reports success → you merge broken code.

The snapshot update command is the problem. It inverts the relationship between test and truth: instead of the expected output being fixed and the implementation being wrong, the expected output becomes wrong and the test silently accepts it.

How to treat snapshot tests in an agentic codebase:

  • Flag snapshot update as a reviewed action. Any commit that touches a __snapshots__ directory or .snap file must be reviewed by a human who verifies the new snapshot is correct.
  • Prefer golden tests (§8.5) for any output that can be hand-curated.
  • If you use snapshots, add a CI lint rule that fails if snapshot files are modified without a corresponding label/tag indicating human review.
  • Never run --updateSnapshot (or equivalent) in an automated agent loop. That flag must require explicit human invocation.

Snapshots are not inherently bad — they catch unexpected changes. They are bad when the mechanism for accepting changes is automated or undiscriminated. In agentic contexts, assume the agent will find and use the update path unless you explicitly prevent it.

8.7 Anti-mocking discipline — integration over isolation

The classic argument for mocks is speed and isolation: unit tests should not touch the network, the filesystem, or the database. This is sound advice for human-written tests operating in a CI environment with shared resources. It is partially wrong for agentic codebases.

The problem with mocks in agent-written tests is that agents mock the thing they just wrote. If the agent writes GitLogParser and then writes a test for it using a mock of GitLogParser, the test is testing the mock, not the parser. It passes trivially. The real parser can be completely broken.

The anti-mocking discipline: prefer integration tests against real dependencies wherever those dependencies are cheap to run locally.

  • Use a real temporary directory instead of mocking the filesystem.
  • Use a real in-memory SQLite database instead of mocking your ORM.
  • Use a real subprocess call to git log on a temp repo instead of mocking the git output.
  • Use real HTTP fixtures (recorded once, replayed) instead of mocking requests.

Integration tests are slower but they test the actual contract. An agent that breaks the real git log interaction will be caught by an integration test and will not be caught by a mock-based unit test.

The exceptions: external services with rate limits, expensive third-party APIs, non-deterministic services. For these, record real responses once (using a tool like vcrpy or msw) and replay them. This is fundamentally different from hand-writing mocks — the recorded response is real truth, not agent-constructed fiction.

8.8 Eval loops — tests for the prompt, not just the code

When your system includes an LLM call — a prompt that asks the model to extract, classify, summarise, or decide — the code around it may be correct while the prompt itself is producing wrong outputs. Unit tests on the code will not catch this. You need an eval loop: a test that runs the actual prompt against a fixed set of inputs and checks the outputs against fixed expected values.

An eval loop has the same structure as a golden test (§8.5), except the "function under test" is a prompt-plus-model call rather than a pure function:

EVAL_CASES = [
    {
        "input": "Extract the author name from: 'abc123 Alice 2024-01-15 Fix bug'",
        "expected": "Alice",
    },
    {
        "input": "Extract the author name from: 'def456 Bob Smith 2024-02-01 Add feature'",
        "expected": "Bob Smith",
    },
]

def test_author_extraction_eval():
    for case in EVAL_CASES:
        result = call_llm(AUTHOR_EXTRACTION_PROMPT, case["input"])
        assert result.strip() == case["expected"], (
            f"Prompt produced wrong output for input: {case['input']!r}"
        )

Eval loops catch:

  • Prompt regressions when the prompt template is edited.
  • Model drift when you upgrade to a new model version.
  • Edge cases the prompt handles inconsistently (multi-word names, special characters, empty input).

Eval loops are expensive (they make real LLM calls) so run them on a slow path: pre-commit on prompt file changes, or nightly CI, not on every unit test run. The key is that they exist and are non-negotiable gates before shipping a prompt change.

For agents writing prompt-heavy features, the eval loop is the spec equivalent for the prompt layer. Require it before any prompt change is merged.

8.9 Coverage as a verification signal

Line coverage tells you which lines of code were executed by at least one test. It is a useful signal but an unreliable metric for quality. The failure mode is coverage theatre: 100% line coverage with tests that make no meaningful assertions. Every line runs; nothing is verified.

Coverage is a necessary condition for confidence, not a sufficient one. A line with 0% coverage is definitely untested. A line with 100% coverage might still be untested in any meaningful sense.

How to use coverage correctly in an agentic codebase:

  • Use coverage to find gaps, not to prove quality. A module at 40% coverage has obvious gaps to address. A module at 100% coverage needs its tests read — not celebrated.
  • Use branch coverage, not just line coverage. Branch coverage catches untested conditional paths. Agents often write code with multiple branches and test only the happy path.
  • Set a floor, not a ceiling. Require, say, 80% branch coverage as a CI gate. Don't optimise for 100% — that incentivises coverage theatre.
  • Mutation testing is the honest metric. Tools like mutmut (Python) or Stryker (JS) introduce small bugs and check whether any test fails. If 100% of mutations survive (no test catches any injected bug), your coverage is theatre regardless of the number.

For agents: never let an agent report "coverage is 95%" as evidence of completeness. Ask instead: "How many of the acceptance criteria from the spec are covered by assertions in the test suite?" That is the number that matters.

8.10 When the agent writes bad tests (and how to spot it)

Agents write bad tests. Not from malice — from the same pattern-matching that makes them write good-looking code: they optimise for tests that pass, not for tests that would catch real bugs. Here are the signs to look for:

Sign What it looks like Why it's bad
Tautological test assert result == result or assert len(result) > 0 Always passes; tests nothing
Tests the mock Mock returns X; test asserts X; real function never called Implementation can be broken; test will pass
Asserts implementation detail assert parser._internal_cache == {} Breaks on every refactor; tests structure not behaviour
No assertion Test calls function, captures result, ends without assert Passes even if function throws wrong output (some frameworks)
Happy-path only 10 tests, all with valid well-formed inputs Edge cases (empty input, malformed data) completely untested
Spec-untraceable test Test covers behaviour not in the spec Agent inventing requirements; may conflict with real spec
Soft assertion assert "Alice" in str(result) instead of exact match Passes even when result is malformed; hides bugs in structure

How to catch bad tests systematically:

  1. Run the test suite against a known-broken implementation. Introduce a deliberate bug (delete a function body, return a wrong value) and run the tests. Any test that still passes is either testing the wrong thing or is tautological.
  2. Read assertions literally. For every assert statement, ask: "What would make this assertion false?" If the answer is "almost nothing," the assertion is weak.
  3. Count the assertions per test. A test with zero assertions is always a bug. A test with one assertion that asserts a trivially true condition is effectively zero.
  4. Run mutation testing periodically (§8.9). Any surviving mutant is a test gap.

9. Debugging with Agents

What you'll learn: the systematic debugging loop with an agent, why agents fix bugs wrong without it, evidence patterns, and how to debug the gitlog-report off-by-one bug step by step.

9.1 The systematic debugging loop

Debugging with an agent without a framework is a gamble. The agent will pattern-match to the most plausible-looking cause, propose a fix, and report success — even when the root cause is untouched. To prevent this, Claude Code provides the superpowers:systematic-debugging skill, which enforces a 5-stage loop before any fix is written.

The 5-stage cycle:

  1. Reproduce — confirm the bug is deterministically triggerable. No reproduction, no debugging.
  2. Isolate — narrow from "the system is broken" to "this specific input to this specific function produces this specific wrong output."
  3. Root cause — identify the exact line, condition, or invariant violation that causes the wrong output. Not the symptom — the cause.
  4. Fix — apply the minimal change that corrects the root cause. Not the symptom.
  5. Verify — rerun the failing test (green), then rerun the entire suite (no regressions).

The skill enforces this order. You cannot skip to stage 4 (Fix) without the agent having produced evidence at stages 2 and 3. This constraint is deliberate: it prevents the most common agent failure mode — applying a patch that silences the symptom while leaving the root cause in place.

To invoke: in Claude Code, type /systematic-debugging (via the skill). Describe the bug. The agent will ask you to complete each stage before advancing. Resist the urge to skip ahead.

9.2 Reproduce → isolate → root cause → fix → verify

Reproduce reliably first. If you cannot reproduce the bug on demand, your fix is a hope. A fix applied to an unreproducible bug may appear to work — the bug simply didn't trigger — and will resurface later under conditions you didn't anticipate.

The reproduction recipe pattern: before touching any code, write down (or have the agent write down) the exact steps that reliably produce the failure:

# Reproduction recipe — write this before any fix attempt
# Bug: date_filter includes boundary commit when it should not
# Preconditions: gitlog_report/parser.py at commit abc1234
# Steps:
#   1. Create tmp git repo with commits on 2024-01-05, 2024-01-10, 2024-01-15
#   2. Run parse_gitlog(repo, start_date="2024-01-10", end_date=None)
#   3. Assert result["Alice"]["commit_count"] == 2
# Expected: 2 (commits on 2024-01-10 and 2024-01-15)
# Actual:   1 (commit on 2024-01-10 excluded)
# Confirmed on: Python 3.11, pytest 7.4

With the recipe written, you have pinned the bug in space and time. Any fix that doesn't make the recipe produce the expected result hasn't fixed the bug.

The stages are not decorative. Isolate means producing a minimal failing case — the smallest input that still triggers the bug. Agents will skip this and jump to the full system. Don't let them. A minimal case eliminates false suspects and makes the root cause obvious. Root cause means reading the actual code and stating a falsifiable hypothesis: "The bug is on line 47 of parser.py — the condition uses > instead of >=." Verify means running the full suite, not just the test that was red. Fixes that introduce regressions are fixes that traded one bug for another.

9.3 Bugs the agent will fix wrong (and why)

Agents don't maliciously produce wrong fixes. They pattern-match to common resolutions and optimise for making the immediate test pass. Here are the recurring failure modes:

Bad fix type What it looks like Why it's wrong
Cargo-cult fix Copies a pattern from a similar file without understanding why Fix is coincidental; root cause is unchanged; bug re-emerges on next edge case
Surface-symptom patch Wraps the buggy function in a try/except or adds a special-case check for the known-bad input Root cause survives; next input that triggers it won't be caught by the special case
Test mutation Changes the assertion in the failing test to match the wrong output The test now passes, but the spec is violated; the bug is hidden behind a lying test
Over-generalisation Rewrites a 5-line function into a 40-line one to "handle all edge cases" Introduces new surface area; makes future bugs harder to isolate
Wrong layer fix Fixes the calling code instead of the function that produced the wrong value Every caller now needs the same fix; root cause is still in the shared function
Snapshot update Runs --updateSnapshot to "fix" the failing test Makes wrong output into the new expected value; the bug is now the spec (see §8.6)

The tell for all of these: the agent says "fixed" and the immediately-failing test goes green — but you haven't seen the agent read and reason about the function body. Push back: "Show me which line was wrong and why. Do not show me the diff yet."

9.4 Root cause vs patch — keeping the agent honest

A patch silences the symptom. A root cause fix corrects the invariant that was violated. The test may go green in both cases. Only one of them has actually fixed the bug.

The technique for forcing root cause work is the "why?" cascade. After the agent names a cause, ask "why?" until you reach an invariant — a property of the system that should always hold but was violated:

Agent: "The count is 1 instead of 2 because the boundary commit is excluded."
You:   "Why is it excluded?"
Agent: "Because the date comparison uses > instead of >=."
You:   "Why does it use > ?"
Agent: "The initial implementation assumed exclusive lower bound."
You:   "What is the correct invariant?"
Agent: "start_date is inclusive. Commits on start_date must be included."
You:   "That is the root cause. Now show me the minimal fix."

The cascade stops when the agent can state an invariant — a design decision that was either wrong or correctly specified but incorrectly implemented. Everything above that level in the cascade is symptom, not cause.

Signs you have a patch, not a fix: the fix adds a special case, wraps in a try/except, modifies the test, or is larger than 3 lines for a bug the cascade traced to a single operator. A root cause fix for an off-by-one is one character. If the agent's proposed diff is 30 lines, ask: "Is this the root cause fix or a workaround?"

9.5 Reading the agent's hypotheses critically

When you paste a bug into an agent, it will generate hypotheses. These are often plausible and frequently wrong. Reading them critically is a skill.

What to look for:

  • Evidence vs. assertion. "The bug is in parse_date" — did the agent read parse_date? Ask: "Show me the line in parse_date that supports this hypothesis." If the agent can't cite a specific line, it's guessing.
  • Confident tone on uncertain reasoning. Agents express hypotheses with the same fluency regardless of confidence. A confident-sounding hypothesis with no cited evidence is a signal to verify, not accept.
  • First hypothesis bias. Agents tend to anchor on their first hypothesis. If you push back once, they adjust. If you push back twice, they often return to the original hypothesis. This is a sign to run the experiment yourself: test the hypothesis by deliberate insertion of a print statement or assertion.
  • Hypothesis count. An agent that lists 5 possible causes for a single failing test is diffusing responsibility. Ask it to rank them by likelihood and provide evidence for the top one before moving on.

The rule: treat agent hypotheses as test candidates, not conclusions. Each hypothesis is a prediction: "if this is the cause, then changing X should make the test pass." Test the prediction. If it fails, the hypothesis was wrong — regardless of how confident the agent sounded.

9.6 Bisecting with the agent's help

When you don't know when a bug was introduced, git bisect is the most reliable tool. Agents can help run and interpret it, but you must stay in control of the process.

git bisect workflow with an agent:

git bisect start
git bisect bad                        # current commit is broken
git bisect good <known-good-sha>       # last commit known to pass the test
# git checks out the midpoint commit
# Ask agent: "Run pytest tests/test_gitlog.py::test_date_filter_excludes_commits_before_start_date"
# If PASS: git bisect good
# If FAIL: git bisect bad
# Repeat until git bisect prints the first-bad commit

The agent's role is: run the test at each bisect step, report pass/fail, and tell you which git bisect good/bad to issue. Your role is to issue the command and read the final output. Do not let the agent issue git bisect reset or skip steps — it may miss the true first-bad commit.

Binary search of inputs is bisect for data, not commits. When a function fails on large input but passes on small input, cut the input in half, run the test, and recurse into the failing half. Agents can help generate the halved inputs and run the tests, but you must frame the search correctly: "Does the function fail on the first half or the second half of this list?"

Narrowing checklist:

  • Start with the full failing case confirmed.
  • Remove half the variables. Does it still fail?
  • Keep halving until you cannot remove anything without the bug disappearing. What remains is the minimal reproducer.
  • Paste the minimal reproducer back to the agent: "This is the smallest input that produces the bug. Now find the root cause."

9.7 Logs, traces, stack frames — feeding evidence

An agent debugging without evidence is reasoning in a vacuum. The quality of the debug session is directly proportional to the quality of evidence you feed it. Here is what to provide and how.

What to paste verbatim:

  • The full pytest failure output, including the assertion error and the traceback. Do not truncate.
  • The relevant stack frame — the line in your code (not a library) where execution was when the assertion failed.
  • The actual vs. expected values from the assertion message (if present).

What to summarise:

  • Long log files — paste only the lines around the error (±10 lines of context).
  • Repeated identical stack frames — paste one instance and note "repeated N times."
  • Long configuration files — paste only the section relevant to the failing behaviour.

What to leave out:

  • Library internals that are not part of your codebase (e.g., deep pytest or stdlib frames).
  • Passing test output — only the failures are evidence of the bug.
  • Unrelated error messages from previous sessions.

Concrete example — good evidence paste:

FAILED tests/test_gitlog.py::test_date_filter_excludes_commits_before_start_date

AssertionError: Expected 2 commits (boundary + after), got 1.
If this is 1, the filter is using strict > instead of >= on the boundary date.
assert result["Alice"]["commit_count"] == 2
       → result["Alice"]["commit_count"] is 1

Traceback (most recent call last):
  File "tests/test_gitlog.py", line 58, in test_date_filter_excludes_commits_before_start_date
    assert result["Alice"]["commit_count"] == 2, (...)
AssertionError

This evidence tells the agent: what test failed, what the assertion was, what the actual vs. expected values were, and which line in your code triggered it. That is sufficient. More is noise.

9.8 When to step in yourself

Agents get stuck. The diagnostic signal is: 3 iterations with no forward progress. If the agent has proposed 3 different fixes, all of which still fail the same test with the same error, the agent is in a pattern-matching loop with insufficient context. Stepping in is not a failure — it is the correct response.

Signs to stop the agent and intervene:

  • The same test fails with the same error after 3 agent iterations.
  • The agent's proposed diffs are getting larger with each iteration (scope creep under pressure).
  • The agent starts suggesting changes to the test file to "resolve the conflict."
  • The agent reports a fix as successful but doesn't show the passing test output.
  • The agent introduces a new failure while fixing the original one, and then focuses on the new failure instead.

What to do when you step in:

  1. Stop the agent: "Stop. Do not produce any more code."
  2. Read the function body yourself. Not the diff — the function as it currently exists.
  3. Trace the execution manually: follow the inputs through the code path until you find where the output diverges from what you expect.
  4. Identify the exact line. State it to the agent: "The bug is on line 47. The condition is commit_date > start_date. It should be commit_date >= start_date. Make only that change."
  5. Verify the result yourself.

The agent is most useful for the exploration and verification phases. The isolation step — reading code and following the execution path — is sometimes faster to do yourself than to explain to an agent in enough detail that it can do it correctly.

9.9 Debugging the agent (not the code) — when prompts go bad

Sometimes the bug is not in the code. The bug is in the prompt — the instructions you gave the agent that caused it to generate the wrong code in the first place.

Signs that the prompt is the bug:

  • The agent generates subtly wrong code every time you ask for the same feature, even after multiple corrections.
  • The agent misunderstands a key term you use (e.g., you say "date filter" and the agent consistently interprets it as exclusive lower bound).
  • The agent adds code you didn't ask for, repeatedly.
  • Fixes to the code keep reverting to the buggy pattern in subsequent sessions.

The debugging process for a bad prompt mirrors the systematic loop for code bugs:

  1. Reproduce: Identify the prompt fragment that consistently produces the wrong output.
  2. Isolate: Remove context from the prompt until you find the minimal fragment that triggers the wrong behaviour.
  3. Root cause: Is the term ambiguous? Is the constraint missing? Is the context contradicting itself?
  4. Fix: Rewrite the ambiguous fragment. Add the missing constraint. Remove the contradiction.
  5. Verify: Run the corrected prompt against the same inputs that produced the bug. Confirm the output is now correct.

Common prompt bugs: under-specified acceptance criteria (the agent fills gaps with assumptions), absent negative constraints ("do not modify the test file" missing), and ambiguous terminology that the agent resolves differently in different sessions. The fix is always the same: make the constraint explicit, not implicit.

Claude Code has no built-in /debug slash command. Do not look for one — it does not exist. The correct path is the superpowers:systematic-debugging skill. Invoke it via the Skill tool or by typing the skill name in a Claude Code session. The skill enforces the 5-stage cycle (§9.1), requires evidence at each stage, and prevents the agent from advancing to Fix without a stated root cause. 10. Safety, Review & Verification

What you'll learn: the three review layers, when to use which tool (code review, /security-review, /ultrareview), the verification-before-completion discipline, and how to spot agent hallucinations in code.

10.1 The three review layers — pre-merge, code, security

Every non-trivial change should pass through three distinct review layers before merge. Each layer has a different scope, different tooling, and catches a different class of defect. Treating them as one combined "review" means each one is done shallowly — you need the distinctions.

Layer 1 · Pre-merge (you)

Who: the author, before anyone else sees it.

Catches: obvious blunders, missing tests, incomplete diffs, left-in debug logs, unintended scope creep.

How: read your own diff. git diff --stat and git diff HEAD. Does the changed surface match the ticket?

Layer 2 · Code review (agent or peer)

Who: an agent (via /code-review) or a human reviewer.

Catches: logic errors, missing edge cases, poor naming, architectural drift, test quality.

How: structured prompt or skill. The reviewer reads intent + implementation and flags mismatches.

Layer 3 · Security review (specialist)

Who: /security-review or a security engineer for high-stakes code.

Catches: injection vectors, secret leaks, insecure defaults, dangerous API usage.

How: purpose-built scan focused on attack surface, not correctness. Runs independently of code review.

The most common mistake is collapsing all three into a single "does this look good?" pass. Layer 2 reviewers are not thinking about injection vectors; Layer 3 reviewers are not thinking about naming conventions. Keep the scopes clean.

10.2 Code review with agents — beyond rubber-stamping

An agent doing code review is not automatically trustworthy. Without guidance, the agent will trend toward politeness: it will notice obvious issues but hedge, praise structure before raising concerns, and stop after two or three findings even when more exist. The default output is a rubber-stamp with footnotes.

To get real code review, you need a skeptic stance prompt. The difference:

# Rubber-stamp prompt (don't use)
"Review this code for me."

# Skeptic stance prompt (use this)
"You are a senior engineer who is skeptical of AI-generated code.
Your job is to find bugs, not confirm correctness.
List every place this code could fail silently, produce wrong output,
or behave differently under concurrent load.
Be terse. Be ruthless. Do not praise anything.
Rate each finding: BLOCKER | MAJOR | MINOR."

Reviewing the review (recursion). The agent's review is itself an artifact that can contain errors. Agents hallucinate findings — flagging non-existent bugs, citing APIs incorrectly, or misreading control flow. Before acting on a finding, verify it manually: read the actual line the agent cited. Does the code actually do what the agent says it does? If the finding cites a function — does that function exist and does it have that signature?

The skeptic stance toward the reviewer: treat every finding as a hypothesis, not a fact. Confirm before you fix.

10.3 /security-review deep dive

The /security-review skill in Claude Code runs a security-focused analysis pass on your codebase or diff. It is distinct from code review: it does not comment on architecture or naming — it looks for attack surface.

What it scans:

  • Injection patterns — SQL injection, shell injection (subprocess with untrusted input), template injection, path traversal.
  • Secret leakage — hardcoded credentials, tokens in source, secrets in log statements.
  • Insecure defaults — TLS disabled, signature verification skipped, debug flags left on.
  • Dangerous API usage — eval(), pickle.loads() on untrusted data, os.system() with interpolated input.
  • OWASP-adjacent patterns — missing authentication checks, direct object references, missing rate limiting.

What it misses (calibration required):

  • Business logic flaws — "user A can see user B's data" depends on your domain model, not the code shape. The scanner cannot reason about intent.
  • Auth boundary correctness — it can spot a missing @require_auth decorator but cannot verify your auth model is sound end-to-end.
  • Second-order effects — data flows across service boundaries, timing attacks, cache poisoning.
  • Configuration-layer vulnerabilities — IAM policies, firewall rules, Kubernetes RBAC. These live outside the code the scanner reads.

Run /security-review before every merge to a main branch. It runs locally, in-terminal, synchronously. Results appear inline.

Critical: /ultrareview is cloud-based, paid, and asynchronous

  • Metered and paid: each run consumes tokens across multiple agents in parallel. It is not free. Reserve it for high-value changes (pre-production releases, security-sensitive refactors, complex feature additions).

10.5 Verification-before-completion — running the thing you built

The most common error in AI-assisted development is claiming done without running the thing. An agent can generate code that looks complete, passes a mental model check, and even passes static analysis — and still fail at runtime in the first smoke test. "I've implemented the feature" is a claim about behaviour. Behaviour is only observable by running the code.

The superpowers:verification-before-completion skill encodes this as a non-negotiable gate. The pattern it enforces:

# Verification-before-completion pattern
# Do NOT claim done until ALL four steps pass:

1. BUILD   — the project compiles / the imports resolve / no syntax errors
             (run: python -c "import mymodule" or npm run build)

2. RUN     — the program starts and reaches its main loop without crashing
             (run: python main.py --help, or start the server, or execute the CLI)

3. SMOKE   — a minimal end-to-end path through the new feature produces
             the expected output with a real (or realistic) input
             (not mocked — actual I/O through the new code path)

4. CLAIM   — only after 1, 2, 3 pass can you write "done" or "implemented"

Invoke the skill with /verification-before-completion in Claude Code. It will ask you to produce evidence for each stage. The agent cannot skip stages. This discipline is especially important after refactoring — it's easy to rename a function, forget one call site, and produce code that passes code review but crashes on first use.

The evidence rule: every "done" claim must be backed by at least one piece of concrete evidence — a test run output, a screenshot of the feature working, a copy of the smoke test output. "It should work" is not evidence.

10.6 Hallucinations in code — APIs that don't exist, imports that fail

Code hallucination is qualitatively different from text hallucination. In a sentence, a hallucinated fact is detectable by cross-referencing. In code, a hallucinated API looks syntactically identical to a real one. The code is well-formed, passes linting, and reads naturally — until it is run.

Common hallucination patterns:

  • Made-up library functions: pandas.read_sql_smart(), requests.get_cached(), os.path.resolve_relative() — functions that sound like they should exist but don't.
  • Wrong method signatures: calling a real function with arguments it doesn't accept, or in an order it doesn't expect.
  • Invented module paths: from django.contrib.auth.utils import check_token where check_token doesn't exist at that path.
  • Version mismatch: a real API that existed in an older version and was removed or renamed — the agent's training data included it.

The Read-then-Edit verification pattern: before accepting any agent-generated code that uses an API you didn't write yourself, verify the API exists. The pattern:

# Read-then-Edit verification pattern
# Before: agent generates code using an API

# Step 1: READ — use the Read tool to check the actual source or docs
#   "Read the actual file at site-packages/requests/api.py and confirm
#    that get() accepts a `timeout` parameter and its default value."

# Step 2: CONFIRM — does the function/class/method exist at that path?
#   Does it accept the arguments the agent used?
#   Is it exported from the module the agent imported it from?

# Step 3: EDIT — only proceed with the generated code once confirmed.
#   If the API doesn't exist: ask the agent to find the correct one,
#   or use the real docs to substitute the correct call.

# Do NOT: assume "it looks plausible" means it works.
# Do NOT: run the code as the first verification step — read first.

For external libraries: use the WebFetch tool to pull the actual documentation page, not the agent's memory of it. The agent's training data has a cutoff; the library may have changed since then.

10.7 The "looks right vs is right" gap

Code can simultaneously satisfy all of the following and still be wrong:

  • Compiles without errors.
  • Passes a linter at zero warnings.
  • Passes a type checker (mypy, TypeScript, etc.).
  • Is syntactically and stylistically indistinguishable from correct code.
  • Passes a casual code review.

The gap between "looks right" and "is right" is where most AI-assisted bugs live. They don't look like bugs. They look like working code that has a subtle behavioural error — an off-by-one on an edge case, a missing await, a silent integer overflow, a dictionary lookup that returns None silently instead of raising.

The type-checks-pass, tests-fail case is the most dangerous variant: the type system confirms that types are consistent but cannot verify that the logic is correct. A function typed as (int, int) -> int that returns a * b instead of a + b passes every type check. Only a test that checks the actual output catches it.

This is why the verification discipline (§10.5) requires a smoke test, not just a build pass. And it's why the TDD discipline from Ch 8 is protective: if you write the test before the implementation, the test codifies what "right" means before "looks right" code can be accepted.

Practical heuristic: if a code change is more than 20 lines and has no corresponding test change, the "is right" question is unanswered. Don't merge it without asking why.

10.8 Receiving code review gracefully

Receiving code review — whether from an agent or a human — is a skill. The default response to negative feedback is defensive: discount the finding, reframe the code so the finding no longer applies, or implement a surface-level change that satisfies the letter of the review without addressing the concern. All of these responses make code worse.

The superpowers:receiving-code-review skill provides a structured framework for processing review findings. The core discipline:

  1. Assume the reviewer is right until proven otherwise. Disagreement is a signal that something is unclear — either the code is unclear, or the reviewer misread it. Both outcomes need resolution.
  2. Verify findings before implementing. Performative agreement — implementing a change because the reviewer flagged it, without understanding whether the finding is correct — is dangerous. You can introduce a new bug while "fixing" a non-existent one.
  3. Ask for clarification before dismissing. A finding you don't understand is not a finding you can safely ignore. "I don't see the problem here" is the start of a conversation, not the end of one.
  4. Distinguish BLOCKER from MINOR. Not all findings are equal. A BLOCKER (correctness bug, security hole) must be resolved before merge. A MINOR (naming preference, style suggestion) can be deferred or declined with explanation.

The receiving-code-review discipline applies equally to agent reviewers. Don't implement every suggestion the agent makes without reading the finding. Agents make incorrect review comments. Read the finding, check the code it references, and make your own judgment.

10.9 Self-review prompts — getting the agent to critique itself

Before requesting external review, you can get the agent to critique its own output. This catches a class of errors the agent is aware of but didn't surface during generation — it knows about edge cases it didn't handle, APIs it wasn't sure about, and assumptions it made.

High-value self-review prompts:

# Prompt 1: find a bug
"Find a bug in the code you just wrote.
Be specific: give the line number and the exact failure condition."

# Prompt 2: list failure modes
"List the ways this code could produce wrong output.
Enumerate silently wrong cases — cases where no exception is raised
but the result is incorrect."

# Prompt 3: find the unhandled inputs
"What inputs does this code not handle?
List at least three cases where the input is valid but the code
will produce an error or incorrect result."

# Prompt 4: find the assumption
"What assumption does this code make that the caller might violate?
State the assumption explicitly and suggest how to guard against it."

# Prompt 5: find the missing test
"What test case is missing from the test suite that, if it existed,
would fail right now?"

The key is specificity: vague prompts get vague responses. "Is there anything wrong with this?" elicits reassurance. "Find a bug" forces the agent to search. "What inputs does this not handle?" forces enumeration of failure modes rather than confirmation of success modes.

Run at least Prompt 2 and Prompt 3 on every non-trivial code generation before accepting the output.

10.10 Sign-off gates — what blocks a "done" claim

A "done" claim is a commitment. Before making it, the following gates must pass. This is not a suggestion — each gate catches a real class of defect that the previous gate does not catch.

Sign-off checklist

  • Build passes. npm run build / python -m compileall / go build exits clean. No import errors, no syntax errors.
  • Tests pass. Full test suite green. Not just the new tests — the full suite. No regressions.
  • Manual smoke. You or the agent ran a real end-to-end path through the new behaviour with actual input. Not mocked.
  • Security scan clean. /security-review run, findings reviewed. BLOCKERs resolved or explicitly accepted with documented rationale.
  • Code review complete. Findings reviewed. BLOCKERs and MAJORs resolved. MINORs triaged.
  • No TODOs in diff. git diff main | grep -i 'TODO\|FIXME\|HACK' is empty (or every hit is intentional and tracked).
  • Reviewer sign-off. A human (or an /ultrareview pass for high-stakes changes) has approved the change.

These gates are sequential, not parallel: if tests fail, the smoke test result is not meaningful (the code you smoked isn't the code that's shipping). If the build doesn't pass, the tests don't reflect reality.

11. Multi-Agent & Parallel Workflows

What you'll learn: when one agent isn't enough, how to dispatch parallel subagents without conflicts, worktree isolation, the agent-of-agents orchestrator pattern, and how to polish gitlog-report in parallel.

11.1 When one agent isn't enough

A single agent working sequentially has two fundamental limits: context window saturation and wall-clock time. When a task has genuinely independent sub-problems, forcing one agent through them sequentially wastes both.

Three signals that you need more than one agent:

  • Independent investigation. You need to research three unrelated APIs simultaneously. Each investigation has no dependency on the others. A single agent would context-switch, losing depth; parallel agents each work the full window on one problem.
  • Large context dilution. A 200-file codebase plus test suite plus documentation saturates the main session. Farming sub-problems to subagents preserves the orchestrator's context for integration work, not retrieval.
  • Specialized roles. One agent reads the spec, a second writes the implementation, a third reviews it. Each agent's prompt is tuned for one job. The reviewer agent receives no implementation bias — it read the spec first and forms its own expectations.

The cost of going parallel is coordination overhead: you need to decompose cleanly, manage worktrees or shared state explicitly, and integrate results. If the sub-problems are not truly independent, you pay coordination cost without the throughput benefit — worse than sequential. Rule: only parallelize at clean dependency boundaries.

11.2 Subagents in Claude Code — the Agent tool

Claude Code exposes an internal Agent tool that the model can call to spawn subagents within the same session. When the orchestrating agent issues multiple Agent tool calls in a single response, Claude Code dispatches them in parallel — each subagent gets its own context, its own tool access, and runs concurrently.

The Agent tool accepts a prompt parameter (what the subagent should do) and an optional description. The orchestrator receives each subagent's final output as a tool result and integrates them.

Subagent type identifiers. Claude Code also exposes named agent types that map to specialized behaviors. The exact identifiers and their casing are subject to Claude Code version changes — always verify against the current Claude Code documentation before scripting against them. At time of writing, commonly referenced identifiers include:

  • general-purpose — default; reads, writes, runs commands
  • code-reviewer — review-focused, no writes
  • Explore — read-only codebase exploration
  • Plan — spec analysis and decomposition, no execution

Note: Verify exact identifiers and casing against current Claude Code docs before use. These may differ between Claude Code versions.

In practice, most parallel work dispatches unnamed subagents via the Agent tool with a well-scoped prompt. Named types are useful when you want Claude Code to enforce role constraints (e.g., a review agent that cannot write files).

11.3 Dispatching parallel subagents — rules of thumb

The critical prerequisite: parallel dispatch is only safe when the subagents' work is genuinely independent. Two agents editing the same file simultaneously produce a merge conflict at best and silent data corruption at worst.

How dispatch works in Claude Code: When you issue a single message with multiple Agent tool calls (or the model decides to dispatch multiple agents in one turn), Claude Code runs them concurrently. Each subagent gets its own context window seeded with the prompt you provide. They do not share context — they cannot "see" each other's in-progress work.

Rules of thumb for parallel dispatch

  • One file per agent. Two agents must not write to the same file in the same dispatch batch. If they need to touch overlapping files, sequence them.
  • Independent output paths. Each agent writes to a different directory, branch, or worktree. The orchestrator integrates after all agents complete.
  • Front-load context in prompts. Each subagent starts with zero memory of prior conversation. Include all necessary context in the dispatch prompt — do not assume shared state.
  • Limit fanout. More than 4–5 parallel agents is rarely beneficial and raises coordination cost sharply. Prefer 2–3 well-scoped agents over 8 narrowly-scoped ones.
  • Explicit integration step. After subagents complete, the orchestrator reads all outputs and synthesizes. This step is not free — budget tokens and turns for it.

This parallelism is what happens in real-time when this guide is built: an orchestrator agent dispatches multiple subagents — one per chapter — in a single turn. Each agent writes its section independently. The orchestrator then integrates the outputs.

11.4 Worktrees for isolation — git worktree patterns

When parallel agents need to write code (not just read), shared file state is the primary failure mode. The solution is git worktrees: one checkout per agent, all pointing at the same underlying repo.

# Create three worktrees for three parallel agents
git worktree add ../gitlog-feat -b polish/json
git worktree add ../gitlog-tests -b polish/tests
git worktree add ../gitlog-docs -b polish/docs

Each agent is dispatched with an explicit working directory. Agent A works in ../gitlog-feat, Agent B in ../gitlog-tests, Agent C in ../gitlog-docs. No agent ever touches another's tree. When all three complete, you review each branch independently, then merge.

Lifecycle:

  1. Create worktrees before dispatching agents (git worktree add).
  2. Dispatch agents with their worktree path in the prompt.
  3. Agents commit to their branch independently.
  4. Orchestrator collects, reviews, and merges (or raises PRs).
  5. Clean up: git worktree remove ../gitlog-feat after merge.

The superpowers:using-git-worktrees skill automates this setup. It handles the worktree creation, branch naming, and teardown — invoke it before dispatching parallel agents on any non-trivial task to ensure clean isolation from the current workspace.

The /loop skill runs a prompt or slash command on a recurring interval, or lets the model self-pace between iterations. It is designed for polling external state — CI status, deploy health, rate-limited APIs — without you manually re-issuing the same command.

  • Polling a deploy pipeline until it completes or fails.
  • Watching a test suite for new failures during active development.
  • Monitoring an external API endpoint for a state change you're waiting on.

11.7 Agent-of-agents — the orchestrator pattern

The orchestrator pattern is the highest-leverage multi-agent structure: one parent agent decomposes a problem, dispatches subagents in parallel to work independent sub-problems, then integrates their outputs into a unified result.

Signature pattern:

  1. Decompose. Parent agent reads the task and identifies N independent sub-problems. Independence check: "Can sub-problem A be solved without knowing the output of sub-problem B?" If yes: parallel. If no: sequential.
  2. Dispatch. Parent agent issues N Agent tool calls in a single turn. Each subagent prompt includes: the sub-problem scope, all necessary context (file paths, relevant code, constraints), the output format expected, and what NOT to do (write to shared files, make network calls outside scope, etc.).
  3. Wait. Claude Code runs all N subagents concurrently. Parent agent is blocked until all complete.
  4. Integrate. Parent agent receives N results. It reconciles conflicts, fills gaps, resolves dependencies between sub-results, and produces the final artifact.

Orchestrator design principles

Orchestrator is the context holder. The orchestrator's session accumulates all sub-results. It must have enough context budget to receive and process N subagent outputs. If the sub-results are large, summarize in subagent prompts ("return a 200-word summary of your findings, not the full output").

Sub-problems must be expressible as self-contained prompts. If the decomposition requires inline real-time coordination between subagents (Agent A's output feeds Agent B's input), that is a sequential dependency, not parallel work.

Integration is work. Budget a full turn (sometimes several) for integration. The orchestrator reading 3–5 substantial subagent outputs and synthesizing them is not a no-op turn.

11.9 When parallel hurts — shared state, races, context fragmentation

Multi-agent is not a universal speedup. Three failure modes are common enough that you need to recognize them before reaching for parallelism.

Shared state races. Two agents dispatched to "add error handling to the codebase" will both modify the same utility files — one agent's writes overwrite the other's. Result: silent data loss or a broken repo. Prevention: enforce one-file-per-agent and use worktrees.

Context fragmentation. Each subagent has a partial view of the system. Agent A knows the API layer. Agent B knows the database layer. Neither knows both. When Agent A makes an assumption about database behavior that contradicts Agent B's implementation, you get a coherent-looking but internally inconsistent result. Prevention: the orchestrator must hold the full-system context and inject relevant cross-cutting constraints into every subagent prompt. Do not assume subagents will "figure out" what they don't know.

Coordination tax exceeding parallelism gain. For tasks that take 5 minutes sequentially: creating worktrees, crafting 3 well-scoped prompts, dispatching, integrating, and resolving conflicts may take longer. Parallelism wins at scale — large tasks with clear decomposition boundaries. It loses on small tasks and tasks with implicit coupling.

Anti-patterns

  • Shotgun dispatch: spawning many agents without decomposing — "do the whole refactor in parallel." No clean boundaries → guaranteed conflicts.
  • Context-free subagents: prompts that say "fix the auth module" without providing the module path, relevant interfaces, or constraints. Subagent hallucinates context.
  • No integration plan: dispatch agents, collect outputs, declare done — without actually reading and reconciling the results. Integration is where most multi-agent value gets destroyed.
  • Parallel review of dependent code: dispatching a review agent on code that a concurrent implementation agent is still writing.

11.10 The token math of multi-agent

Multi-agent is not free. Each subagent consumes tokens independently. The cost model:

Token cost formula

Total tokens = N × (C_prompt + C_work + C_output)
  + C_orchestrator

Where:
  N           = number of parallel subagents
  C_prompt    = tokens in each subagent's seeded context (your dispatch prompt
                + any injected file content)
  C_work      = tokens consumed by the subagent during its work turns
  C_output    = tokens in the subagent's final output returned to orchestrator
  C_orchestrator = tokens consumed by the orchestrator reading + integrating
                   all N outputs

Example: You dispatch 3 subagents. Each receives a 4 000-token prompt, does 8 000 tokens of work, and returns a 2 000-token result. The orchestrator reads all three results (6 000 tokens) and produces a 3 000-token integration.

Subagent cost: 3 × (4 000 + 8 000 + 2 000) = 42 000 tokens
Orchestrator:  6 000 (input) + 3 000 (output) = 9 000 tokens
Total:                                          51 000 tokens

Sequential equivalent (same work, one agent):  ~28 000 tokens
Overhead:                                       +23 000 tokens (≈ 82 % more)

But wall-clock time: 3 × sequential → 1 × parallel (if tasks are truly independent)
Break-even: the 82% token overhead is justified if the work takes > ~15 min sequentially
            and you need the result in < 5 min.

Multi-agent amortizes only when the tasks are genuinely parallel and the wall-clock savings matter. For background tasks where you don't care about latency, sequential is almost always cheaper. For interactive workflows where you need results fast, the token overhead is often worth paying.

12.1 Architecture — VS Code extension, Cline/Roo lineage

Kilo Code is an open-source VS Code extension that embeds an AI coding agent directly into the IDE. It descends from the Cline (formerly Claude Dev) project and shares significant lineage with Roo Code — both are open-source forks of the same codebase that diverged in different directions. Kilo Code's particular emphasis is on multi-model routing, structured modes, and team configuration: it was explicitly designed for professional workflows where different tasks warrant different models and different capability surfaces.

Architecturally, Kilo Code runs as a VS Code webview extension. When activated, it registers a sidebar panel, a set of VS Code commands, and a background Node.js process that manages model API calls. The extension communicates with the VS Code editor APIs to read files, run terminal commands, apply diffs, and interact with the broader workspace. Unlike some AI tools that operate purely through a chat interface, Kilo Code has bidirectional access to the VS Code environment: it can read the active editor selection, open new tabs, trigger tasks, and observe terminal output — all within the same session context.

The open-source nature of Kilo Code matters practically: the configuration schemas, mode definitions, and routing rules are human-readable JSON and YAML files committed to your repository. This means AI configuration is version-controlled alongside your code — team members get consistent behavior by checking out the same config. Verify the extension's current GitHub repository for the latest architecture details, as the extension structure evolves across releases.

12.2 The five modes — Architect / Code / Ask / Debug / Orchestrator

Architect mode is for planning and high-level design. In Architect mode, Kilo Code can read files and write specification documents, but it is constrained from making arbitrary code edits or running shell commands. You use it when you want to produce a technical spec, review architecture, or produce a structured plan for subsequent execution. The model used in Architect mode is typically the most capable and expensive — it is doing reasoning-heavy work where quality matters more than speed.

Code mode is the general coding workhorse. It has full file read/write access and terminal execution. This is the default mode for implementation tasks — writing functions, fixing bugs, running tests. Code mode is where most of your token spend occurs. Routing a fast, capable model (e.g., Claude Sonnet) here balances quality and cost.

Ask mode is strictly read-only. It can read files and answer questions, but it cannot write, edit, or execute. Ask mode is ideal for code Q&A, understanding an unfamiliar codebase, or checking your mental model of a system — tasks where you want an answer, not a change. Because it cannot write, it cannot make mistakes that need reverting. A smaller, faster model works well here; the cost savings on high-volume Q&A sessions are significant.

Debug mode is specialized for root-cause analysis. It has access to read files, read terminal output, and run diagnostic commands (e.g., running tests to collect failure messages), but its prompting is tuned toward systematic hypothesis testing rather than broad implementation. Debug mode is what you reach for when you have a specific failing test or error and want targeted diagnosis without rewriting half the module.

Orchestrator mode is the multi-agent coordinator. It decomposes a high-level task, dispatches subagents in other modes (called "boomerang tasks" in Kilo Code's terminology), and integrates their results. Orchestrator mode does not write code directly — it delegates to Code, Debug, or Architect subagents. This mode is covered in depth in Ch 11.8 and is the subject of the parallel workflows walkthrough.

12.3 Why modes exist — constraint as feature

The instinct when encountering modes is to see them as restrictions. The correct mental model is the opposite: modes are footgun prevention. When you ask a question in Ask mode, you have a guarantee — not a hope — that the AI cannot accidentally modify a file. That guarantee changes how you interact with it. You can freely explore a live production codebase without a mental safety tax. You do not need to mentally track whether this particular question might trigger a tool call that rewrites something.

The same principle applies to Architect mode. If you're doing architectural planning, you want the model to think broadly and boldly — proposing structure, questioning assumptions, suggesting refactors. But you don't want it to start implementing that refactor mid-thought. Architect mode's write constraint keeps it in the design space. The constraint is not a limitation; it enforces the conceptual boundary between designing and building, which is a real boundary that matters for quality.

Modes also have a second effect: they shape the system prompt the model receives. Architect mode's system prompt primes the model to think in terms of structure, tradeoffs, and specifications. Code mode's system prompt primes it for implementation correctness and test coverage. Debug mode's system prompt primes it for evidence-gathering and hypothesis testing. You're not just changing what tools are available — you're changing what kind of agent you're working with. The combination of constrained tools and mode-specific prompting means mode switching is a meaningful state transition, not just a label change.

12.4 Picking a model per mode — BYO providers

Kilo Code's "Bring Your Own model" architecture lets you configure any combination of supported providers — Anthropic, OpenAI, Google Gemini, AWS Bedrock, Azure OpenAI, OpenRouter, and local models via Ollama — and route different modes to different models. This is where significant cost optimization lives: use a frontier model for Architect, a fast capable model for Code, and a cheap/fast model for Ask.

Mode-to-model routing is configured in Kilo Code's custom modes file. 12.5 Custom modes — defining your own

Beyond the five built-in modes, Kilo Code lets you define custom modes with their own name, system prompt, tool permissions, and model assignment. A custom "Reviewer" mode, for example, might have read-only file access (like Ask), a system prompt tuned for finding bugs and suggesting improvements, and route to a different model than the default Ask config. Custom modes are defined in the same modes config file as built-in mode overrides.

Example: custom "Reviewer" mode (verify schema against current Kilo Code docs)

{
  "customModes": [
    {
      "slug": "reviewer",
      "name": "Reviewer",
      "model": "claude-opus-4-7",
      "provider": "anthropic",
      "roleDefinition": "You are a senior code reviewer. Your job is to identify bugs, security issues, performance problems, and design violations in the provided code. You do NOT write code or suggest rewrites — you identify and explain problems only.",
      "groups": ["read"],
      "toolPermissions": {
        "readFile": true,
        "writeFile": false,
        "executeCommand": false,
        "browser": false
      }
    }
  ]
}

The groups field controls which tool categories are available. Common groups include read (file reads), edit (file writes), command (terminal execution), and browser (web access). The roleDefinition string becomes the mode's system prompt. You can define as many custom modes as your workflow needs — a "SecurityAuditor" mode with no writes, a "Documenter" mode that writes only Markdown, a "Migrator" mode with access to your migration toolchain. Verify the groups values and toolPermissions schema against the current Kilo Code documentation — these identifiers may differ between versions.

Custom modes are particularly powerful for onboarding: a "NewbieHelper" mode with an explanatory system prompt and no write access gives junior developers a safe exploration surface without the risk of accidental modifications. The mode definition lives in version control, so the whole team benefits automatically.

12.6 Custom rules — per-project and global

Kilo Code supports two levels of custom rules: per-project rules and global rules. Per-project rules live inside the repository — historically in a .kilocode/rules/ directory (verify the exact path against current docs, as it may also be .clinerules or similar). Global rules live in the user's home configuration directory and apply to every Kilo Code session regardless of which project is open.

Per-project rules are the right place for: coding conventions (naming, formatting, file organization), framework-specific patterns (e.g., "always use the Result type for error handling, never throw"), testing requirements ("every public function must have a corresponding unit test"), and security invariants ("never log PII, never hardcode credentials"). Because they live in the repository, they're automatically applied for every team member. When a new developer joins, they get the same AI behavior everyone else has — no manual configuration step needed.

Example per-project rule files (.kilocode/rules/ — verify path against current docs)

.kilocode/rules/
  coding-style.md      # Naming conventions, file structure, import order
  testing.md           # Unit test requirements, coverage expectations
  security.md          # No PII logging, no hardcoded secrets, SQL parameterization
  git-conventions.md   # Commit message format, branch naming, PR size limits

Global rules are the right place for: your personal preferences across all projects (preferred response style, verbosity level, how you like diffs presented), authentication or workspace patterns that are consistent across your work, and developer identity information (e.g., "My name is Alice; sign all generated commit messages accordingly"). Global rules are not committed to any repository — they live in your user profile and apply universally. The split ensures team-shared conventions are in the repo, while personal preferences stay personal.

Rules are evaluated at the start of each task in that mode. Kilo Code injects the applicable rules into the system prompt as additional context. The order of precedence (when both global and per-project rules are present) is: per-project rules take priority for any conflict, with global rules filling in the rest. Verify the exact rule file format, directory structure, and precedence behavior against current Kilo Code documentation.

12.7 Settings deep dive — auto-approve, terminal, MCP, telemetry

Auto-approve toggles. Kilo Code's settings panel (accessible via the Kilo Code sidebar gear icon or VS Code settings under kilocode.*) provides fine-grained auto-approval controls per tool category. You can configure: auto-approve file reads always, auto-approve file writes only within specific directories (e.g., src/ but not .env or secrets/), require approval for all terminal commands, and auto-approve terminal commands that match a specific allowlist of safe patterns. The key insight: auto-approve is not binary. Configuring directory-scoped write approval and command-specific approval means you get the speed of automation for low-risk operations while retaining human gates for high-risk ones. The exact settings keys and UI location should be verified against the current Kilo Code release notes, as these have moved between versions.

Terminal integration. Kilo Code can run commands in a VS Code integrated terminal, observe their output, and use that output to inform subsequent decisions. Settings control: which shell is used (bash, zsh, fish, or the VS Code default), whether terminal sessions are reused across tasks or fresh per-task, and the timeout for long-running commands. For development workflows involving test runners or build systems that produce large output, the terminal output capture settings matter — you can configure a maximum output length to prevent runaway context consumption on verbose build logs.

MCP server registration. Model Context Protocol (MCP) servers are registered in Kilo Code's settings as a JSON array under the MCP configuration section (see 12.9 for a full example). Settings also control whether MCP tools are auto-approved per server or require manual confirmation per-call — useful when a server exposes a mix of safe read operations and destructive write operations.

Telemetry. Kilo Code, like most AI extensions, includes optional telemetry. By default it collects usage statistics (mode switches, model selections, task durations) to improve the product. This can be disabled entirely via the kilocode.telemetry.enabled setting (verify the exact key name). For enterprise environments where data governance matters, telemetry should be reviewed and disabled if required by policy. Kilo Code's open-source codebase means you can audit exactly what telemetry is collected before enabling it — a significant advantage over closed-source tools.

12.8 Memory and Context Bank

By default, Kilo Code does not persist memory across sessions — each new task starts fresh, with no knowledge of prior conversations or decisions. The Context Bank (also referenced as Memory Bank in some Kilo Code versions — verify current terminology) is the mechanism for explicitly persisting information across sessions. It works by writing structured files to a designated location in your project (historically .kilocode/memory/ or memory-bank/ at the project root) that Kilo Code reads at the start of each new session.

The Context Bank is organized around a set of standard files that capture different kinds of persistent knowledge. Common entries include: projectbrief.md (high-level project description and goals), activecontext.md (current task state, recent decisions, open questions), progress.md (what's done, what's in progress, what's blocked), and systempatterns.md (architectural decisions and conventions). Kilo Code agents in supported modes read these files before beginning work, so they arrive with project context rather than starting blind. When significant decisions are made during a session, the agent can update the Context Bank files to ensure the next session inherits that knowledge.

The practical implication: for long-lived projects, the Context Bank is the difference between an AI that needs re-orientation every session and one that operates with continuity. Maintaining it is low-overhead — the agent can update it as part of its end-of-task cleanup. For one-off tasks or short projects, the Context Bank overhead is not worth the setup cost; it pays off on projects that span multiple sessions over days or weeks. Verify the exact file names, directory location, and update mechanisms against current Kilo Code documentation, as this feature has evolved significantly across versions.

12.9 MCP integration in Kilo

Model Context Protocol (MCP) integration in Kilo Code follows the same MCP standard described in Ch 16, but the registration mechanism is specific to Kilo Code's settings. MCP servers are registered via the Kilo Code settings panel or directly in the VS Code settings.json. Once registered, an MCP server's tools become available to modes that have the mcp tool group enabled. Verify the exact settings structure against current Kilo Code docs.

Example: registering an MCP server in Kilo Code settings (verify schema against current docs)

// In VS Code settings.json (or Kilo Code's MCP config section):
{
  "kilocode.mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/workspace"],
      "env": {}
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${env:GITHUB_TOKEN}"
      }
    },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres"],
      "env": {
        "DATABASE_URL": "${env:DATABASE_URL}"
      }
    }
  }
}

Each registered MCP server starts as a subprocess when Kilo Code loads and remains running for the duration of the VS Code session. The server's exposed tools appear in the Kilo Code tool list and can be called from any mode with MCP access enabled. You can configure per-server auto-approval: for a read-only filesystem server you might auto-approve all calls; for a server that writes to a database, require per-call confirmation. Tool calls to MCP servers count against your context window just like any other tool call — large responses from database or filesystem servers can consume substantial tokens, so scoping queries carefully matters for cost management.

MCP servers can also be scoped to specific modes via mode tool permissions. A "DatabaseDebug" custom mode might have access to the Postgres MCP server while Code mode does not — preventing accidental database modifications during routine coding. This is the composability advantage of the modes-plus-MCP architecture: capability access is defined declaratively per mode, not negotiated per-task.

12.10 Commit message and PR features

Kilo Code includes automated commit message generation and PR description generation as built-in features. After a Code mode task that modifies files, Kilo Code can inspect the diff and generate a structured commit message following conventional commit format (feat, fix, docs, refactor, etc.). The quality of generated commit messages depends on the model used in Code mode — more capable models produce more accurate and contextually appropriate messages. You can configure commit message templates in the per-project rules to enforce a specific format (e.g., requiring issue numbers, ticket IDs, or specific scoping).

PR description generation works similarly: Kilo Code can analyze a branch diff versus the base branch, read the associated commits, and produce a structured PR description covering the change summary, motivation, testing notes, and reviewer checklist. This integrates with VS Code's GitHub extension to pre-populate the PR creation dialog. For teams with PR description standards, encoding them as per-project rules ensures Kilo Code generates descriptions that match the template.

The exact UI locations and commands for commit message and PR generation (e.g., slash commands, context menu items, or sidebar buttons) vary between Kilo Code versions — verify the current interface in the extension's changelog or documentation before building team workflows around specific UI interactions.

12.11 Cost dashboard and tracking

Kilo Code maintains a per-session cost tracker that reports token consumption and estimated dollar cost for each task. The cost display appears in the sidebar panel after each task completes, broken down by input tokens, output tokens, cache hits (if the provider supports prompt caching), and total cost at the model's current pricing. This makes cost visible at the task level rather than as a surprise on the monthly bill — you can see immediately whether a particular task or mode is consuming disproportionate resources.

To identify cost hotspots, examine the per-task breakdown over a few days of usage. Common patterns: Orchestrator mode tasks tend to have high orchestrator-turn costs because they read all subagent outputs into a single context; Ask mode Q&A sessions are frequently the highest-volume but should be low-cost if routed to a fast/cheap model (this is the main reason to use a cheaper model in Ask mode — the volume is high); large file reads in Code mode (e.g., reading a 3000-line file to make a 5-line change) are a common optimization target. If you see a mode consistently consuming more than expected, check whether the file reads injected by rules files are large, whether MCP server responses are verbose, or whether the system prompt for that mode is disproportionately long.

Kilo Code also supports per-provider budget limits — you can set a daily or per-task token cap that triggers a warning or hard stop before exceeding the threshold. Verify the exact budget/cap configuration path and behavior against current Kilo Code documentation, as this feature has evolved across versions. For team environments, the cost tracking data is exportable for allocation and chargeback purposes.

12.12 Working with multi-repo and monorepo setups

VS Code supports multi-root workspaces (a .code-workspace file that references multiple folders), and Kilo Code respects this structure. In a multi-root workspace, Kilo Code loads per-project rules from each workspace folder independently — the rules in packages/api/.kilocode/rules/ apply when the agent is working in the API package, and the rules in packages/frontend/.kilocode/rules/ apply when working in the frontend package. This enables per-package conventions in a monorepo without a single unwieldy global rules file.

For monorepo setups, the Context Bank placement matters: a project-level Context Bank at the workspace root captures cross-package architectural decisions, while package-level context can capture package-specific state. A recommended structure: .kilocode/memory/projectbrief.md at the root describes the overall system, and individual packages maintain their own activecontext.md if they're in active development. The orchestrator mode can read both levels to maintain a coherent cross-package view when dispatching subagents to different packages.

A practical multi-repo pattern: use a VS Code workspace file that references all related repositories. Kilo Code operates across all of them in a single session. When you ask Code mode to "make the API changes needed to support this new frontend feature," it can read both repositories' codebases and write to both. This cross-repo capability is an advantage over CLI-based tools that are inherently single-repo-scoped. Verify multi-root workspace behavior against current Kilo Code documentation — file access and rules resolution across workspace roots may have version-specific edge cases.

12.13 Power-user shortcuts

Mode quick-switch. The most used shortcut: Kilo Code registers a VS Code command for switching modes directly from the keyboard. The default keybinding (verify in current docs — it may be Ctrl+Shift+M / Cmd+Shift+M or accessible via the command palette as "Kilo Code: Switch Mode") opens a quick-pick menu of available modes. Assigning a dedicated keybinding via VS Code's keyboard shortcuts editor (keybindings.json) to the mode-switch command makes the Architect→Code→Ask cycle a muscle memory operation.

At-mentions and context injection. In the Kilo Code chat input, @ prefixes inject context: @file:path/to/file.ts injects a file's contents, @folder:src/ injects a directory listing, @git:diff injects the current git diff, and @problems injects the VS Code Problems panel contents (compile errors, linter warnings). Combining these in a single message — "@file:src/auth.ts @problems fix the TypeScript error on line 42" — gives the model precise context without it needing to explore the filesystem. This dramatically reduces the number of tool call turns and associated latency.

Task continuity and resume. Kilo Code tracks task history in the sidebar panel. You can click a previous task to resume it — re-loading the task's context and continuing from where it left off. This is useful for long-running tasks interrupted mid-session. The resume functionality respects the Context Bank if enabled, merging session state with persisted memory for a coherent continuation. Specific shortcut keys, @-mention syntax details, and resume behavior should be verified against the current Kilo Code documentation as these have changed between major versions.

Daily usage pattern:

  • Morning: Switch to Ask mode. Review overnight CI failures, read relevant code sections, understand the day's starting state. No accidental writes.

  • Implementation: Switch to Code mode. Work through the spec produced by Architect. Auto-approve writes within src/.

This pattern eliminates context re-establishment overhead. The most expensive part of an AI coding workflow is repeatedly explaining the same background context. The Context Bank, per-project rules, and consistent mode routing solve this at the infrastructure level — you invest in the config once and amortize it across every subsequent session.

13.1 Architecture — terminal, headless, IDE extensions

Claude Code is Anthropic's official CLI for Claude. At its core it is a Node.js process that runs in your terminal and gives Claude bidirectional access to your filesystem, shell, and development environment. Unlike IDE-embedded AI tools, Claude Code is surface-agnostic by default: it runs anywhere a terminal runs — local laptops, remote SSH sessions, CI containers, Docker environments. In headless mode Claude Code reads instructions from stdin or command-line flags, executes the task, and exits. This makes it a first-class participant in automated workflows: you can invoke it from a GitHub Actions step, a pre-commit hook, or a cron job and get structured output back. The --output-format json flag (or equivalent; verify the current flag name in claude --help) produces machine-parseable results.

IDE extensions are available for VS Code and JetBrains IDEs. These extensions embed the Claude Code REPL inside the IDE's sidebar or panel, providing the same capabilities as the terminal client but with direct access to the open editor context: the active file, selected text, diagnostic errors, and diff views. The underlying agent is identical — the extensions are thin shells that pass editor context into the same CLI runtime. Verify which IDE extension versions are currently shipping and stable, as the JetBrains extension in particular has lagged behind the VS Code release cadence historically.

13.2 CLAUDE.md — global, project, subdirectory scope

CLAUDE.md is Claude Code's instruction-injection mechanism. Unlike a system prompt that you pass at invocation time, CLAUDE.md files are discovered automatically based on where you are in the filesystem. Claude Code reads them at session start and incorporates their contents into its context. There are three distinct scopes, and all three are active simultaneously when they exist.

Global (~/.claude/CLAUDE.md): Applies to every Claude Code session on this machine, regardless of project. This is the right place for personal preferences that span all projects: your preferred language style, response format preferences, always-on constraints ("never commit with --no-verify"), personal skill registrations, and identity context the agent should always have. Think of it as your personal system prompt layer. Changes here affect every project immediately — treat it like a dotfile.

Project root (<project>/CLAUDE.md): Applies when Claude Code is run inside that project directory or any subdirectory. This is where project-specific guidance lives: the tech stack, architectural constraints, testing conventions, CI pipeline details, code style rules specific to this repo, and any context about the codebase the agent should always have loaded. Committing this file to the repository ensures every teammate gets the same agent behavior. This is the most important CLAUDE.md for team workflows.

Subdirectory (<project>/src/payments/CLAUDE.md): Applies only when Claude Code's working context is within that subdirectory. Use this for modules with unusual conventions, security-sensitive areas that need extra constraints ("never log PII in this module"), or subsystems where a domain-specific glossary helps. Subdirectory CLAUDE.md files stack on top of the project root and global files — all three merge into the active instruction set. This granularity is particularly useful in monorepos where different packages have different conventions.

Claude Code vs Kilo Code — memory and instruction injection: Claude Code uses CLAUDE.md files at three scope levels (global ~/.claude/, project root, subdirectory). Kilo Code uses .kilocode/rules/ — a directory of Markdown rule files that are loaded per-mode or globally. Both approaches store instructions as plain text files that are version-controlled alongside the project. The key difference: Kilo Code's rules system supports per-mode targeting (a rule file can apply only in Code mode, not in Ask mode), while Claude Code's CLAUDE.md is always-active within its scope. If you need per-capability gating, Kilo Code's rules model is more expressive; if you want a single coherent instruction document per scope level, CLAUDE.md's simplicity wins.

13.3 Slash commands — built-in and custom

Slash commands are Claude Code's in-session control surface. Type / at the prompt to see the full list. Built-in commands include: /clear — reset the conversation context to an empty state; /compact — summarize the current conversation and replace the history with a compact representation, reducing token usage while preserving essential state; /init — scaffold a new CLAUDE.md for the current project by analyzing the codebase; /review — trigger a code review skill on the current diff or specified files; /security-review — run a security-focused review; /config — open settings; /help — list all available commands. The full list evolves across releases; /help is the canonical source.

Other notable built-ins include /ultrareview (deep review with multiple passes, if installed as a skill), /schedule (create or manage scheduled remote agents), /loop (run a command on a dynamic interval), /plugin (plugin management), and model-specific commands. Several slash commands are actually thin wrappers around skills — invoking /review triggers the code-review skill via the Skill tool internally.

Custom commands live in ~/.claude/commands/ (global, available in all sessions) or <project>/.claude/commands/ (project-scoped). Each custom command is a Markdown file whose filename becomes the command name: ~/.claude/commands/standup.md becomes /standup. The file body is a prompt template that Claude executes when the command is invoked. You can reference $ARGUMENTS in the template to pass positional arguments from the command invocation. Custom commands are the fastest way to codify a recurring workflow — daily standup generation, PR description drafting, changelog updates — into a single keyable action.

13.4 Skills — what they are, how they activate

Skills are Claude Code's reusable capability units — structured prompting packages that encode a complex, multi-step workflow into a named, invocable artifact. A skill lives in ~/.claude/skills/<name>/SKILL.md. The file has two parts: a YAML frontmatter block that declares metadata, and a Markdown body that contains the actual instructions Claude follows when the skill executes.

A representative SKILL.md structure:

SKILL.md structure (~/.claude/skills/my-skill/SKILL.md)

---
name: my-skill
description: "One-line description shown in skill list"
version: 1.0
author: your-name
tags: [review, quality]
---

# My Skill

When this skill is invoked, do the following:

1. Read the current git diff with `git diff HEAD`.
2. Analyze each changed file for ...
3. Produce a structured report in the following format: ...

Skills activate via two mechanisms. First, they are discoverable as slash commands: if ~/.claude/skills/code-review/SKILL.md exists, you can type /code-review and Claude will invoke it. Second, they can be invoked programmatically via the Skill tool — other skills or orchestrating agents can call Skill({ skill: "code-review", args: "..." }) to chain skill executions. Auto-discovery means that skills registered in ~/.claude/skills/ appear automatically in /help output and in the skill list shown in the system reminder. You do not need to register them anywhere else — dropping a valid SKILL.md file into the directory is sufficient for activation.

13.5 Plugins and the plugin marketplace

Plugins are distribution bundles that package multiple skills, custom commands, and hooks into a single installable unit. Where skills are individual capabilities, a plugin is a coherent capability set — for example, a "Jira workflow" plugin might include an Atlassian MCP integration, a /triage-issue skill, a /generate-status-report skill, and a hook that auto-attaches Jira context at session start.

The plugin marketplace is Claude Code's ecosystem for sharing and discovering these bundles. To install a plugin, the workflow is a two-step process: first, use /plugin marketplace add <plugin-name> to search the marketplace and stage the plugin for installation; then run /plugin (the interactive plugin management flow) to confirm, configure, and activate it. Verify this flow against current Claude Code documentation — the plugin system is evolving and the exact command sequence may differ in newer releases. Installed plugins are tracked in your Claude Code settings and their components (skills, commands, hooks) are registered automatically.

You can also install plugins from local paths or git URLs for custom or private plugins. The plugin manifest format defines what gets installed and where — skills land in ~/.claude/skills/, commands in ~/.claude/commands/, and hooks are merged into ~/.claude/settings.json. For teams, packaging your shared Claude Code configuration as a plugin and hosting it on an internal registry is a powerful way to give everyone consistent capabilities with a single install step.

13.6 Hooks — lifecycle and use cases

Hooks are shell commands or scripts that Claude Code executes at defined points in the session lifecycle. They are configured in .claude/settings.json (project-level) or ~/.claude/settings.json (global). The primary hook lifecycle events are: SessionStart — fires when a new Claude Code session begins; PreToolUse — fires before any tool call, with the tool name and parameters available as environment variables; PostToolUse — fires after a tool call completes; Stop — fires when the session ends or /clear is run.

Use cases for hooks span a wide range: injecting dynamic context at session start (e.g., running git status and appending its output to the session), enforcing constraints before tool use (e.g., blocking Bash calls that contain rm -rf /), logging all tool calls to an audit file, sending a Slack notification when a long-running task completes, or updating a MEMORY.md file after each session ends. Hooks execute with the same permissions as the Claude Code process — they can read/write files, call APIs, and run arbitrary shell commands.

Example hooks configuration in .claude/settings.json

{
  "hooks": {
    "SessionStart": [
      {
        "command": "git log --oneline -5 2>/dev/null || true",
        "description": "Show recent commits at session start"
      }
    ],
    "PostToolUse": [
      {
        "matcher": { "tool": "Bash" },
        "command": "echo \"[$(date -u +%H:%M:%S)] Bash call completed\" >> ~/.claude/audit.log",
        "description": "Audit log for Bash tool use"
      }
    ],
    "Stop": [
      {
        "command": "~/.claude/scripts/update-session-notes.sh",
        "description": "Update session notes on exit"
      }
    ]
  }
}

Verify the exact hook event names and matcher syntax against current Claude Code docs — the hooks schema has evolved across versions and matcher fields differ per event.

13.7 Sub-agents — the Agent tool

Claude Code supports multi-agent architectures through the Agent tool, which allows the orchestrating Claude instance to spawn specialized sub-agents as separate, isolated sessions. Each sub-agent has its own context window, its own tool access, and executes a specific task in parallel or sequentially. The orchestrator receives the sub-agent's output when it completes and can use it to drive the next step of a larger workflow. This is the mechanism behind parallel code review, concurrent test generation, and any pattern where you want multiple specialized perspectives on the same problem simultaneously.

Claude Code exposes several sub-agent types. Note: the exact identifiers, names, and capability sets of sub-agent types are version-specific — always verify against current Claude Code documentation before relying on a specific type name in production workflows. At the time of writing, sub-agent types include general-purpose agents, exploration-focused agents that are optimized for read-heavy codebase analysis, planning agents that focus on structured decomposition, and code-reviewer agents tuned for quality analysis. The TaskCreate, TaskGet, TaskList, and TaskStop tools provide programmatic sub-agent lifecycle management within skills and hooks.

The key design principle for sub-agent use is task isolation: each sub-agent should receive a self-contained task brief with all the context it needs embedded in its initial prompt. Sub-agents do not share memory with the orchestrator or with each other — any shared state must be passed explicitly through the task description and result. For large parallel workloads (e.g., reviewing 20 files concurrently), this isolation is a feature: sub-agents cannot interfere with each other's reasoning. The orchestrator's job is decomposition, dispatch, and synthesis of results.

13.8 Plan mode workflow

Plan mode is Claude Code's approval-gate mechanism for complex, potentially destructive operations. When you enter plan mode, Claude reads your request, analyzes the codebase, and produces a structured execution plan — a list of proposed actions (file writes, shell commands, API calls) with rationale — but does not execute any of them. You review the plan, request modifications if needed, and then explicitly approve execution. This separates the reasoning step from the action step, giving you a review checkpoint before irreversible changes happen.

To enter plan mode, cycle through modes using Shift-Tab at the Claude Code prompt until "Plan" mode is shown, or prefix your message with an explicit plan request. In plan mode, Claude outputs a structured plan in Markdown format describing each proposed action. When you are satisfied with the plan, approve it — the ExitPlanMode mechanism signals to Claude that it should proceed to execution. Claude then executes the approved plan, tool by tool, with normal tool-use confirmation flows active.

Plan mode is most valuable for: multi-file refactors where you want to see the full scope before any file is touched; database migrations or infrastructure changes where partial execution is worse than no execution; onboarding to an unfamiliar codebase where you want to understand what Claude is about to do before it does it; and any task where you have a strong prior about the correct approach and want to verify Claude's plan matches it. The cost of plan mode is one extra round-trip to the model; the benefit is a review gate that prevents costly rollbacks.

13.9 Output styles

Claude Code's output style system lets you tune the tone, structure, and verbosity of Claude's responses without modifying CLAUDE.md. Styles are named presets — examples include concise, verbose, technical, explanatory, and bullet-heavy formats — that adjust how Claude structures its text output. This is distinct from capability changes (which modes and tools are active); output styles affect presentation only.

Styles can be set at the session level via the /config command or through settings. You can also define custom styles in your CLAUDE.md by describing the desired output format explicitly ("always use numbered lists for multi-step instructions, never use more than 2 levels of nesting, keep code blocks short and focused"). In practice, most advanced users find that a well-written CLAUDE.md output format section is more precise than a named style preset — you can specify exactly the formatting contract you want rather than choosing from a fixed menu. The styles system is most useful for quick, temporary changes within a session.

13.10 Fast mode — when and why

Fast mode trades reasoning depth for latency. When fast mode is active, Claude Code uses a faster response configuration — typically this means using a faster model variant or reducing the thinking budget — producing responses more quickly at the cost of some depth in complex reasoning tasks. Fast mode is not a different model selection in the sense of manually switching to Haiku; it is a tunable configuration within a session that adjusts the latency/quality tradeoff along a continuous axis. The exact implementation of fast mode — whether it swaps models, reduces context, or adjusts sampling — is subject to change; consult current documentation for the precise behavior.

When to use fast mode: interactive Q&A where you need rapid back-and-forth and the questions are not deeply complex; exploration tasks where you are orienting in a new codebase and want quick directional answers rather than exhaustive analysis; high-volume routine tasks (linting explanation, simple one-liner generation) where the full reasoning budget is overkill. When to avoid fast mode: plan generation, architectural analysis, security review, complex debugging where missing a subtlety has real cost. The practical heuristic: if you would be comfortable asking a junior developer with the context who answers quickly, fast mode is fine; if you want senior-level depth, use standard mode.

13.11 ScheduleWakeup, /loop, /schedule

Claude Code provides three distinct scheduling primitives that overlap in purpose but differ in mechanism and scope. Understanding which to use requires understanding what each actually does. ScheduleWakeup is a tool (callable within skills and agent workflows) that schedules Claude Code to wake and execute a task at a specific future time — a one-shot delayed execution. It is the programmatic primitive: a skill can call ScheduleWakeup to schedule follow-up work (e.g., "check if this CI job passed in 10 minutes"). It operates within the current machine's session lifecycle.

/loop is a dynamic interval runner. It takes a prompt or slash command and an interval specification and repeatedly executes that command at the given cadence within a running Claude Code session. Unlike ScheduleWakeup, /loop is interactive — you run it in a live session and it keeps running until you stop it. Use /loop for monitoring tasks where you want to watch a metric, poll a status endpoint, or repeatedly run a check while you are actively working. The interval can be model-paced (Claude decides when enough time has passed) or fixed-clock. It does not persist across session restarts.

/schedule is the persistent, cross-session scheduler. It creates "remote agents" — cron-like scheduled tasks that run on a schedule, survive session restarts, and execute even when you are not at the keyboard. You configure them with a cron expression or natural language schedule. /schedule is the right primitive for daily standup generation, nightly report emails, weekly code quality scans, or any task that should run reliably on a calendar-based cadence. The three primitives form a hierarchy: /schedule for persistent recurring jobs, /loop for in-session monitoring, ScheduleWakeup for programmatic one-shot delays.

13.12 Settings and permissions — .claude/settings.json

Claude Code's settings are controlled through two JSON files: ~/.claude/settings.json (global, applies to all projects) and <project>/.claude/settings.json (project-scoped, committed to the repo). The project settings override global settings where they conflict. The settings schema covers three major areas: permissions (what tools and shell commands Claude can run without prompting), environment variables injected into shell tool calls, and hooks.

The permissions system uses allowlists and denylists. The allowlist defines patterns of tool calls that Claude can execute without asking for confirmation — for example, allowing all Bash calls matching git *, or allowing Read on any file under src/. The denylist defines patterns that are always blocked regardless of what Claude or the user requests. This architecture means you can grant broad automation for safe operations (git, test runners, linters) while maintaining strict confirmation requirements for destructive operations (production deployments, database mutations).

Example .claude/settings.json

{
  "permissions": {
    "allow": [
      "Bash(git *)",
      "Bash(npm test *)",
      "Bash(npm run lint *)",
      "Read(**)",
      "Edit(src/**)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force *)",
      "Bash(* production *)"
    ]
  },
  "env": {
    "NODE_ENV": "development",
    "LOG_LEVEL": "debug"
  },
  "hooks": {
    "SessionStart": [
      {
        "command": "echo 'Project: MyApp | Branch: '$(git branch --show-current)",
        "description": "Show project context at session start"
      }
    ]
  }
}

13.13 Memory system — auto-memory, MEMORY.md

Claude Code's memory system provides structured persistence across sessions. The core component is a MEMORY.md index file (typically at ~/.claude/MEMORY.md) that acts as a table of contents for individual memory files. Each memory is a separate Markdown file with a typed header. The memory system supports four types: user memories capture personal preferences, communication style, and workflow patterns the agent has learned about you; feedback memories record corrections you have given ("don't add trailing commas to JSON", "always use single quotes in Python") so Claude does not repeat mistakes; project memories capture project-specific knowledge that was discovered mid-session (e.g., "the payments module uses a non-standard event emitter pattern"); reference memories store factual information you have explicitly asked Claude to remember (API keys, team member names, recurring context).

Auto-memory is the mechanism by which Claude Code proactively creates memory entries without being explicitly asked. When Claude notices it has learned something durable — a correction you gave, a pattern it should remember, a project fact that took several messages to establish — it can automatically write a new memory file and update the MEMORY.md index. The auto-memory system is triggered by signals in the conversation: explicit "remember this" instructions, corrections to Claude's behavior, and discovery of facts that are likely to recur. At session start, Claude reads MEMORY.md and loads relevant memory files as additional context, giving it continuity across sessions.

The memory system architecture (separate files + index) is intentional: it allows selective loading rather than dumping all memories into every context window. As memory volume grows, Claude can selectively load only the memories relevant to the current task. The exact implementation of auto-memory, the MEMORY.md schema, and the loading strategy are subject to change across Claude Code versions — treat this as an architectural description rather than a specification. You can also manually create and edit memory files; they are plain Markdown and fully human-readable.

13.14 Hands-on: configure Claude Code for your daily workflow

This walkthrough takes you from a fresh Claude Code installation to a fully configured daily workflow in six steps. Each step is independently valuable — you can stop after any step and have a meaningfully improved setup.

Walkthrough · Configure Claude Code for your daily workflow

  1. Create your global CLAUDE.md. 
    mkdir -p ~/.claude
cat > ~/.claude/CLAUDE.md << 'EOF'
# Global Claude Instructions

## Identity context
- My name is [Your Name]. I'm a [role] working primarily in [language/stack].
- My email is [email].

## Response preferences
- Be concise. Skip preamble. Lead with the answer.
- Use numbered lists for multi-step processes.
- When in doubt, ask one clarifying question rather than guessing.

## Constraints (always active)
- Never use `git push --force` without explicit confirmation.
- Never commit secrets or credentials.
- Always run tests before declaring a task complete.
EOF
    This file will be active in every Claude Code session from this point forward. Edit it whenever you notice a preference that should be universal.
  2. Initialize your project CLAUDE.md. Navigate to your project root and run: 
    cd /path/to/your-project
claude /init
    The /init command analyzes your codebase (package.json, directory structure, README, test files) and generates a starter CLAUDE.md. Review it, remove anything inaccurate, and add your project's specific conventions. Commit it: git add CLAUDE.md && git commit -m "chore: add Claude Code project config".
  3. Configure project permissions. Create .claude/settings.json in the project root: 
    mkdir -p .claude
cat > .claude/settings.json << 'EOF'
{
  "permissions": {
    "allow": [
      "Bash(git *)",
      "Bash(npm test *)",
      "Bash(npm run *)",
      "Read(**)",
      "Edit(src/**)",
      "Edit(tests/**)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force *)"
    ]
  }
}
EOF
    This eliminates confirmation prompts for safe operations while keeping hard blocks on destructive commands. Commit alongside CLAUDE.md.
  4. Write a custom slash command. Create a standup command: 
    mkdir -p ~/.claude/commands
cat > ~/.claude/commands/standup.md << 'EOF'
Generate a standup update for today.

1. Run `git log --oneline --since="yesterday" --author="$(git config user.email)"` to see yesterday's commits.
2. Check if there are any open PRs: `gh pr list --author "@me" --state open` (skip if gh is not available).
3. Produce a standup update in this format:
   **Yesterday:** [bullet points from commits]
   **Today:** [ask me what I plan to work on if not obvious from context]
   **Blockers:** [any blockers visible from PR comments or open issues, or "None"]
EOF
    Now /standup is available in every session. Test it: open Claude Code and type /standup.
  5. Install a plugin from the marketplace. Open Claude Code and run: 
    /plugin marketplace add superpowers
    Then complete the interactive installation: 
    /plugin
    Follow the prompts to confirm and activate. After installation, /help will show the new skills and commands the plugin registered. Verify the superpowers plugin name against the current marketplace — plugin identifiers may differ from skill names.
  6. Verify everything is wired up. Start a fresh Claude Code session in your project: 
    claude
    Check that: (a) Claude greets you with awareness of the project (from CLAUDE.md); (b) /standup appears in /help; (c) a git status Bash call does not prompt for confirmation (allowlisted); (d) attempting a rm -rf /tmp/test Bash call prompts for confirmation or is blocked (depending on your deny rules). If any of these fail, review the settings and CLAUDE.md for typos or scope mismatches.

Daily rhythm with this setup: Start each session with /standup to orient. Use plan mode (Shift-Tab) for any task touching more than two files. Use /schedule to set up nightly code quality scans. When Claude makes a mistake, correct it explicitly and let auto-memory capture the correction — it will not repeat that mistake tomorrow. The investment in this config compounds: every session is faster than the last because the agent accumulates accurate context about how you work.

14. Gemini CLI Deep Dive

What you'll learn: Gemini CLI's architecture, the free-tier story, GEMINI.md, extensions, MCP integration, how 1M context changes the calculus, and how to configure Gemini CLI for daily work.

14.1 Architecture — terminal, open-source, Google-backed

Gemini CLI is Google's official command-line interface for the Gemini family of models. Released as open-source under the Apache 2.0 license, it is a Node.js application that runs in any terminal and gives the Gemini model bidirectional access to your local filesystem, shell environment, and the wider internet via built-in search tools. The open-source nature means the entire agent loop — tool dispatch, context management, hook invocation — is auditable and forkable in a way that proprietary CLI tools are not. You can read exactly what gets sent to the model and patch behavior without waiting for an upstream release.

In architectural shape, Gemini CLI is close kin to Claude Code: both are terminal-first, both use a REPL-style conversation loop, both discover project-level instruction files automatically, and both expose extension points for adding tools and skills. The meaningful differences surface in defaults and emphasis. Gemini CLI ships with GoogleSearch and WebFetch as first-class built-in tools — web retrieval is not an add-on. It also defaults to a dramatically larger context window (1M tokens on supported models) and routes to Gemini models rather than Claude. Think of them as two implementations of the same architectural pattern, optimized for different model families.

Being Google-backed means Gemini CLI benefits from tight integration with Google's infrastructure: Vertex AI for enterprise deployments, Google account authentication for personal use, and a free tier that is genuinely generous by industry standards. The Google affiliation also means roadmap pacing tracks Gemini model releases closely — when a new Gemini model ships, CLI support typically follows quickly. As with any rapidly evolving tool, verify the current release cadence and version in the official GitHub repository before depending on specific behavior.

14.2 The model story — Gemini 3 Pro/Flash, free-tier economics

Gemini CLI defaults to Gemini models and surfaces model routing through settings.json (verify schema against current docs). The primary workhorses today are Gemini 3 Pro (the reasoning-heavy, higher-latency option suited for complex multi-step tasks) and Gemini 3 Flash (the speed-optimized, lower-cost option suited for fast iteration and high-volume tasks). Model names evolve with each generation — the pattern gemini-{version}-pro and gemini-{version}-flash has been stable, but verify current model identifiers in the Gemini API documentation before hardcoding them in configuration files.

Beyond the defaults, Gemini CLI supports routing to alternative models via OpenAI-compatible API endpoints. If you have a self-hosted model or a third-party inference provider that speaks the OpenAI chat completions format, you can point Gemini CLI at it through the openai_compat model provider configuration. This makes Gemini CLI a general-purpose agentic shell, not a Gemini-only tool. You can also configure direct Gemini API access for models not yet surfaced through the default routing.

The model selection decision in practice: use Flash for exploratory work, quick edits, and anything where latency matters. Use Pro for code generation tasks that require multi-file reasoning, architectural design discussions, or long planning sessions where an extra few seconds of model latency is irrelevant compared to the quality difference. With a 1M context window available on both variants, the choice is almost never about "fitting the context" — it's about the quality-latency tradeoff for the specific task.

14.3 Authentication paths — personal Google, API key, Vertex AI

Gemini CLI supports three authentication paths serving different use cases. Personal Google account authentication is the entry point for individual developers: you log in with your Google account via OAuth and get access to the free tier. As of mid-2025, the personal free tier provides approximately 1M context tokens per request and around 1,000 requests per day — these numbers are subject to change; verify current limits at ai.google.dev/gemini-api/docs/rate-limits. This is a genuinely usable daily-driver tier, not a preview teaser, and it is the reason Gemini CLI has low friction for new users.

API key authentication is the step up from free-tier personal use. You generate an API key at Google AI Studio, set it in your environment (GEMINI_API_KEY), and gain access to higher rate limits and pay-as-you-go pricing. API key auth is the right choice when you need reliable, higher-volume access for personal projects or small teams, without the full enterprise setup. It also enables programmatic use in CI pipelines and scripts where OAuth browser flows are not possible.

Vertex AI authentication is the enterprise path. Here Gemini CLI uses Google Cloud Application Default Credentials (ADC) — typically via gcloud auth application-default login — and routes requests through your organization's Google Cloud project. Vertex AI gives you VPC-SC controls, data residency guarantees, audit logging, and the ability to use private model endpoints. This is the correct auth path for any production or compliance-sensitive deployment. The configuration lives in settings.json under the vertexai key; exact schema should be verified against current documentation as the Vertex AI integration has expanded significantly since initial launch.

14.4 GEMINI.md — global, project, subdirectory scope

GEMINI.md is Gemini CLI's instruction-injection mechanism, directly analogous to Claude Code's CLAUDE.md. At session start, Gemini CLI discovers and loads GEMINI.md files from three scope levels, merging them into the active context. Understanding which scope to use is the first configuration decision every team should make deliberately rather than accidentally.

Global (~/.gemini/GEMINI.md): Applies to every Gemini CLI session on this machine. This is the right place for personal preferences — your communication style preferences, always-on constraints, personal tooling context, and any facts about you the agent should always know. Like a personal dotfile, changes here affect every project immediately. A minimal but effective global GEMINI.md might contain: your name and role, your preferred explanation depth, your go-to languages, and any firm constraints you never want the agent to violate ("never push directly to main").

Project root (<project>/GEMINI.md): The most important scope for team workflows. This file describes the project to the agent: tech stack, architecture overview, testing conventions, CI pipeline, code style rules, common commands, and known gotchas. Commit it to the repository so all teammates get consistent agent behavior. A good project GEMINI.md eliminates the need to re-explain context at the start of every session. Subdirectory (<project>/src/payments/GEMINI.md): Applies only within that directory tree. Use it for modules with unusual conventions, security-sensitive areas, or domain-specific glossaries. All three levels stack — the agent sees global + project root + subdirectory simultaneously. Here is a minimal example:

# GEMINI.md — payments service
## Stack
Node.js 20, Postgres 15, Stripe SDK v12.

## Constraints
- Never log card numbers or CVV values, even in debug output.
- All DB queries must go through the query builder in src/db/index.ts.
- Tests live in __tests__/ alongside source files.

## Commands
- npm test — run unit tests
- npm run migrate -- --env staging — apply pending migrations
GEMINI.md vs CLAUDE.md — structural equivalence: The two files serve identical purposes and share the same three-scope hierarchy (global / project / subdirectory). The practical difference is tooling: /init in Claude Code generates a CLAUDE.md by analyzing your codebase; Gemini CLI has its own equivalent scaffolding command (verify current command name). If you work across both tools, maintaining parallel GEMINI.md and CLAUDE.md files with shared content is a common pattern — some teams symlink them or use a shared source of truth with a generation step.

14.5 Slash commands — built-in and custom

Gemini CLI exposes a slash command interface in the REPL. Type / at the prompt to see the current list. Known built-in commands include: /help — list all commands; /clear — reset the conversation context; /chat — manage named conversation sessions (save, resume, list); /compress — summarize and compress the conversation history to reduce token usage while preserving key state; /memory — manage the MemoryTool's stored facts; /tools — list available tools and their status; /stats — display token usage for the current session; and /quit (or /exit) — end the session. The complete and authoritative list is in /help — these commands evolve frequently, and names or behaviors may differ in your installed version.

Custom slash commands can be added through GEMINI.md and extensions. The mechanism mirrors Claude Code's approach: you define a command in a skill or extension manifest and it becomes available as a slash command in the session. This allows teams to surface domain-specific workflows as first-class commands — for example, a /deploy-preview command that runs your staging deployment workflow, or a /lint-fix command that runs your full linting pipeline and applies safe auto-fixes.

14.6 Skills — activate_skill and on-demand loading

Gemini CLI has a skills system, but its activation model differs from Claude Code's. In Claude Code, skills are discovered at session start from the filesystem and loaded proactively — available skills appear in the system-reminder context and can be invoked immediately. In Gemini CLI, the primary activation path is the activate_skill tool: the agent calls this tool with a skill name or path, which loads the skill's SKILL.md into context and makes its capabilities available. This is an explicit pull model rather than an implicit push model.

The practical implication is session initialization: in Claude Code, you often rely on the harness to auto-inject available skills. In Gemini CLI, the agent needs to know what skills exist (typically via GEMINI.md listing them) and then activate the relevant ones for a task. A common pattern is to list available skills in your project GEMINI.md with short descriptions, so the model can recognize when a task maps to a skill and call activate_skill appropriately. Some teams make this more explicit by writing activation instructions directly in GEMINI.md: "For deployment tasks, activate the deploy skill first."

Skill authoring for Gemini CLI follows the same SKILL.md convention. A skill is a directory containing a SKILL.md (instructions for the agent on what the skill does, when to activate it, and how to use it) plus any supporting scripts or configuration. The key difference from Claude Code skills is that Gemini CLI skills don't automatically expose slash commands or appear in system reminders — they rely on the activate_skill invocation path. This makes the activation more explicit but requires slightly more deliberate configuration in GEMINI.md to wire up well.

14.7 Extensions — install, discover, share

Extensions are Gemini CLI's primary mechanism for adding tools, capabilities, and integrations beyond the built-ins. An extension is a directory with a manifest file (typically gemini-extension.json) that declares the extension's name, description, tools it provides, and any GEMINI.md content to inject. Extensions can provide MCP servers, custom tools implemented as shell commands, additional slash commands, or skill bundles.

Installation from a remote Git repository uses a command in the form gemini extensions install --source <git-url>; for a local extension directory the flag is --path <local-path>. Verify the exact flag names and command syntax with gemini extensions --help, as the CLI's extension management commands have changed across versions and the flags above may not match your installed version exactly. Installed extensions are tracked in your global Gemini CLI configuration and activated in all sessions unless scoped otherwise.

Discovering community extensions currently happens through GitHub search and word of mouth — there is no centralized extension registry analogous to VS Code's marketplace, though Google has indicated a more structured discovery mechanism is planned. Sharing an extension is as simple as publishing the extension directory to a public Git repository: the --source install path accepts any valid git URL, including GitHub, GitLab, or self-hosted repositories. For internal team extensions, private repositories work fine as long as the installing user has read access and appropriate SSH keys or tokens configured.

14.8 Hooks — lifecycle events

Gemini CLI supports lifecycle hooks that let you inject behavior at key points in the agent loop. Hooks are shell commands (or scripts) configured in settings.json under the hooks key. They fire at defined lifecycle events and receive context about the current state via environment variables or stdin. This makes hooks the right place for concerns like logging, notification, safety gates, and environmental setup that should happen consistently regardless of the conversation content.

Known lifecycle events include pre- and post-tool execution hooks (fire before/after any tool call), session start/end hooks, and command hooks that fire around specific slash commands. The complete list of supported hook events is narrower than Claude Code's hook system and has grown incrementally — verify the current supported events in the official repository before writing hooks that depend on specific event types. A practical minimum viable hook setup: a post-session hook that appends a summary to a daily log file, and a pre-shell-command hook that echoes the command to stderr for human review in high-trust environments.

Unlike Claude Code's hooks, which are integrated into the Claude Code harness and can trigger skills, Gemini CLI hooks are currently more limited to shell-command invocations. The asymmetry is worth noting: if you are migrating a Claude Code workflow that relies heavily on hooks triggering complex skill orchestration, you may need to rebuild that logic differently in Gemini CLI — typically by encoding the orchestration in the agent's instructions rather than in hook scripts.

14.9 Built-in tools — Read, Write, Shell, GoogleSearch, WebFetch, MemoryTool

Read gives the agent access to your local filesystem for reading files and directories. It respects the permissions model configured in settings.json and will prompt for confirmation on paths outside the project root unless permissions have been pre-approved. This is the workhorse tool for any code-understanding or analysis task.

Write allows the agent to create or overwrite files. Like Read, it is subject to the permissions model and will prompt by default for writes to sensitive paths. Write is used for code generation, configuration file creation, and any output the agent produces that should persist beyond the session.

Shell executes arbitrary shell commands in the local environment. This is the most powerful and the most dangerous built-in tool — it gives the agent the ability to run tests, install packages, invoke build systems, and perform any action your user account can perform. The permissions model and the --yolo flag (see 14.11) both affect how Shell invocations are confirmed.

GoogleSearch is a first-class built-in, not an optional add-on. The agent can invoke Google Search directly to retrieve current information, resolve documentation questions, check package versions, or look up error messages. The results are returned as structured summaries with source URLs, not raw HTML. Having search as a built-in fundamentally changes how you prompt the agent — you can ask questions that require current information without needing to pre-populate context.

WebFetch retrieves the full content of a specific URL and returns it as text for the agent to reason over. Use it when GoogleSearch returns a URL you want the agent to read in full — a documentation page, a GitHub issue, a PR diff, or a specification. WebFetch and GoogleSearch together give Gemini CLI a web-retrieval capability that is genuinely useful without external MCP servers.

MemoryTool provides a key-value persistence layer across sessions. The agent can store facts, decisions, and state using MemoryTool, and they will be available in future sessions. This is how Gemini CLI achieves cross-session memory without relying purely on GEMINI.md. MemoryTool is inspectable and editable via the /memory slash command, making it easy to audit and correct what the agent has stored. See 14.12 for how MemoryTool and GEMINI.md work together as a complete memory system.

14.10 MCP integration in Gemini CLI

Gemini CLI supports the Model Context Protocol (MCP), allowing it to connect to external MCP servers and use the tools, resources, and prompts they expose. MCP servers are registered in settings.json under the mcpServers key, using the same JSON structure that is becoming the de facto standard across CLI tools. Each server entry specifies a name, transport type (stdio or sse), the command to launch the server (for stdio), and any environment variables it needs.

Once registered, MCP tools appear in the agent's tool list alongside built-ins and are callable by name. The agent discovers available MCP tools at session start via the standard MCP tools/list call, and then invokes them using tools/call. From the agent's perspective, MCP tools are indistinguishable from built-in tools — the routing is transparent. This means you can extend Gemini CLI with any MCP server: databases, cloud APIs, internal tooling, observability systems, or specialized code analysis tools.

Differences from Claude Code's MCP support: Gemini CLI's MCP integration is evolving and may not yet support the full MCP specification surface — in particular, MCP Resources (server-side context documents) and MCP Prompts (server-defined prompt templates) may have more limited support than MCP Tools. Verify current MCP feature coverage in the Gemini CLI release notes before depending on Resource or Prompt features. Claude Code's MCP integration, having been in production longer, has broader resource and prompt support at this writing.

14.11 Settings — settings.json, permissions, --yolo

Gemini CLI configuration lives in ~/.gemini/settings.json (global) and optionally <project>/.gemini/settings.json (project-scoped). The settings file controls: model selection, authentication configuration, permissions for tool use, MCP server registrations, hook definitions, and UI preferences. The project-scoped settings file is useful for teams that want to standardize tool permissions or MCP server registrations per project without requiring each developer to configure them manually.

The permissions system gates tool invocations that could have side effects. By default, Write, Shell, and MCP tool calls prompt for confirmation. You can pre-approve specific paths, commands, or tool names in the permissions configuration to reduce friction for common operations. The permissions model is intentionally conservative — the default is to ask, not to assume — which means the first time you set up a project you should expect permission prompts, and the right response is to add patterns to your permissions config rather than clicking through repeatedly.

The --yolo flag is frequently misunderstood. It is a per-invocation flag that auto-approves all tool calls for that single gemini command run — it is not a persistent mode toggle and does not modify settings.json. Use it for scripted, non-interactive invocations where you trust the task completely and do not want prompt interrupts: CI pipelines, batch processing scripts, automated one-shots. Do not use it interactively as a way to skip confirmations during exploratory work, where the prompts exist precisely to catch unintended side effects. The asymmetry to internalize: --yolo is a scripting convenience, not a workflow setting.

14.12 Memory and context tools

Gemini CLI uses two complementary mechanisms for state persistence: MemoryTool for dynamic, session-updated facts, and GEMINI.md for stable, human-curated context. Together they cover the two ends of the memory spectrum. GEMINI.md is what you know before the agent starts working — project conventions, constraints, background context. MemoryTool is what the agent learns during work — user preferences revealed over time, decisions made, corrections applied, workflow patterns observed.

MemoryTool stores data as named key-value entries that persist in the Gemini CLI memory store (typically a local file in ~/.gemini/). The agent can read, write, and delete entries via the MemoryTool API. Entries are loaded into context at session start, so facts stored in one session are available in the next without any manual copy-paste. The /memory slash command lists current stored entries, lets you edit them, and lets you delete stale or incorrect entries. This human-in-the-loop inspection is important: do not treat MemoryTool as an opaque black box — review it periodically and remove entries that are outdated or wrong.

A practical memory hygiene pattern: at the end of a significant work session, ask the agent to summarize what it learned that should be remembered, review the proposed entries, approve or edit them, and let MemoryTool store the result. This intentional "close session" step prevents MemoryTool from accumulating a growing pile of stale facts. For facts that should survive a full MemoryTool reset (e.g., fundamental project constraints), move them to GEMINI.md rather than relying on MemoryTool persistence.

14.13 Working with the 1M context window

A 1M-token context window is not just a quantitative improvement — it changes the qualitative nature of how you work with the agent. The scarcity model that governs most AI-assisted work (carefully curate what you include, summarize aggressively, rotate files in and out) largely dissolves. You can load entire repositories, full conversation histories, comprehensive documentation sets, and long-running task state without hitting limits. This should change your prompting approach: instead of pre-filtering context for the agent, load broadly and let the model's attention mechanism do the filtering.

Patterns that work well: Load the full repository at the start of a session when working on a non-trivial codebase. Keep the full conversation history in context across a long multi-step task rather than compressing. Include full specification documents and API references directly, rather than summarized excerpts. Ask the model to reason about the full test suite when debugging a regression — not just the failing test. The 1M window makes "just load the whole thing" a viable strategy for most real-world codebases.

Anti-patterns to avoid: The most common mistake is treating the 1M window as a dumping ground — loading everything available just because you can. Irrelevant context still costs tokens and can dilute attention on what matters. The second anti-pattern is using the large window to avoid writing good GEMINI.md — foundational project context should be in GEMINI.md and loaded efficiently on every session, not reconstructed by loading thousands of files each time. The third is forgetting that long contexts increase latency: a nearly-full 1M context window will produce noticeably slower responses than a focused 10K context, even on Flash. Load broadly, but load intentionally.

14.14 Hands-on: configure Gemini CLI for your daily workflow

This walkthrough takes you from a fresh Gemini CLI installation to a configured daily-driver setup. Complete it once and you will have a working foundation to iterate on.

Walkthrough · Configure Gemini CLI for your daily workflow

1. Install Gemini CLI. Gemini CLI requires Node.js 18 or later. Install globally via npm:

npm install -g @google/gemini-cli

Verify the installation: gemini --version. Check the GitHub repository for the current package name and minimum Node version, as these may have changed.

2. Authenticate with your personal Google account. The simplest starting point:

gemini auth login

This opens a browser window for OAuth authentication. After approving access, your credentials are cached locally. Verify the exact subcommand — it may be gemini auth or a direct gemini login depending on the version. Confirm you're authenticated: gemini auth status (or equivalent). You are now on the free tier.

3. Create your global GEMINI.md. Create the directory and file:

mkdir -p ~/.gemini
# Edit ~/.gemini/GEMINI.md with your preferred editor

Add at minimum: your name and role, your preferred programming languages, 3–5 always-on constraints, and a line listing where your projects live. This file is loaded on every session — keep it focused and under 500 lines.

4. Create a project GEMINI.md. Navigate to a project you work in regularly:

cd ~/projects/your-project
# Create GEMINI.md describing the project stack and conventions

Run gemini in the project directory and ask the agent: "Analyze this project and help me write a GEMINI.md that captures the key context you would want for future sessions." Review and edit the output. Commit the result to the repository.

5. Install an extension. Find an extension you want (e.g., a community tool from GitHub):

gemini extensions install --source https://github.com/example/gemini-ext-name

Verify the exact flag syntax with gemini extensions --help. After installation, restart your session and confirm the extension's tools appear in /tools.

6. Register an MCP server. Open or create ~/.gemini/settings.json and add an MCP server. Example for a filesystem MCP server:

{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/allow"],
      "transport": "stdio"
    }
  }
}

Start a new Gemini CLI session and verify the MCP tools appear: ask the agent "What tools do you have available?" and look for tools from the registered server.

7. Validate your setup. In a Gemini CLI session in your project directory, run through a quick smoke test: ask the agent to explain the project's main entry point (tests Read), create a scratch file (tests Write), run your project's test command (tests Shell), look up a dependency's changelog (tests GoogleSearch + WebFetch). If all five tools work without unexpected permission errors, your daily-driver config is operational.

15. The Superpowers Methodology — Claude Code Skills, Gemini CLI Skills & Kilo Code Modes

What you'll learn: why methodology bundles exist, the portable patterns Superpowers encodes, the canonical Claude Code plugin, how to adapt to Kilo Code (modes/rules) and Gemini CLI (skills), and how to ship your own methodology bundle for your team.

15.1 What Superpowers is — a methodology bundle, not a tool

Every experienced developer has a workflow: a set of habits and checkpoints they apply to every non-trivial task — think before you code, write the test first, get a second opinion before merging. The problem with agentic coding is that the agent has no habits. Left unprompted, it will skip steps that humans would never skip: writing code before understanding requirements, merging without verification, implementing without planning. A methodology bundle is a collection of encoded workflows that teaches the agent your habits. It is not a tool in the traditional sense — it does not add capabilities — it shapes how the agent uses the capabilities it already has.

Superpowers is the canonical methodology bundle for Claude Code. It encodes a specific, opinionated way of working: every creative task starts with brainstorming; every multi-step task gets a written plan before a single file changes; every implementation follows test-driven discipline; every completion goes through a verification gate; every significant change goes through a code review loop. These habits are not invented for the bundle — they are the habits that experienced software engineers apply anyway. Superpowers makes them automatic for the agent.

The critical framing is tool-agnostic at heart. The methodology — the pattern of brainstorm → spec → plan → execute → TDD → verify — is not Claude-specific. The same sequence of behaviors can be encoded as Kilo Code custom modes, as Gemini CLI skills, or as a structured session-opening prompt. Superpowers is the canonical, most fully-featured implementation, but the pattern transfers. Teams that understand this can carry the methodology across tool changes, model upgrades, and organizational standardization efforts without losing their workflow investment.

15.2 The Superpowers methodology — portable patterns

The methodology's spine is a linear sequence that keeps the agent honest at each phase transition. The six stages are: (1) Brainstorm — before touching code or writing specs, explore the problem space, surface hidden requirements, and consider multiple approaches. (2) Spec — write down what you are building in enough detail that a collaborator could implement it without asking questions. (3) Plan — decompose the spec into an ordered list of concrete steps, identifying dependencies and risks before any file changes occur. (4) Execute — implement the plan, step by step, with human checkpoints at phase boundaries. (5) TDD — write tests that demonstrate the implementation is correct, not after the fact but as part of the execution phase. (6) Verify — confirm that the thing you built matches the thing you specified, using the agent's own verification skills before declaring done.

Each stage has a corresponding skill in the Superpowers library. The skills are not strictly sequential in all workflows — a small bugfix might start at Execute and skip Brainstorm and Spec entirely. The methodology is a default sequence that the agent applies when the task complexity warrants it, with lighter-weight shortcuts for simpler work. The key insight is that the methodology encodes the decision about which stages to apply, not just the execution of each stage. This is what separates a methodology bundle from a collection of isolated prompts.

The portable pattern is the phase-gate model: before moving from one stage to the next, produce an artifact (a brainstorm document, a spec file, a plan file, a test suite) that the human can review and approve. Artifacts are checkpoints. This is the mechanism that keeps the agent from sprinting ahead while the human loses track of what is being built. Regardless of which tool you use to implement this, the artifact-gate structure is what makes the methodology meaningful in practice.

15.3 The library tour — what each skill enforces

The Superpowers library covers the full development lifecycle. Each skill is a named, installable unit of methodology. Here is the canonical library in order:

  • brainstorming — Forces exploration before implementation. Invokes structured divergent thinking (multiple approaches, hidden requirements, risks) before the agent produces any artifact. The mandatory pre-step for any creative work.
  • writing-plans — Takes a spec or requirements description and produces a written, numbered implementation plan. No code is written during this skill. The plan is an artifact for human review.
  • executing-plans — Works through an approved plan step by step, checking off items and pausing at defined review points. Keeps execution aligned to the plan rather than improvising.
  • subagent-driven-development — Dispatches independent plan tasks to parallel subagents, collecting results back into the main session. The parallelism skill for decomposable plans.
  • test-driven-development — Enforces the red-green-refactor cycle: write a failing test, make it pass with minimal implementation, then refactor. The agent is blocked from writing implementation before tests.
  • systematic-debugging — Structures debugging as a hypothesis cycle: form a hypothesis about root cause, write a minimal reproducer, verify, fix, confirm fix. Prevents random trial-and-error code changes.
  • verification-before-completion — Before declaring a task done, the agent runs a structured verification checklist: tests pass, no regressions, output matches spec, edge cases considered.
  • requesting-code-review — Prepares a structured review request: summarizes the change, highlights design decisions, identifies areas of uncertainty, and formats for a human or agent reviewer.
  • receiving-code-review — Processes incoming review feedback systematically: acknowledges each finding, classifies it (agree/disagree/needs-clarification), and produces a response plan before making any changes.
  • finishing-a-development-branch — The branch-close checklist: all tests green, branch rebased or merged cleanly, PR description written, review addressed, merge-ready signal sent.
  • writing-skills — The meta-skill. Guides the creation of new skills following the Superpowers format: name, description (for retrieval), body (agent instructions), references. The bootstrapping skill for methodology extension.

The library is not exhaustive by design — it covers the critical phase transitions that agents most commonly skip. Teams extend it with domain-specific skills (deployment workflows, incident response runbooks, database migration procedures) using the same format.

15.4 Three implementations, one idea — Claude / Gemini / Kilo

The Superpowers methodology has three concrete implementations, each optimized for its host tool. Claude Code skills (canonical): skills are SKILL.md files discovered automatically from ~/.claude/skills/ and plugin directories. They appear in system-reminder context at session start and are invoked via the Skill tool. Auto-invocation via SessionStart hooks means the agent can apply skills without explicit user instruction — the methodology fires automatically when task patterns match. This is the most seamless implementation because the harness does the wiring.

Gemini CLI skills (explicit): the same SKILL.md format works in Gemini CLI, but activation is explicit via the activate_skill tool rather than automatic. Skills listed in GEMINI.md give the agent awareness of what's available; the agent then decides when to call activate_skill. This pull model is slightly more manual but has one advantage: it is transparent. Every skill activation is a visible agent action in the conversation log. Gemini CLI shines here when you want audit trails of which methodology steps were applied.

Kilo Code modes/rules (mode-selected): Kilo Code encodes methodology as custom modes. Each Superpowers skill maps to a custom mode whose system prompt contains the skill body. The user (or an Orchestrator mode) selects the appropriate mode for each phase. Kilo Code's advantage is model selection per mode — you can route brainstorming mode to a reasoning-heavy model and executing-plans mode to a faster, cheaper model. The tradeoff is that mode transitions require explicit user action; there is no auto-invocation equivalent. Kilo Code is the best implementation for teams that want fine-grained model routing as part of their methodology.

15.5 The Claude Code plugin — installation and auto-invocation

The canonical installation path for Superpowers in Claude Code is the plugin marketplace. Install via the /plugin interactive flow — either through the official marketplace (/plugin install superpowers@claude-plugins-official or equivalent) or via the obra fork (/plugin marketplace add obra/superpowers-marketplace then /plugin). Verify the current canonical install path against the Superpowers README at github.com/obra/superpowers before scripting against it. To view installed plugins and confirm the installation was successful, run /plugin. After installation, skills are available immediately in the current session and all subsequent sessions. The plugin manager handles versioning and updates — you can check for updates by revisiting the plugin command.

The auto-invocation mechanism is the using-superpowers meta-skill, which is wired to the SessionStart lifecycle hook. When Claude Code starts a new session, the harness fires the SessionStart hook, which triggers using-superpowers. This meta-skill's job is to orient the agent: it reminds the agent that the Superpowers methodology is active, enumerates the available skills and their trigger conditions, and sets the behavioral defaults for the session. The result is that the methodology is "on" from the first message, without the user needing to invoke anything explicitly.

The using-superpowers meta-skill also handles a subtle problem: skill discovery is passive (the skills appear in context), but behavioral adoption requires active orientation. Without the meta-skill, an agent might have all the skills loaded but still skip the brainstorming phase because nothing prompted it to apply the methodology. The SessionStart hook-driven orientation solves this by making the methodology's presence explicit at the start of every session, turning passive availability into active behavioral defaults.

15.6 The Claude Code skill machinery — format, discovery, Skill tool

A Claude Code skill is a directory containing a SKILL.md file (and optionally supporting scripts or configuration). The SKILL.md format has a frontmatter YAML block at the top followed by a Markdown body. The frontmatter declares at minimum: name (the kebab-case identifier), description (the when-to-invoke text used for retrieval), and optionally metadata (for type tagging). Note: a trigger field appears in some community and user-authored skill formats (for example, slash-command bindings in personal skills), but it is not part of the standard Superpowers SKILL.md convention — the standard fields are name, description, and metadata. The Markdown body is the agent's instruction set — what to do when this skill is active, in whatever level of detail the skill requires.

Discovery works through a path hierarchy. Claude Code scans ~/.claude/skills/ for user-level skills, plugin directories for installed plugin skills, and project-level .claude/skills/ for project-local skills. All discovered skills are surfaced in the system-reminder context block that appears in the agent's context at session start and periodically during the session. The agent sees skill names and descriptions, which is what enables it to invoke the right skill for the right task.

Invocation uses the Skill tool. When the agent decides a task matches a skill's description, it calls Skill with the skill name and optional arguments. The tool loads the full SKILL.md body into the agent's active context and executes the skill's instructions. From the user's perspective, skill invocation is transparent — you see the agent's actions, not the tool call that loaded the skill. Understanding this machinery matters when you are writing skills or debugging why a skill is not firing: the description must be specific enough that the agent recognizes it as relevant, but not so narrow that it only fires in obvious cases.

15.7 Rigid vs flexible skills — when to enforce, when to suggest

Not all skills should behave the same way. Some workflows have hard sequencing requirements where skipping a step produces bad outcomes — test-driven development is the canonical example: if you write implementation before tests, you are not doing TDD, period. Other workflows are more like checklists that improve quality but where deviating on a specific task is sometimes correct — a code review checklist might be skippable for a one-line typo fix. The skill itself signals which category it belongs to through the language of its body.

Rigid skills use imperative, blocking language: "You MUST write the failing test before writing any implementation code. Do not proceed to implementation until you have a red test." This language tells the agent that deviation is not appropriate, and the agent will typically respect it. Rigid skills are appropriate for methodology steps where the discipline is the value — if you allow shortcuts, the methodology degrades to nothing. Use rigid enforcement for TDD, for verification gates, and for any step where "I'll do it later" is a broken promise.

Flexible skills use advisory language: "Consider structuring your approach as... If the task is small enough to skip planning, use your judgment." These skills provide a scaffold the agent can adapt. They are appropriate for tasks where the pattern has value at scale but where mechanical enforcement would be counterproductive for small tasks. The practical rule: if a senior engineer would be annoyed at being forced to follow the full procedure for a trivial task, the skill should be flexible. If skipping the procedure is how technical debt accumulates, the skill should be rigid.

15.8 Anatomy of a great skill

A well-written skill has four elements working together. Name (kebab-case): the identifier must be memorable and self-describing. systematic-debugging is better than debug-helper because it communicates the approach, not just the domain. Names are used in inter-skill references and slash commands, so they should be stable once published. Description (for retrieval): this is the most performance-critical field. The agent reads descriptions to decide whether a skill is relevant. A good description answers: "when should I invoke this skill?" It should include the trigger conditions — "Use when you encounter a bug or unexpected behavior and need to diagnose root cause" — not just a noun description of what the skill does.

Body (agent instructions): the meat of the skill. Write it as instructions to the agent, not documentation for humans. Use numbered steps for sequences the agent should follow, use imperative language for requirements, and use inline examples for anything where the agent might otherwise guess wrong. Avoid vague instructions like "be thorough" — instead say "check the last three commits for related changes before proposing a fix." The body should be long enough to be unambiguous and short enough that the agent can hold it in working context while executing.

References (composed sub-skills via explicit tool calls): skills can call other skills. There is no special wiki-link syntax for this — composition is done via explicit tool calls in the agent's reasoning flow. The skill body instructs the agent to invoke the Skill tool with another skill's name. For example, a high-level workflow skill might instruct: "invoke the Skill tool with writing-plans, then with test-driven-development, then with verification-before-completion," delegating the detailed methodology for each phase to the corresponding specialist skill. Note: the [[...]] double-bracket pattern is used by the auto-memory system, not by the skill runtime. References should be used deliberately — every reference is a potential invocation, and over-referencing creates an agent that is always switching context instead of doing work.

15.9 Adapting to Kilo Code — custom modes and rules

Kilo Code's custom mode system is the natural host for Superpowers skills in a Kilo Code workflow. A custom mode has a name, a model selection, and a system prompt — map the skill body directly to the system prompt. The mode's model selection is where Kilo Code adds unique value: you can route brainstorming to a reasoning-capable model (Claude Opus, Gemini Pro) and executing-plans to a speed-optimized model (Claude Haiku, Gemini Flash), matching the model to the cognitive demands of each phase.

Here is a concrete example — adapting the systematic-debugging skill to a Kilo Code custom mode. In Kilo Code's custom mode configuration (typically in .kilocode/modes/ as a YAML or JSON file):

# .kilocode/modes/systematic-debugging.yaml
name: "Systematic Debugging"
slug: systematic-debugging
model: claude-opus-4-5           # reasoning-heavy: root cause analysis benefits from depth
roleDefinition: |
  You are a systematic debugger. When diagnosing bugs, you follow the
  hypothesis cycle: (1) read the failing output and form ONE specific
  hypothesis about root cause — not a list, one hypothesis; (2) write
  the minimal reproducer that would confirm or deny that hypothesis;
  (3) run it; (4) if confirmed, fix the specific root cause; if denied,
  form a new hypothesis and repeat. You do not make random changes.
  You do not fix symptoms. You trace to root cause every time.
customInstructions: |
  Before proposing any fix, state your current hypothesis explicitly
  in the format: "Hypothesis: [root cause]. Evidence: [what led me here]."

Kilo Code rules add a complementary layer. Where modes define behavior per-conversation, rules define behavior across all modes — for example, a rule that "always run tests after any file edit" applies regardless of which mode is active. Use rules for the invariants of your methodology (never commit to main, always verify before declaring done) and modes for the phase-specific behaviors (how to brainstorm, how to debug, how to write plans). Together, modes plus rules give you the full Superpowers methodology in a Kilo Code deployment.

15.10 Adapting to Gemini CLI — GEMINI.md and activate_skill

Gemini CLI's skill system uses the same SKILL.md format, but the integration requires explicit wiring via GEMINI.md. The first step is registering the skills so the agent knows they exist. In your project GEMINI.md (or global ~/.gemini/GEMINI.md), add a section that lists your methodology skills with short descriptions:

## Available Methodology Skills
The following skills are available for this project. Activate them with
activate_skill when the task matches.

- **brainstorming** — activate before any creative feature work
- **writing-plans** — activate when given a spec to decompose into a plan
- **systematic-debugging** — activate when diagnosing a bug or unexpected behavior
- **verification-before-completion** — activate before declaring any task done
- **test-driven-development** — activate for any new implementation task

When a task matches, the agent calls activate_skill("systematic-debugging") (or the appropriate skill name), which loads the full SKILL.md body into the active context. From that point, the skill's instructions govern the agent's behavior for the current task. The explicit activation shows up in the conversation log, which is useful for auditing: you can see exactly which methodology steps were applied to which tasks.

For teams that want a closer approximation of Claude Code's auto-invocation, the workaround is a session-opening instruction in GEMINI.md: "At the start of every session, activate the using-superpowers skill to orient yourself to this project's methodology." This is a soft instruction rather than a hard hook, but in practice the model follows it reliably. An alternative is to use Gemini CLI's session-start hook (if supported in your version) to inject an orientation message programmatically. Verify hook support in your Gemini CLI version before depending on this.

15.11 What you give up outside Claude Code

Auto-invocation via SessionStart hook is the primary feature lost outside Claude Code. In Claude Code, the methodology is on by default — the using-superpowers meta-skill fires at session start without any user action, and skills in the system-reminder context are available without explicit activation. In Gemini CLI and Kilo Code, the methodology is opt-in per task. This is not a fatal flaw, but it is a meaningful difference in practice: auto-invocation creates a floor for methodology compliance that opt-in activation does not.

The practical consequence is drift. In a team using Gemini CLI, an agent under time pressure will skip the activate_skill("brainstorming") call before diving into implementation, because nothing prevents it. In Claude Code, the brainstorming skill is in the system-reminder context and the agent's orientation to the methodology makes skipping it feel like a deliberate override rather than a silent omission. Teams migrating from Claude Code to Gemini CLI often report that their methodology compliance degrades unless they add explicit enforcement via GEMINI.md instructions.

Three workarounds for non-Claude Code deployments: (1) Explicit mode selection (Kilo Code) — require that the user selects the appropriate mode at task start, making methodology application a visible user action. (2) Explicit activate_skill calls (Gemini CLI) — add GEMINI.md instructions that name the specific skills to activate for each task type, making the default behavior skill-activation rather than skip. (3) Session-start prompt listing the methodology — in GEMINI.md or at session open, enumerate the phases and tell the agent to announce which phase it is in before starting each step. This is the lowest-fidelity workaround but requires zero additional tooling.

15.12 Writing your first skill

Start with a daily friction point — a workflow you correct the agent on repeatedly. A common first skill for many teams is "always read the existing implementation before answering questions about it" or "always check the latest API docs before using an unfamiliar method." Here is a concrete example: a skill that enforces committing at the end of every completed task, because agents frequently leave work uncommitted when a session ends.

Create the skill directory and file: mkdir -p ~/.claude/skills/commit-on-complete && touch ~/.claude/skills/commit-on-complete/SKILL.md. Then write the SKILL.md:

---
name: commit-on-complete
description: >
  Use when a task is declared complete. Ensures all work is committed to
  git before closing out the task. Invoke before any "task done" declaration.
---

# Commit on Complete

Before declaring a task complete, you MUST:

1. Run `git status` to identify all modified and untracked files related
   to this task.
2. Stage the relevant files explicitly (never use `git add .` — stage by
   file or directory to avoid committing unrelated changes or secrets).
3. Write a commit message following the project's commit convention.
   If no convention is visible, use conventional commits:
   `type(scope): short description`.
4. Commit and confirm the commit was created with `git log --oneline -1`.
5. Only then declare the task complete.

Do NOT skip this if the changes seem small. Every completed task ends
with a commit.

Restart Claude Code (or open a new session) and the skill appears in your system-reminder context. Test it by completing a small code change — the agent should now run through the commit checklist before saying "done." The first skill you write is usually the most revealing: the process of encoding the workflow as agent instructions forces you to articulate exactly what the agent should do, which often reveals that your mental model of the workflow was fuzzier than you realized. Refine the SKILL.md based on what you observe, and after two or three sessions you will have a skill that reliably enforces the behavior.

15.13 Skill and mode composition — chaining methodology

Skills become more powerful when composed. In Claude Code, a high-level workflow skill can orchestrate an entire development cycle by instructing the agent to invoke specialist skills in sequence via explicit Skill tool calls. For example, a feature-dev skill might instruct the agent to: invoke the Skill tool with brainstorming to explore the problem space, then with writing-plans to produce the implementation plan, then with executing-plans to work through it, then with verification-before-completion before declaring done. The user invokes one skill; the methodology handles the phase sequencing automatically.

The Skill tool is the mechanism for this composition — there is no special wiki-link syntax. The skill body contains natural-language instructions telling the agent to call Skill with another skill's name at the appropriate step. The referenced skill then runs within the same conversation, with its own instructions layered on top of the parent skill's instructions. This is not inheritance — both sets of instructions are active simultaneously, which means there is a risk of conflict if skills are not written with composition in mind. Good composed skills are aware of each other: the high-level skill sets the task context and delegates the how to the specialist skill, rather than both trying to specify behavior at the same level of detail.

In Kilo Code, composition works through the Orchestrator mode. An Orchestrator-mode conversation routes tasks to specialist modes: "This task requires brainstorming first — switching to Brainstorming mode, then Planning mode, then Execution mode." This is more explicit than Claude Code's transparent skill invocation, but it gives the user full visibility into which methodology phase is active. For teams that want methodology transparency as a feature (not a bug), Kilo Code's explicit mode-switching is the right implementation. The tradeoff is friction: every phase transition requires a user action or an Orchestrator decision rather than happening silently within a single conversation.

15.14 Testing skills — does it fire?

The most common failure mode for new skills is a description that does not trigger. The agent makes skill invocation decisions based on description matching — if the description does not match the task as the agent describes it to itself, the skill sits idle. The diagnostic: after writing a skill, ask the agent to describe the task you intend the skill to handle, then compare that description to your skill's description field. If there is no lexical or semantic overlap, the skill will not fire. Fix by rewriting the description to use the same vocabulary the agent uses when it encounters the task type.

The second failure mode is an overruling skill — a skill so broadly described that it fires for tasks it should not handle, adding overhead to simple tasks and causing the agent to over-apply methodology. The test: deliberately give the agent a trivial task (a one-word variable rename, a comment typo fix) and watch whether your skill fires. If it does, narrow the description with specificity indicators: "Use when the task involves multiple files or requires design decisions" rather than "Use for coding tasks." The description is a classifier, not a label — write it with classification precision in mind.

A third failure mode is a skill that fires but is then silently overridden by user instructions or other context. This surfaces as the agent acknowledging the skill ("I'll follow the systematic-debugging approach") and then immediately reverting to its default behavior. The fix is usually language strength in the skill body — replace advisory phrasing with imperative requirements, and add explicit checkpoints ("Do not proceed to step 2 until you have stated your hypothesis aloud"). Testing with adversarial prompts ("just quickly fix it, skip the debugging steps") reveals whether your skill's instructions hold up under pressure. A well-written skill should survive the user's impatience.

Walkthrough · Ship a methodology bundle for your team

This walkthrough encodes one workflow — the PR creation flow — as a Claude Code skill, a Kilo Code mode, and a Gemini CLI session-start prompt. By the end you will have a distributable methodology bundle that any teammate can install regardless of their tool choice.

Step 1: Define the workflow artifact. Before encoding anything, write the workflow as plain English. The PR creation flow for most teams looks like: (1) confirm all tests pass and there are no uncommitted changes; (2) write a PR description that summarizes the change, the motivation, and any testing notes; (3) identify the right reviewers; (4) create the PR and post a brief summary to the team channel. This is the ground truth that all three implementations will encode. Write it in a file called pr-creation-workflow.md — you will reference it throughout the steps.

Step 2: Claude Code skill. Create ~/.claude/skills/create-pr/SKILL.md:

  PR creation checklist before opening the PR.

1. **Tests green**: run the full test suite. If any test fails, stop and
   fix the failure — do not create a PR with a red suite.

   appropriate message before proceeding.

   `git log` authors on the affected files.
5. **Create the PR**: use `gh pr create` with the description and reviewers.
6. **Team notification**: post a one-sentence summary to the team Slack
   channel if the change is significant (more than 10 lines changed).

What you've built. A tool-agnostic methodology bundle that encodes one workflow as three first-class artifacts. The pattern scales: apply it to your deployment workflow, your incident response runbook, your database migration procedure. 16. MCP Servers — Using and Building

What you'll learn: what MCP is and why it matters, the three primitives, how to use existing servers, how to build your own (Python canonical example), and how to ship a tiny local-notes MCP server end-to-end.

16.1 What MCP is — in plain terms

The Model Context Protocol (MCP) is an open protocol, originally authored by Anthropic and now an industry-standard adopted across the AI tooling ecosystem, that standardises how LLM-based agents connect to external tools and data sources. Before MCP, every AI coding tool and every enterprise integration had to reinvent its own ad-hoc plugin protocol — resulting in fragmented, non-transferable integrations. MCP defines a single contract: a server exposes capabilities, a client (the AI tool or harness) discovers and calls them, and the LLM receives a structured description of what's available. Anyone's MCP server works with anyone's MCP-compatible agent.

Why does this matter in practice? Ecosystem leverage. There are already hundreds of MCP servers — for databases, version control, project management, communication tools, cloud APIs, file systems, and more. When you configure one of them in Claude Code or Kilo Code, your agent immediately gains the ability to query Jira tickets, post Slack messages, read Confluence pages, or look up GitHub issues — without a single line of integration code on your part. You simply point your tool at a server and it works. The protocol also future-proofs your work: if you build an MCP server for your team's internal API today, it will work with whatever agent harness your team adopts next year.

MCP is also the reason Claude Code's deferred tools list (those <system-reminder> entries you've seen) can include mcp__claude_ai_Atlassian__getJiraIssue alongside mcp__claude_ai_Slack__slack_send_message — each of those is a tool exposed by an MCP server that has been registered with the harness. The harness discovers the server, fetches its tool list, and injects the tool schemas into the model's context so the model knows what to call.

16.2 The three primitives — tools, resources, prompts

MCP servers expose exactly three kinds of capabilities. Understanding each primitive is essential before you build or configure a server.

PrimitiveWhat it isWhen to use it
Tools Callable functions with side effects. The agent invokes a tool with typed parameters and receives a structured result. Tools can create, update, delete, query, or send — anything that requires executing an action against an external system. Any time the agent needs to do something: create a Jira ticket, send a Slack message, run a database query, push a file to S3, trigger a CI job.
Resources Read-only, referenceable data identified by a URI. The agent (or user) requests a resource by URI and receives its content. Resources are pulled, not called — they don't execute logic, they return data. Any time there is large, stable, or reference content the agent might need to read: a Confluence page, a file from an S3 bucket, a database schema, a configuration document. Resources avoid the overhead of tool round-trips for pure reads.
Prompts Pre-built, guided workflows that the user or harness can invoke by name (typically via a slash command). A prompt template encodes the instructions and any required parameters for a specific, repeatable task. Any time there is a workflow complex enough to benefit from a curated preamble: a standup-update generator, a code-review template, an incident-response runbook. Prompts give non-technical users a safe, structured entry point into agent capabilities.

Most MCP servers focus primarily on tools, because tools are the most broadly useful primitive for agent-driven work. Resources are the right choice when the content is large (several kilobytes of documentation), read-only, and likely to be reused across multiple tool calls in the same session — the agent can reference the URI rather than re-fetching through a tool each time. Prompts are the least commonly authored but the most valuable for encoding team workflows that less experienced users should follow consistently.

16.3 Transport — stdio vs HTTP/SSE

MCP supports two transport mechanisms that determine how the client and server communicate. The choice has significant operational implications.

MechanismClient spawns the server as a local subprocess; communicates over stdin/stdout JSON-RPC.Server runs as a persistent HTTP process; client connects via Server-Sent Events for streaming + HTTP POST for calls.

For the vast majority of servers you will author yourself — especially the kind of local-productivity or team-internal servers described in this chapter — stdio is the right default. It requires no networking, no authentication infrastructure, and the server binary is just a script you run. HTTP/SSE becomes necessary when multiple team members need to share a single server instance (e.g., a central integration with your company's internal API that requires credentials you don't want to distribute), or when the server needs to maintain state across multiple client connections.

16.4 Existing MCP server tour — Atlassian, Slack, Box, Figma, GitHub

Atlassian MCP server surfaces the full breadth of Jira and Confluence operations. On the Jira side, you get tools to search issues with JQL (searchJiraIssuesUsingJql), fetch individual issues, create and edit issues, transition issues through workflows, add comments, and log work. On the Confluence side, you can get and search pages, create new pages, add inline and footer comments, and traverse page hierarchies. If your team uses Jira for backlog management, the Atlassian MCP server is probably the highest-leverage integration you can add: agents can now read the ticket context before writing code and update the ticket status when they're done.

Slack MCP server exposes channel reading, thread reading, user profile lookup, message sending (including drafts and scheduled sends), channel and user search, and canvas creation and editing. For an agent doing team-facing work — posting standup updates, sending PR notifications, surfacing deployment summaries to a channel — the Slack server is indispensable. Note that the server requires appropriate OAuth scopes for the workspace; read-only scopes suffice for most ambient-awareness use cases, while send scopes require explicit OAuth approval.

Box MCP server provides file and folder CRUD operations, content retrieval, metadata templates, search (by keyword or metadata), collaboration listing, and file commenting. If your team stores documentation, contracts, or design assets in Box, this server gives agents the ability to retrieve reference materials, upload generated artifacts, and maintain a structured audit trail of what was created and when.

Figma MCP server enables read access to Figma design files, component libraries, and diagrams (including FigJam boards). With authentication, agents can retrieve design specs, inspect component properties, and extract style tokens. The primary use case is bridging design and code: an agent implementing a UI component can fetch the exact spec from Figma rather than relying on a screenshot or a human description.

GitHub MCP server wraps the GitHub REST and GraphQL APIs to expose repository operations, issue and PR management, code search, file content retrieval, and workflow status. For an agent doing software development work, this is frequently the first MCP server you should add: the agent can look up open issues, read PR comments, fetch file contents from a branch, and create or update issues without leaving the conversation.

16.5 Adding an MCP server to Kilo Code and Claude Code

Both tools use a JSON configuration file to register MCP servers. The structure is nearly identical; the differences are in where the file lives and what the top-level key is called.

Claude Code reads MCP server configuration from ~/.claude/settings.json (global) or .claude/settings.json (project-local). Add a mcpServers key:

16.6 Authoring an MCP server — Python or TypeScript

Anthropic provides official SDKs for both Python (mcp on PyPI) and TypeScript (@modelcontextprotocol/sdk on npm). Both expose the same protocol surface through idiomatic language patterns, and both support stdio and HTTP/SSE transports out of the box.

Python is the natural choice when your server needs to interact with ML models, data science libraries, internal Python-based systems, or when the team is primarily Python-fluent. The SDK is installable with pip install mcp and requires Python 3.10+. The programming model uses async def handlers decorated with SDK decorators — familiar to anyone who has written FastAPI or asyncio code. Because most AI-adjacent tooling (LangChain, HuggingFace, custom model wrappers) lives in the Python ecosystem, Python MCP servers tend to be the right fit for ML-adjacent integrations.

TypeScript is the right choice when your server needs to integrate deeply with the npm ecosystem, when the rest of your frontend or backend is TypeScript/Node, or when you want to publish to npm for easy team distribution. The TS SDK mirrors the Python SDK's structure with TypeScript-idiomatic wrappers. The official MCP quick-start at modelcontextprotocol.io/quickstart/server shows both languages side by side. For this chapter, all examples use Python because it requires less toolchain overhead for a first server.

16.7 The server skeleton — handlers, schemas, errors

Every MCP server, regardless of what it does, has the same structural skeleton: it declares its capabilities, registers handlers for each capability type, and runs a transport loop. Here is the minimal Python skeleton using the mcp SDK:

from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.types import Tool, TextContent
import asyncio

app = Server("my-server")

@app.list_tools()
async def list_tools() -> list[Tool]:
    return [
        Tool(
            name="hello",
            description="Returns a greeting. Call this to test the server is alive.",
            inputSchema={
                "type": "object",
                "properties": {
                    "name": {"type": "string", "description": "Name to greet"}
                },
                "required": ["name"]
            }
        )
    ]

@app.call_tool()
async def call_tool(name: str, arguments: dict) -> list[TextContent]:
    if name == "hello":
        return [TextContent(type="text", text=f"Hello, {arguments['name']}!")]
    raise ValueError(f"Unknown tool: {name}")

async def main():
    async with stdio_server() as (read, write):
        await app.run(read, write, app.create_initialization_options())

if __name__ == "__main__":
    asyncio.run(main())

The same shape applies when you add resources: decorate an async handler with @app.list_resources() and another with @app.read_resource(). For prompts: @app.list_prompts() and @app.get_prompt(). The SDK handles protocol framing, capability negotiation, and transport plumbing — your only job is to implement the handlers. The TypeScript equivalent has an identical structure: server.setRequestHandler(ListToolsRequestSchema, ...) and server.setRequestHandler(CallToolRequestSchema, ...) — see the official TS quick-start for the verbatim equivalent.

For error handling, raise a standard Python exception from call_tool — the SDK will catch it and return a proper MCP error response to the client. For user-facing errors (e.g., "note not found"), return a TextContent with the error message rather than raising, so the agent can read and reason about the error in its next turn rather than treating it as a fatal fault.

16.8 Designing tools agents use well

The most important thing to understand about tool design for MCP servers is that the model reads your tool descriptions. The description field of each Tool object and the description fields of each parameter in the JSON schema are injected verbatim into the model's context. They are not documentation for humans; they are instructions to the model. A vague description produces unreliable tool calls; a precise description produces reliable ones.

Good tool design principles: Give each tool a single, clearly bounded purpose. Name it with a verb that describes what it does (create_note, search_notes, not notes_operation). Write the description as if instructing a junior developer: "Creates a new note with the given title and body. Returns the note ID. Call this when the user asks to save, record, or note something." Keep parameter schemas narrow — use enums for fixed choices, mark only truly required fields as required, and describe each parameter's purpose and acceptable range. Make tools idempotent where possible so the model can safely retry a call if it loses the result.

Anti-pattern: the kitchen-sink tool. A single tool called manage_notes with a required action parameter that accepts "create", "update", "delete", "list", or "search" is a common beginner mistake. The model has to make two decisions — which tool to call, and which action to pass — and the parameter schemas for each action are different but all stuffed into one schema. The result is frequent incorrect calls, incorrect action values, and missing required parameters. Split it: one tool per action. The agent's decision of which tool to call is made at the selection step where the model is most reliable; the "what to pass" decision then has a clean, unambiguous schema.

16.9 Authoring resources — when they fit better than tools

Resources are the right primitive when your server has read-only data that the agent might want to reference multiple times across a session, or data that is large enough that streaming it as a resource (identified by URI) is preferable to embedding it in a tool call response. The key distinction: a tool call is a one-off action; a resource is a named, stable thing that can be referenced by URI. The agent (or the harness) can fetch a resource once, cache it locally for the session, and reference it by URI in subsequent tool calls without re-fetching.

Concrete examples where resources are the right choice: a server that exposes your team's architecture decision records (each ADR as a resource URI like adr://decisions/004-use-postgres); a server that exposes your API's OpenAPI spec (openapi://spec/v3); a server that exposes database schema documentation. In each case, the content is large, read-only, and reference material — not something that needs to be re-generated on each call. Implement @app.list_resources() to return a list of available URIs and @app.read_resource() to return the content for a given URI. The content can be text or binary (base64-encoded); use TextContent for text and BlobResourceContents for binary.

16.10 Authoring prompts — guided workflows

Prompts are pre-built, parameterised message templates that the harness or user can invoke by name. When a user invokes a prompt (typically via a /prompt-name command in the chat UI, or programmatically via the harness's prompt invocation API), the MCP server receives the invocation with any provided arguments, and returns a list of messages that the harness injects into the conversation as if the user had typed them. This gives you a way to encode multi-step, carefully worded workflows that less experienced users can trigger without having to know the exact phrasing.

Implement @app.list_prompts() to return available prompt templates and @app.get_prompt() to return the rendered messages for a given prompt name and arguments. A well-designed prompt template for a standup generator might accept a since date parameter and return a system message instructing the agent to fetch recent commits, recent Jira completions, and current blockers, then format them in the team's standup format. The user just types /standup since=yesterday rather than having to remember and type all of that.

The exact invocation syntax for prompts depends on the harness. In Claude Code, slash commands that map to MCP prompts are surfaced when the server is registered and the harness discovers the prompt list — verify with /mcp to see what prompts are available from each registered server. In Kilo Code, MCP prompts appear in the prompt library accessible from the chat UI.

16.11 Auth and secrets in MCP servers

Environment variables are the right choice for the vast majority of MCP server authentication scenarios. For an API key (GitHub PAT, Slack Bot Token, an internal API key), inject it as an env var in the server's registration config ("env": {"GITHUB_TOKEN": "..."} in the settings JSON). The server reads os.environ["GITHUB_TOKEN"] at startup or at call time. For local developer tools, this is ideal: the key lives in the settings file, which lives in the developer's home directory and is not committed to source control. The secret never appears in the server code, never appears in conversation context, and is scoped to the local machine.

OAuth is necessary when the server needs to act on behalf of a specific user rather than a service account — typically when you're integrating with user-scoped APIs (personal Google Drive, user-specific Jira permissions, Slack DMs on behalf of a user). OAuth adds significant implementation complexity: you need to implement the authorization code flow, store and refresh tokens, and handle token expiry during long-running sessions. For most team-internal MCP servers, a service account API key (env var) is the right answer and OAuth is unnecessary overhead. When you do need OAuth, the MCP specification defines an authorization extension; consult the official docs at modelcontextprotocol.io/docs/concepts/authentication for the current recommended implementation pattern, as the OAuth profile for MCP is still evolving.

Never hardcode secrets in the server script itself. Never log secrets in the server's stdout (the MCP client reads stdout as the protocol stream — any debug output that accidentally contains a secret will be visible in the harness's MCP log viewer). Use stderr for all debug and log output from your server; the MCP SDK routes stderr to the harness's log panel, separate from the protocol stream.

16.12 Testing your MCP server

Unit tests for handlers are straightforward: because each handler is an async function that takes plain Python arguments and returns typed objects, you can test them directly without running the full transport stack. Mock the database or external API calls, call the handler functions directly in pytest-asyncio tests, and assert on the returned TextContent or Tool lists. This covers the logic of your server without any MCP infrastructure.

Integration testing against the real MCP protocol requires a client. The official tool for this is the MCP Inspector: run npx @modelcontextprotocol/inspector python your_server.py and it opens a browser-based UI that lets you browse the server's tool/resource/prompt list, invoke tools with arbitrary parameters, and inspect the raw JSON-RPC messages. This is the fastest way to verify that your server's schemas are correct, that tool calls return the expected structure, and that error handling works. Use the Inspector before registering your server in Claude Code or Kilo Code — it will catch schema errors and missing fields that would otherwise show up as cryptic "tool not found" errors in the harness.

For automated integration tests, the Python MCP SDK includes test utilities that let you create an in-process client/server pair without a real transport: instantiate your server and a test client, run them in the same event loop, and call tools programmatically. This is appropriate for CI pipelines where you want to test the full MCP protocol path (capability negotiation, tool listing, tool calling, error propagation) without spawning a subprocess.

16.13 Publishing and distribution

PyPI and npm are the standard distribution channels for MCP servers intended for broad use. A Python MCP server published to PyPI can be installed with pip install your-server-package and registered in Claude Code/Kilo Code with "command": "python", "args": ["-m", "your_server_package"]. A TypeScript server published to npm can be registered with "command": "npx", "args": ["-y", "your-npm-package"] — which downloads and runs the latest version automatically. For internal team distribution, a private PyPI repository or npm registry is the cleanest solution; alternatively, install directly from a Git URL (pip install git+https://github.com/your-org/your-server.git).

GitHub Releases are appropriate for servers that are too team-specific or deployment-specific to warrant a PyPI/npm package. Tag a release, include installation instructions in the release notes, and have teammates clone the repo and configure the command path directly. This is the right pattern for servers that require project-specific configuration at installation time.

The MCP Registry at registry.modelcontextprotocol.io is the growing community index of publicly available MCP servers. If you build a server that might benefit others outside your team, submitting it to the registry makes it discoverable. Check the registry before building a new server — there is a good chance someone has already built and published a server for the API you need.

16.14 Hands-on: build a tiny local-notes MCP server

Walkthrough · Build a tiny local-notes MCP server

Goal. Build a Python MCP server with three tools — add_note, list_notes, search_notes — backed by a SQLite database. Register it in Claude Code. Invoke it. Verify it works.

Step 1: Install the SDK.

pip install mcp

Step 2: Write notes_server.py. Save this to ~/tools/notes_server.py (or any stable path):

#!/usr/bin/env python3
"""Local notes MCP server — SQLite-backed."""
import os
import sqlite3
import asyncio
from datetime import datetime, timezone
from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.types import Tool, TextContent

DB_PATH = os.environ.get("NOTES_DB_PATH", os.path.expanduser("~/.notes.db"))

def get_db() -> sqlite3.Connection:
    conn = sqlite3.connect(DB_PATH)
    conn.execute(
        "CREATE TABLE IF NOT EXISTS notes "
        "(id INTEGER PRIMARY KEY AUTOINCREMENT, "
        " title TEXT NOT NULL, "
        " body TEXT NOT NULL, "
        " created_at TEXT NOT NULL)"
    )
    conn.commit()
    return conn

app = Server("local-notes")

@app.list_tools()
async def list_tools() -> list[Tool]:
    return [
        Tool(
            name="add_note",
            description=(
                "Saves a new note with a title and body to the local notes database. "
                "Call this when the user asks to save, record, remember, or note something. "
                "Returns the ID of the created note."
            ),
            inputSchema={
                "type": "object",
                "properties": {
                    "title": {"type": "string", "description": "Short title for the note"},
                    "body":  {"type": "string", "description": "Full content of the note"}
                },
                "required": ["title", "body"]
            }
        ),
        Tool(
            name="list_notes",
            description=(
                "Returns all notes in the database, newest first. "
                "Call this when the user asks to see, show, or list their notes. "
                "Returns a numbered list with IDs, titles, and creation dates."
            ),
            inputSchema={"type": "object", "properties": {}, "required": []}
        ),
        Tool(
            name="search_notes",
            description=(
                "Searches notes by keyword in title or body. Case-insensitive. "
                "Call this when the user wants to find a specific note or recalls partial content. "
                "Returns matching notes with their IDs, titles, and body previews."
            ),
            inputSchema={
                "type": "object",
                "properties": {
                    "query": {"type": "string", "description": "Search term to look for in title or body"}
                },
                "required": ["query"]
            }
        ),
    ]

@app.call_tool()
async def call_tool(name: str, arguments: dict) -> list[TextContent]:
    conn = get_db()
    try:
        if name == "add_note":
            now = datetime.now(timezone.utc).isoformat()
            cur = conn.execute(
                "INSERT INTO notes (title, body, created_at) VALUES (?, ?, ?)",
                (arguments["title"], arguments["body"], now)
            )
            conn.commit()
            return [TextContent(type="text",
                                text=f"Note saved. ID: {cur.lastrowid}")]

        elif name == "list_notes":
            rows = conn.execute(
                "SELECT id, title, created_at FROM notes ORDER BY id DESC"
            ).fetchall()
            if not rows:
                return [TextContent(type="text", text="No notes yet.")]
            lines = [f"[{r[0]}] {r[1]} ({r[2][:10]})" for r in rows]
            return [TextContent(type="text", text="\n".join(lines))]

        elif name == "search_notes":
            q = f"%{arguments['query']}%"
            rows = conn.execute(
                "SELECT id, title, body FROM notes "
                "WHERE title LIKE ? OR body LIKE ? ORDER BY id DESC",
                (q, q)
            ).fetchall()
            if not rows:
                return [TextContent(type="text", text="No matching notes.")]
            lines = [f"[{r[0]}] {r[1]}: {r[2][:80]}..." for r in rows]
            return [TextContent(type="text", text="\n".join(lines))]

        else:
            return [TextContent(type="text", text=f"Unknown tool: {name}")]
    finally:
        conn.close()

async def main():
    async with stdio_server() as (read, write):
        await app.run(read, write, app.create_initialization_options())

if __name__ == "__main__":
    asyncio.run(main())

Step 3: Test with the MCP Inspector. Before registering with Claude Code, verify the server works:

npx @modelcontextprotocol/inspector python ~/tools/notes_server.py

Open the Inspector URL in your browser. In the Tools panel, you should see add_note, list_notes, and search_notes. Call add_note with {"title": "test", "body": "hello from inspector"} and confirm you get back a note ID. Call list_notes and verify the note appears.

Step 4: Register with Claude Code. Add to ~/.claude/settings.json:

{
  "mcpServers": {
    "local-notes": {
      "command": "python",
      "args": ["/Users/you/tools/notes_server.py"],
      "env": {
        "NOTES_DB_PATH": "/Users/you/.notes.db"
      }
    }
  }
}

Replace /Users/you with your actual home directory path.

Step 5: Invoke and verify. Start a new Claude Code session. Run /mcp — you should see local-notes listed as a connected server with 3 tools. Then say:

Please add a note titled "MCP chapter done" with body "Finished Ch 16 of Hero to Architect".

Claude Code will call add_note and return the note ID. Then say:

List all my notes.

You should see the note you just created. Finally:

Search my notes for "architect".

The note appears in search results. Your local-notes MCP server is live and working end-to-end.

What to extend next. Add an update_note tool and a delete_note tool. Add a resource that exposes the full notes list as a URI (notes://all) so the agent can reference it without calling a tool. Add a daily-summary prompt that renders a standup-style summary of notes created today. Each of these extensions follows exactly the same SDK patterns shown above.
